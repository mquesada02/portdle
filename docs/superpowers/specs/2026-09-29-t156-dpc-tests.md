# Ticket spec: Harden device progress choice tests (#156)

Ticket [#156](https://github.com/mquesada02/portdle/issues/156) of Spec 4 (accounts, sync, and leaderboards; issue #127, spec file `docs/superpowers/specs/2026-09-28-spec4-backend.md`). Map: #114. Follow-up from the Device progress choice ticket (#138, PR #154, spec `docs/superpowers/specs/2026-09-29-t138-device-progress-choice.md`), accepted by the owner on 2026-09-30. The owner decision on preferences (2026-09-30) is written into Spec 4. It has no blockers. This ticket changes tests and one test helper, plus one owner decision written into Spec 4. Except for one behaviour change (below), it changes no app behaviour, no `Remote`, no adapter, no SQL, no migration, and no glossary term, and it needs no owner steps.

In this spec "progress" means the Daily, run, Best, and Codex rows on the device, as in #138; preferences alone are not progress.

## Problem Statement

Three gaps remain in the tests of the Device progress choice. One test ends with a fixed 50 ms sleep before it asserts that nothing was pulled or pushed, so it can pass before Sync has reached the pending check (a false pass) and it slows the suite. Nothing proves that Escape on the choice stays out of the How-to dialog, which is the reason the choice stops the key event. The Sync module's pending rule test misses a device with only Codex rows and a device whose stored Daily cannot be read.

## Solution

The tests wait for an observable result instead of a clock. A new App-level test proves Escape on the choice does not close the How-to under it. Two new pending-rule tests cover a Codex-only device and an unreadable stored Daily. Spec 4 also records the owner decision of 2026-09-30 on "Add this device's progress to your account": the account's preferences win, and only Codex, Best, run, and Daily rows are added.

## User Stories

1. As the owner, I want the device progress choice test to stop using a fixed sleep, so that it fails whenever Sync pulls or pushes while the choice is pending, and never passes by luck of timing.
2. As the owner, I want the test to wait for a signal that Sync ran its pending check, so that the "nothing pulled or pushed" assertion covers a finished check.
3. As the owner, I want a test that Escape on the choice does not reach the How-to dialog, so that the choice never closes the How-to (and sets its seen flag) by accident.
4. As the owner, I want a test that a device with only Codex rows is pending, so that the most common first progress is covered by the pending rule.
5. As the owner, I want a test that a device whose stored Daily cannot be read is not pending, so that the rule counts only rows Sync can import.
6. As the owner, I want Spec 4 to state that the account's preferences win on "Add this device's progress", so that the written spec matches the decision.
7. As the owner, I want the Device progress choice bullet in Implementation Decisions to agree with that decision, so that the spec does not contradict itself.

## Implementation Decisions

- **Wait signal for the sleep.** The fake `Remote` gains a counter of started `getAccount` calls (a `getAccountCalls` field). The account menu calls `getAccount` once on mount and Sync calls it once at the start of each run; the two may happen in either order. The test first waits for the choice dialog (the menu shows it from its own `getAccount` result, so the menu's call has happened), then for the counter to reach 2 (Sync's first run has started), then fires a window `focus` inside `act` (a Sync trigger). A trigger during a run queues one more run after it, and runs never overlap, so the counter reaching 3 proves the first run has finished its pending check. The test waits for that, then asserts nothing was pulled or pushed and the local rows stayed. It runs for two accounts, one with a confirmed name and one with an unconfirmed name, because only the confirmed one reaches the pending check on its own (an unconfirmed name already stops Sync before any pull, so that run cannot show a missing gate); the unconfirmed run also asserts the name confirm is not shown, which is the ordering check the test has today. Waiting for only 1 would be unsound, because that could be the menu's call. The counter is the only change to the fake; it breaks no existing test.
- **Escape test.** A device that never saw the How-to and holds another account's progress opens the How-to and the choice; the test builds its own device, because the existing device helper marks the How-to as seen. The existing no-dismiss test already presses Escape on the choice but never has the How-to open, so this is not a duplicate. Escape is sent twice: a real key press with focus on a button inside the choice (the test focuses the Add button and asserts the focus is inside the dialog first, because the test setup's `showModal` stub focuses only the dialog element, which is not focusable, so a press would otherwise land on the page body and miss the choice's handler), and a `keyDown` fired on the choice dialog. The test renders `App` without StrictMode, as the existing mount helper does. After each, the How-to dialog is still open, the choice is still open, and the How-to seen flag is still unset. The How-to closes on Escape through a document listener, so this fails if the choice stops stopping the event (checked by temporarily removing the stop).
- **Pending-rule tests.** Both go in the Sync module test file beside the existing pending rule test, and use `Persist` over `memoryStore`, as it does. Codex only: a device marked as another account's with only a Codex entry is pending. Unreadable Daily: a stored Daily whose value does not read back as a Daily (for example text that is not JSON) under a key with a valid category and UTC date is not pending when it is the only row, so a bad date cannot make the test pass for the wrong reason; the same device becomes pending once a readable row is added, so the unreadable row is what was ignored, not the whole device. The test keeps a reference to the memory store and writes the unreadable value straight into it under the stored Daily's key, written out as the storage tests do.
- **Spec 4 edit.** Further Notes gains the owner decision line: on 'Add this device's progress' the account's preferences win, including over preference changes made on this device while signed out that were never pushed; those pending changes of the previous user are dropped when Add is picked; the pending-change rule (#137) still applies to the same account's own changes; only Codex, Best, run, and Daily rows are added. The "Another account's device" bullet in Implementation Decisions said "imports as above", which includes pending preferences, so it is reworded to name the rows added and to state the same rule. The other bullet named Device progress choice (in UI) only says the dialog cannot be dismissed, so it stays as it is.
- **Add drops pending preferences (owner decision 2026-09-30).** A new `addDeviceProgress(persist, accountId)` in `src/sync/device-progress.ts` clears the pending preference changes, then writes the account id, and returns false if either write fails (the choice then stays pending). The Add handler in the account menu calls it. "Start from your account only" already clears everything. Sync is unchanged: with the pending preferences empty, the pull writes the account's preferences and no preference is pushed; the same account signing back in never runs Add, so its signed-out change is still pushed. Sync tests (the first asserts the signed-out change is pending before Add and gone after): a theme changed while signed out, then a different account picks Add, ends with the account's theme and no preference push; the same account signing back in still pushes its signed-out change.

## Testing Decisions

- Good tests assert what the player or the account sees (the open dialogs, the store's contents, the fake account's pull and push records), never internal calls. The seams are the ones #138 used: `App` with `memoryStore` and the fake `Remote` for the two dialog tests, and `Persist` over `memoryStore` for the pending rule.
- Prior art: the existing tests in the Device progress choice test file (the opens-over-How-to test and the no-dismiss test), the Escape test in the Account deletion tests, and the pending rule test in the Sync module tests.
- The edited sleep test, the Escape test, the two pending-rule tests, the counter on the fake `Remote`, and the Spec 4 edit, `addDeviceProgress`, and its two Sync tests are the whole change. The Escape test and the wait are checked to fail when the behaviour they guard is removed (the event stop; the pending check in Sync, for the confirmed-name run) and then restored. The Sync module test file already covers the gate at the Sync level.
- `pnpm lint`, `pnpm typecheck`, `pnpm test`, and `pnpm build` pass.

## Out of Scope

Any behaviour change to the choice, Sync, or the pending rule other than the preference drop on "Add"; other sleeps in other test files; the smoke script, migrations, and owner steps.

## Further Notes

Author calls not decided by #156 or Spec 4, listed so they can be overruled:

- The wait uses a started-call counter on the fake `Remote`, a small addition to a test helper, because nothing else the app shows tells a test that Sync finished a run that does nothing.
- The Spec 4 bullet is reworded rather than only adding the new line, because "as above" contradicts the decision.
- The unreadable-Daily case also asserts the device becomes pending with a readable row, so the test cannot pass by the rule ignoring everything.
