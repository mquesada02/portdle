# Spec: Shell, nav, How-to dialog, Help

Spec for #23. Tracker: https://github.com/mquesada02/portdle/issues/23

## Problem Statement

A player who opens Portdle today sees raw, unstyled HTML: a nav of six underlined links (three Dailies plus Blitz, History, Help), a top bar that scrolls away, and How-to rendered as a block of text at the bottom of the page instead of a dialog. There is no way to reread the rules without leaving the screen, the "Progress may not save." warning is unstyled text wherever it appears, and on a phone the nav takes space a bottom tab bar should own instead. The shell gives the player no sense of a real app.

## Solution

Portdle gets a real shell: a sticky top bar with the Portdle wordmark (linking to Daily), a "How to play" button, and the theme toggle, plus one `nav` named "Main" holding exactly four items — Daily, Blitz, History, Help. Below the medium breakpoint the nav renders as a tab bar fixed to the bottom of the viewport with an icon over a label per item and safe-area padding; at the medium breakpoint and up it sits inline in the top bar as links with a filled pill on the active item. The Daily item is highlighted on all three Daily routes. How-to becomes a native `dialog` opened with `showModal`, centered with a dimmed backdrop, trapping focus, closing on Escape, Got it, or a backdrop click, and writing How-to seen on every close path. Help shows the same rules as a numbered list in a card under the `h1` "Help". The "Progress may not save." notice becomes one shared styled component used everywhere it already renders. The global stylesheet gains the pop, shake, draw, and rise motion keyframe classes the rest of the redesign will use, already covered by the existing reduced-motion rule. A Vitest setup file stubs the native dialog and `scrollTo` so jsdom tests can exercise them. The Daily, Blitz, and History screens keep rendering exactly as they do today; only the shell around them changes.

## User Stories

### Top bar

1. As a player, I want a top bar with the Portdle wordmark, so that I always know what site I am on and can return to the Daily with one tap.
2. As a player, I want the top bar to stay visible while I scroll, so that the theme toggle and How-to button are always reachable.
3. As a player, I want a How-to button in the top bar, so that I can reread the rules without leaving the screen.
4. As a player, I want the theme toggle to keep its current behavior (follow system until clicked, then light or dark persists) and its accessible name, so that nothing I already chose is lost.
5. As a keyboard player, I want to Tab through the wordmark, nav items, How-to button, and theme toggle in order, so that I can move around without a pointer.

### Nav

6. As a player, I want a nav with exactly four items, Daily, Blitz, History, and Help, so that the main surfaces fit on a phone without hiding anything.
7. As a phone player, I want the nav as a tab bar fixed to the bottom of the screen with an icon and a label per item, so that I can switch surfaces with my thumb.
8. As a phone player, I want the tab bar to respect the device safe area, so that the home indicator does not cover the labels.
9. As a phone player, I want page content to end above the tab bar, so that the last thing on a screen is never hidden behind it.
10. As a desktop player, I want the nav as links inside the top bar, so that the screen does not waste a bottom strip.
11. As a player, I want the current nav item highlighted, so that I can see which surface I am on.
12. As a player on Protocols or Applications, I want the Daily nav item highlighted, so that the three Dailies read as one surface.

### How-to dialog

13. As a first-time player on any route, I want How-to to open as a real modal dialog centered on the screen with a dimmed backdrop, so that I read the rules before anything else.
14. As a player, I want the How-to dialog to trap focus and close on Escape, on the Got it button, or on a backdrop click, so that it behaves like every other dialog I know.
15. As a player, I want any of those dismissals to mark How-to as seen, so that it does not reopen on the next visit.
16. As a player, I want the How-to button in the top bar to open the same dialog later, so that the rules are one tap away.
17. As a screen reader user, I want the dialog to have the accessible name "How-to" and a single heading, so that it announces properly.

### Help

18. As a player, I want the Help page to show the same rules as How-to in a readable numbered card, so that a deep link to Help is useful.
19. As a player, I want Help under the `h1` "Help", so that the page structure is clear.

### Progress notice

20. As a player whose browser cannot write storage, I want the "Progress may not save." notice styled as a small visible banner, so that I notice it without it blocking play.
21. As a player, I want that same styled notice used on every screen that already shows it today, so that the warning looks consistent everywhere it appears.

### Theme, motion, and accessibility

22. As a player with reduced motion, I want the shell's animations disabled, so that the app respects my setting.
23. As a player, I want every interactive element in the shell to have a visible focus ring, so that keyboard navigation is trackable.
24. As a player on a route without a puzzle answer, I want the existing "Puzzle unavailable" state to keep working under the new shell, so that the failure case still renders.
25. As a phone player at 375px, I want no horizontal scrolling in the shell or on Help, so that the layout fits.

### Maintainer

26. As a maintainer, I want the redesign to keep the existing accessible names where behavior did not change, so that the current tests keep passing with minimal edits.
27. As a maintainer, I want jsdom test scaffolding for the native dialog and scrolling, so that UI tests run without a browser.
28. As a maintainer, I want the shell to avoid CSS that makes an ancestor the containing block for the fixed tab bar, so that the tab bar cannot silently jump to the top again.
29. As a maintainer, I want the motion keyframe classes added to the global stylesheet without being wired into any screen yet, so that later tickets can use them without redefining them.
30. As a maintainer, I want the v1 design spec's no-UI-kit and no-state-library rule kept and no web font added, so that the dependency list stays as it is.

## Implementation Decisions

### Design language

- Wordle cousin, quiet shell. Palette is Tailwind zinc for surfaces and text, with the existing dark-mode `dark` class on `html`. Every new element defines both light and dark colors. No web fonts, no UI kit, no state library.
- Layout is one centered column, matching the width the rest of the redesign will use. Breakpoint differences in this ticket are limited to nav placement: the medium breakpoint (768px) switches the nav between tab bar and top-bar links.

### Top bar

- The top bar is sticky. Left: the wordmark (a two-by-two mark plus "Portdle") linking to Daily. Right: a "How to play" icon button that opens the How-to dialog, then the existing theme toggle with the accessible name "Toggle color theme".
- The top bar, and any ancestor of the tab bar, must not use `backdrop-filter`, `filter`, or `transform` — any of these makes that element the containing block for the fixed tab bar, which then renders inside the top bar instead of at the viewport edge.

### Nav

- One `nav` element with the accessible name "Main" holds the four items Daily, Blitz, History, Help, in that order, each with an icon and a label. Below the medium breakpoint it is fixed to the bottom of the viewport, four equal columns, icon over label, with bottom padding equal to the device safe-area inset. At the medium breakpoint and up it sits inline in the top bar as text links with a filled pill on the active item.
- Daily links to the root route. It is marked active on the root route and on the Protocols and Applications routes; Blitz, History, and Help are each marked active only on their own route.
- Page content below the top bar carries bottom padding on phones that clears the fixed tab bar, so the last element on any screen is never hidden behind it.
- Removing the three per-category links from the main nav does not remove the Protocols and Applications routes themselves; a Daily switcher that links to them is a later ticket's concern. This ticket's nav holds only the four items above.

### How-to and Help

- How-to is a native `dialog` element opened with `showModal`. It opens on first visit (How-to not yet seen) on whatever route the player lands on, and reopens from the top-bar button. Its accessible name is "How-to" via its one heading. The close button reads "Got it". Escape and a click on the backdrop also close it. Every close path writes How-to seen. Closing returns focus to the element that was focused before the dialog opened, which is native dialog behavior.
- Help renders the same rules as a numbered list in a card under the `h1` "Help". How-to and Help read from one shared rules list so their copy cannot drift.

### Progress notice

- The "Progress may not save." notice becomes one shared styled component: a small, visible banner, non-blocking, announced via `role="status"`. It replaces every place that already renders that exact warning today, with no change to when it appears.

### Motion

- The pop, shake, draw, and rise keyframes and their small utility classes are added to the global stylesheet this ticket, at the durations already accepted for the redesign: pop 150ms, shake 300ms, draw 300ms, rise 300ms after a 250ms delay. The existing reduced-motion rule already zeroes all animations, so these classes need no separate reduced-motion handling. No screen applies these classes yet; that is later tickets' work.

### Test scaffolding

- A Vitest setup file stubs `HTMLDialogElement.prototype.showModal` and `close` to toggle the dialog's `open` attribute, and stubs `window.scrollTo`, so jsdom tests can open and close the How-to dialog and later tickets can assert scroll calls without a real browser.

## Testing Decisions

A good test renders the app through its public seam and asserts what a player can see or do: roles, accessible names, visible text, and focus. It does not assert class names, CSS, animation timing, or component internals, and it does not recompute expected values the way the code does. Expected strings are literals from this spec.

One seam, already existing:

- **App seam.** Render `App` with a memory store, a memory history at a route, and an injected `utcToday`. Prior art: the existing shell, Mixed Daily, Blitz, and History test files, plus the shared helpers for the memory store and `matchMedia` stub. Cover: the nav has exactly four links, named Daily, Blitz, History, and Help, all focusable; the Daily link is marked active on the root route and on the Protocols and Applications routes, and each other link only on its own route; the "How to play" button opens a dialog named "How-to"; the dialog opens on first visit on any route; Got it, Escape, and a backdrop click each close the dialog and write How-to seen, and it does not reopen after; the theme toggle keeps its existing behavior and accessible name; Help shows the `h1` "Help" and the same rule text as How-to; the "Progress may not save." notice still appears with `role="status"` wherever a page already triggers it.

Tests that must change by this ticket's decision: the existing shell test that expects six nav links ("Mixed", "Protocols", "Applications", "Blitz", "History", "Help") drops the three Daily-category links and expects "Daily" in their place; every other accessible name asserted by existing tests keeps its current value.

No snapshot tests, no visual regression, no Playwright. This ticket is proven done by `pnpm lint`, `pnpm typecheck`, `pnpm test`, and `pnpm build` all passing, in addition to the App-seam coverage above.

## Out of Scope

- The Daily switcher (Mixed/Protocols/Applications) and every other Daily screen change: board, try counter, digit slots, miss popover, reveal, stats, share
- Blitz setup, HUD, and run screens
- History row grouping or styling
- The catalog `sources` schema and validation
- Applying the pop, shake, draw, or rise classes to any screen
- Any new game feature, rule change, engine change, persistence key, or route
- A control to return the theme to system
