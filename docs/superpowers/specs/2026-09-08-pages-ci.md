# Spec: Pages CI

Spec for #7. Tracker: https://github.com/mquesada02/portdle/issues/15

## Problem Statement

A player cannot open a public Portdle site yet. The repo is private, there is no GitHub Actions workflow, and a production build does not write the GitHub Pages SPA fallback, so a refresh on a client route would 404 even after someone hosted the files. Maintainers also have no shared check that lint, typecheck, tests, schedule validity, and the production build all pass before master is published.

## Solution

Pushing to `master` and opening pull requests runs lint, typecheck, tests, `gen:schedule --check`, and the production build. A successful push to `master` deploys the Vite output as the public GitHub Pages project site at `https://mquesada02.github.io/portdle/` (private repo, public site, GitHub Pro). The production build writes `404.html` as a byte-identical copy of `index.html` so a refresh of a client route still loads the SPA. English-only, no PWA, no backend. History and Blitz stay as they are on `master`.

## Implementation Decisions

- GitHub Actions workflow triggers: `push` to `master`, and `pull_request`. No other events (no `workflow_dispatch`, no preview environments, no deploy on tags).
- One build job always runs the five commands in order, after checkout, pnpm setup from the pinned `packageManager`, Node 22 (Actions must name a runtime; this is not a product pin), and `pnpm install --frozen-lockfile`:

  1. `pnpm lint`
  2. `pnpm typecheck`
  3. `pnpm test`
  4. `pnpm gen:schedule --check` with `PORTDLE_UTC_TODAY` unset
  5. production build (`pnpm build`)

- Deploy is a separate job that needs the build job. It runs only when the event is a `push` and the ref is `master`. It uses GitHub's official Pages artifact-upload and deploy actions. The artifact is the Vite production output directory. The Pages environment name is `github-pages`. The public URL is `https://mquesada02.github.io/portdle/`. Do not publish via a `gh-pages` branch, a `docs/` folder, or a third-party Pages action.
- Permissions: checkout/build contents `read`; Pages deploy `pages: write` and `id-token: write`.
- Production build already uses Vite `base: '/portdle/'` (app shell). This ticket must not change that base or the router `basepath: '/portdle'`.
- SPA fallback copy is a **build helper** (same kind of seam as `gen:schedule`), not engine, persist, UI, or a Vite plugin. After the Vite bundle is written, the production build calls:

  ```ts
  copyIndexHtmlTo404(outputDir: string): void
  ```

  `outputDir` is the Vite production output directory. The function reads `index.html` from that directory and writes `404.html` in the same directory as a byte-identical copy. If `index.html` is missing, it throws (does not write `404.html`). It must not change `index.html`. A pre-existing `404.html` is overwritten. GitHub Pages serves that `404.html` for missing paths under `/portdle/`, which is how a refresh of a client route loads the SPA.
- English-only. Do not add i18n, a service worker, a web app manifest, a backend, Playwright, History rows, or Blitz gameplay.

## Testing Decisions

A good test checks observable behavior through a public interface. It does not inspect private helpers, mock the filesystem beyond the directory passed in, assert GitHub Actions internals, or recompute the expected bytes by re-implementing the copy. Expected values are literals: filenames `index.html` and `404.html`, and byte equality with the fixture `index.html` contents.

One Vitest seam only:

1. **SPA fallback copy** — `copyIndexHtmlTo404(outputDir)`. Cover: when the directory contains `index.html`, `404.html` exists and is byte-identical to it; when `index.html` is missing, the call fails and `404.html` is not written; `index.html` bytes are unchanged after a successful copy; a pre-existing `404.html` is overwritten to match `index.html`; a second call leaves `404.html` still byte-identical to `index.html`. Use a temporary fixture directory, not the real Vite `dist`. Do not run Playwright. Do not hit live GitHub Pages. Do not assert workflow YAML from Vitest.

Prior art: `scripts/gen-schedule.test.ts` exercises a CLI through `execFileSync`. This ticket tests the copy function directly (higher seam than spawning the full production build).

The CI workflow is **not** a Vitest seam. The YAML is the contract: pull requests and `master` run lint, typecheck, test, `gen:schedule --check`, and build; only a `master` push deploys the Vite output to `https://mquesada02.github.io/portdle/`. Prove it by the workflow matching that contract, plus a local run of those five pnpm commands. No GitHub Actions mock.

## Out of Scope

- History rows and Blitz (default or inverted) gameplay; leave those routes as they are on `master`
- Accounts, leaderboards, inverted Daily, PWA, archive play, skip, i18n, custom domain, IANA scrape
- Playwright, live Pages probes, PR preview deploys, `workflow_dispatch`
- Changing catalogs, schedules, engine, persist, How-to, theme, or nav
- Changing Vite `base` or router `basepath`
- A backend, cookies, analytics, UI kit, Redux/Zustand
- Publishing via a `gh-pages` branch or a `docs/` folder
