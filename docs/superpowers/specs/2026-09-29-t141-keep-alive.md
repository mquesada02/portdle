# Ticket spec: Keep-alive job

Spec for #141. Tracker: https://github.com/mquesada02/portdle/issues/141. Parent: Spec 4 (stories 67 to 69), https://github.com/mquesada02/portdle/issues/127 (`docs/superpowers/specs/2026-09-28-spec4-backend.md`, Operations, "Keep-alive"). Map: https://github.com/mquesada02/portdle/issues/114.

## Problem Statement

The Supabase free project pauses after a week without activity. A paused backend breaks sign-in, sync, and the Leaderboards tab for every player until the owner restores it by hand.

## Solution

The Daily freeze workflow gains a second, separate job. Every day it sends one cheap read to the Supabase REST API with the public anon key. The two jobs do not depend on each other: a failed ping cannot fail the freeze, and a failed freeze cannot skip the ping. The URL and key come from the repository Actions variables `SUPABASE_URL` and `SUPABASE_ANON_KEY`. The "anon key" is the public `sb_publishable_` key; this spec uses "anon key" for it throughout.

## User Stories

1. As the owner, I want a daily ping to the Supabase REST API, so that the free project never pauses from inactivity.
2. As the owner, I want the ping in the existing Daily freeze workflow, so that one schedule drives both daily chores.
3. As the owner, I want the ping and the freeze to be independent jobs, so that a failed ping cannot fail the freeze and a failed freeze cannot skip the ping.
4. As the owner, I want the URL and anon key read from `vars.SUPABASE_URL` and `vars.SUPABASE_ANON_KEY`, so that no value is hard-coded and no secret is needed.
5. As the owner, I want the ping to fail visibly when the backend does not answer, so that I notice a paused or down project in the Actions tab.
6. As the owner, I want a manual run of the workflow to ping too, so that I can test the ping on demand.
7. As the owner, I want the ping job to hold no token rights, so that it cannot change the repository.
8. As the owner, I want a repository that has no backend configured to skip the ping cleanly, so that a fork does not show a red run.

## Implementation Decisions

- The change is confined to `.github/workflows/daily-freeze.yml` (`name: Daily Freeze`). The `freeze` job, its triggers, permissions, and concurrency stay as they are.
- New job `keep-alive`: `runs-on: ubuntu-latest`, `permissions: {}`, no `needs`, no checkout, no dependency install.
- One step runs `curl` with a GET request to the REST API root with `limit=1` in the query (`<SUPABASE_URL>/rest/v1/?limit=1`) and the header `apikey: <SUPABASE_ANON_KEY>`. The URL and key enter the step through `env`, never through inline `${{ }}` in the script.
- The `SUPABASE_URL` variable holds no trailing slash (the owner set it that way in #129); the step strips one anyway, as a defence.
- The step captures the HTTP status with curl (`--write-out`) instead of `--fail`, and compares it. The status comes from curl with `-sS -o /dev/null -w '%{http_code}'` and is printed. A status from 100 to 499 passes (a 3xx included). A status of 000 (no answer), 500 or above, an empty or non-numeric status, a curl error, or a timeout fails the step. The step runs with `set -e` semantics so a curl exit code fails it.
- The ping targets no Portdle table, so it does not depend on the migrations. A reply from PostgREST with any status below 500 (including 401 or 404) counts as success. A status of 500 or above also fails the step. The curl call uses `--max-time 30` and no retry.
- Skip rule: when `SUPABASE_URL` or `SUPABASE_ANON_KEY` is empty (a missing `vars` entry reads as empty), the step prints a `::notice::` annotation and exits with success, so a fork without the variables stays green.
- The workflow-level `concurrency` group stays as it is and applies to a whole run, not to a job. The two jobs of one run run in parallel. When runs overlap, one runs and one waits; a newer waiting run replaces an older waiting one, which is harmless at one run per day.
- The freeze job and the keep-alive job run in parallel on the same triggers (`schedule` and `workflow_dispatch`).

## Testing Decisions

- A workflow file has no Vitest seam. The existing convention (the freeze and Pages CI specs) is that the YAML matches the written contract and the underlying commands run locally.
- Checks: the YAML parses; the step script is run locally with `env` set to each case; the `keep-alive` job has no `needs` and no other job lists it in `needs`; the ping command run locally against the real project (URL and key are public repository variables) exits 0; the same script with an unreachable host exits non-zero, and a stubbed 500 reply exits non-zero; the script with empty variables exits 0.
- `pnpm lint`, `pnpm typecheck`, `pnpm test`, and `pnpm build` still pass.
- The workflow only runs on a schedule or by `workflow_dispatch`, so CI cannot exercise it. After merge, a manual `workflow_dispatch` run is the check; both jobs must show the expected result.

## Out of Scope

- Any database table, view, or migration.
- Changes to the `freeze` job or to `ci.yml`.
- Retries, alerts, or notifications when the ping fails.
- Pinging the Auth service.

## Further Notes
- Owner decision (during ticket work): ping the REST root now and pass on any status below 500. This is an API request; the research on the pause rule (#115) says a few API or database requests per day prevent pausing. A follow-up switches the ping to a real read of the All-time leaderboard view once the Leaderboards ticket (#139) migration is applied.

- Author calls, so they can be overruled:
  - The ping counts any status below 500 as success. With the current publishable key, `GET /rest/v1/` itself returns 401, so `curl --fail` would fail every day; a table read returns 404 before the migrations exist. Both prove the API answered. The cost: a wrong key alone does not turn the job red.
  - The job skips with success when the variables are empty. This can hide a missing variable, so the owner setup (#129) must keep both variables set.
  - A paused project answers with a connection failure or a status of 500 or above, so the rule still catches a pause.
  - The ping runs on `workflow_dispatch` too.
- Facts checked on 2026-09-29 against the live project: `GET /rest/v1/` with the publishable key returns 401; a read of a missing table returns 404 with a PostgREST error body.
