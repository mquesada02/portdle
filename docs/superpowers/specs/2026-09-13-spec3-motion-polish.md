# Spec: Motion polish (Spec 3)

Spec for the motion pass after Spec 2. Tracker: https://github.com/mquesada02/portdle/issues/87 (feedback given in conversation: screen changes and popovers feel abrupt).

## Problem Statement

Portdle's motion stops at the board. Tiles pop, the active row shakes on an invalid or duplicate try, the reveal rises, and a fresh Codex card pops, but everything else cuts: tapping a nav item swaps the whole screen in one frame, the Daily switcher and the History switcher swap their content the same way, the miss popover appears and vanishes with no transition, both dialogs and their backdrops snap on and off, a Rounds disclosure dumps its list, a Blitz run starts and ends with a hard cut, and the Codex sort toggle makes seventy-four cards jump. Each cut is small; together they make the app feel less finished than its board.

## Solution

Every abrupt moment gets one short, consistent motion. Screen changes, switcher changes, and Blitz state changes fade the old content out over 100ms and rise the new content in over 150ms, using the browser's View Transitions API, while the shell holds still. The miss popover fades and scales in from its trigger and fades out. Dialogs and their backdrops fade in and out. A Rounds disclosure rises its list in. Codex cards glide to their new positions when the sort changes. Nav items and switcher items transition their colors instead of flipping. Browsers without the View Transitions API keep today's instant screen changes, and the reduced-motion rule turns all of it off.

## User Stories

### Screen changes

1. As a player, I want the content to fade out and the next screen to fade in and lift slightly when I tap a nav item, so that moving around feels smooth instead of jarring.
2. As a player, I want the top bar and the tab bar to hold still during a screen change, so that only the content moves and the nav stays where my thumb is.
3. As a player, I want a screen change to finish within a fraction of a second, so that motion never slows me down.
4. As a player, I want tapping the wordmark to move with the same motion as a nav tap to the same place, so that every route change feels the same.
5. As a player on a browser without the View Transitions API, I want screen changes to work exactly as today, so that an older browser loses only the polish.

### Switcher changes

6. As a Daily player, I want everything below the Daily switcher, from the target's name down to the reveal, to change with motion when I pick Mixed, Protocols, or Applications, so that the switcher stays put and the category swap reads as a content change.
7. As a History reader, I want only the list below the History switcher to change with motion when I pick Daily or Blitz, so that the heading and the switcher I just tapped do not move under my finger.

### Miss popover

8. As a Daily player, I want the miss popover to fade and scale in from its trigger when it opens, so that it reads as attached to the miss I tapped.
9. As a Codex reader, I want a card's popover to open with the same motion, so that the popover feels the same on every surface.
10. As a player, I want the popover to fade out whenever it closes, whether by Escape, an outside click, a second click, moving the pointer away, or moving focus away, so that it does not vanish in one frame.
11. As a player, I want the popover's close to feel immediate even though it fades, so that Escape never feels laggy.
12. As a keyboard player, I want the popover's open and close motion to change nothing about focus, pinning, hover, or Escape, so that the existing behavior is untouched.

### Dialogs

13. As a player, I want the How-to dialog and its backdrop to fade in when they open, so that the dialog arrives instead of snapping on.
14. As a player, I want the setup dialog to open and close with the same motion as the How-to dialog, so that both dialogs feel alike.
15. As a player, I want a dialog and its backdrop to fade out on Escape, backdrop click, Cancel, or Start, so that dismissal is as soft as arrival.
16. As a player, I want a dialog's close motion to be shorter than its open motion, so that leaving feels quicker than arriving.

### Round log disclosures

17. As a player, I want the round log to rise in when I open a Rounds disclosure on the arena or a row of History's Blitz segment, so that the list arrives instead of appearing at once.
18. As a player, I want closing a Rounds disclosure to be instant, so that collapsing stays snappy.

### Blitz

19. As a Blitz player, I want the arena to give way to the run with the same motion as a screen change when I press Start, so that a run beginning feels like arriving somewhere.
20. As a Blitz player, I want the run to give way to the end card with the same motion when the run ends, so that the end lands softly.
21. As a Blitz player, I want Play again to bring the arena back with the same motion, so that the loop feels consistent.
22. As a Blitz player, I want the HUD countdown and the round log to keep updating without motion during a run, so that fast play is never delayed by animation.

### Codex

23. As a Codex reader, I want cards to glide to their new positions when I switch the sort between Name and Port, so that I can follow where an entry went.
24. As a Codex reader, I want a fresh card's pop to keep working as it does today, so that new finds still feel rewarding.
25. As a Codex reader on a browser without the View Transitions API, I want the sort to reorder instantly as today, so that the toggle always works.

### Nav and switchers

26. As a player, I want a nav item's color to transition when it becomes current, so that the active state slides into place instead of flipping.
27. As a player, I want a switcher item's color to transition when it becomes current, so that the Daily switcher and the History switcher match the nav.

### Accessibility

28. As a player who has asked my system to reduce motion, I want none of these transitions to play, so that the app respects my setting as it already does for the board.
29. As a screen reader user, I want none of these transitions to change what is announced or when, so that motion stays purely visual.

### Maintainer

30. As a maintainer, I want one shared helper that starts a view transition when the browser supports it and just applies the change when it does not, so that the Blitz state changes and the Codex sort reorder do not each reimplement the fallback.
31. As a maintainer, I want every duration and easing this spec writes in one place in the stylesheet, and the color transition reused from the pills rather than written again, so that the motion language stays consistent.
32. As a maintainer, I want the seam tests to keep passing with no new fake-timer use, so that motion stays outside the test contract as the redesign decided.
33. As a maintainer, I want the view-transition stylesheet rules to pass lint without weakening the linter for the rest of the stylesheet, so that the linter keeps its value.

## Implementation Decisions

### Technique

- Screen changes, switcher changes, Blitz state changes, and the Codex sort reorder all use the same-document View Transitions API. Route changes go through the router's built-in view-transition option, which passes a list of transition types per navigation. State changes outside the router go through one shared helper in the UI layer that takes a list of types and an update function: when the document has `startViewTransition` and the reduced-motion media query does not match, it calls that method, in its object form with the update callback and the types when the browser supports the `:active-view-transition-type()` selector and in its callback form otherwise, the same two-step gate the router uses; the callback commits React synchronously with React's `flushSync`. Without the API, or under reduced motion, it runs the update directly; the reduced-motion check comes first, before either form, which is stricter than the router in the untyped band and harmless there, since the CSS gate covers that band. The helper is the only place that calls the API outside the router. A view transition changes nothing about what the DOM contains or when: the update commits at the same moment it does today, so every live region keeps its timing: the message lines, the setup dialog's empty-pool notice, the progress notices of the shell and of the Daily, Blitz, and Codex screens, and the Search panel's "No matches." line, some of which sit inside animated regions.
- The stylesheet keys every animation on transition types, never on route paths. The types are: `screen` (a different nav screen), `switcher` (a Daily category or History segment change under a switcher), `phase` (a Blitz state change), and `reorder` (a Codex sort change).
- The router's types function returns a list holding `screen` when the nav screen changes (Daily, Blitz, History, Codex, looked up in the nav's own fixed table of screens and their match paths, which becomes a shared export that the shell and the router both import rather than a copy, where the three Daily addresses are one screen and both History addresses are one screen) and a list holding `switcher` when the pathname changes within one screen. Tapping the Daily nav item from Protocols, or the History item from the Blitz segment, changes the pathname within one screen and so plays the switcher motion, not the screen motion. The wordmark link, which sits outside the nav, resolves through the same function like any route change. It reads the reduced-motion media query itself, the way the reveal's scroll already does, and returns the boolean `false` when it matches, which is the only value the router treats as "no transition" (an empty list would still start one), so the JS gate and the CSS gate agree.
- Named regions and cards: the shell's content wrapper (the element holding the shell's progress notice and the routed screen) is named `screen`; on the Daily screen and the History screen, the element holding everything below the switcher is named `switcher-content`. Codex cards are each named after their entry (`codex-{id}`) on the card's outermost element, the grid's list item, so the browser can track the whole card, popover trigger included, across a reorder. A no-animation rule on a name zeroes the animation of that name's group, old, and new pseudo-elements, since the browser's default crossfade runs on the old and new snapshots and its default position and size tween on the group, and resets the two snapshots' blend mode to normal, the one reset the prototype's root rule already carried, since the browser blends them additively for the crossfade and two static snapshots at full opacity would brighten. Every snapshot that animates keeps the browser's additive blend, as the prototype's did, since it is what keeps an overlapping fade-out and fade-in from dipping in brightness: `screen` under the `screen` and `phase` types, `switcher-content` under the `switcher` type, and the Codex cards under the `reorder` type; only the zeroed ones are reset.

### Screen changes

- Under the `screen` type, the old `screen` snapshot fades out over 100ms and the new one rises in over 150ms: opacity from 0 to 1 and an 8px lift, the reveal's existing rise keyframe with no delay. The root carries an explicit no-animation rule, not type-keyed, so the top bar and the tab bar hold still rather than crossfading with the browser's default; the `switcher-content` region and the Codex cards carry a no-animation rule under the `screen` type, so a screen entering or leaving them does not crossfade them separately. The prototype settled this feel over a crossfade and a directional slide.

### Switcher changes

- Under the `switcher` type, only the `switcher-content` snapshots animate, the old fading out and the new rising in as on a screen change; `screen` carries an explicit no-animation rule under this type, and the root its untyped no-animation rule from the screen-change decision, so both hold still instead of taking the browser's default crossfade, and the switcher stays put while its active item changes color through the color transition below. On the Daily screen the region is everything below the switcher: the target caption and heading, the Daily screen's own progress notice, the try counter, the board, the tracker strip, the message line, the Submit button, and the reveal, since the target changes with the category; those are siblings today, so the Daily screen gains one wrapping element around them to carry the name. Switching to a category whose Daily is already finished plays the region's rise and then the reveal's own delayed rise, which already plays on every mount of a finished Daily; nothing suppresses the second. On History the region is the list below the switcher, already a single element in both segments, its empty state included, so History gains no wrapper; the `h1` sits above the switcher and stays put.

### Blitz state changes

- The Blitz screen's transitions from arena to run (Start), from run to ended (lives or timeout), and from ended to arena (Play again) run through the helper with the `phase` type, and animate the `screen` snapshots as on a screen change, the old fading out and the new rising in; the root keeps its untyped no-animation rule from the screen-change decision, so the shell holds still. Opening and closing the setup dialog is not a phase change and uses the dialog motion below. Round commits, HUD ticks, and round-log updates during a run never start a view transition, with one exception: the guess that spends the last life ends the run, and that single update takes the phase path so the end card rises in; a timeout end takes the same path from the timer.

### Codex sort reorder

- Changing the sort runs the state update through the helper with the `reorder` type. Each card's group moves from its old position to its new one with the browser's default group tween shortened to 200ms, and its snapshots' default crossfade is shortened to match; `screen` carries an explicit no-animation rule under this type, and the root its untyped no-animation rule from the screen-change decision, so the rest of the Codex screen holds still. A card whose position does not change gets no motion. Spec 2's grouping decision sorts every card by name or by port and keeps unseen cards in their sorted slot, which is what its accepted port-order leak presupposes; the grouping that shipped with Spec 2 instead read "keep their position" as the catalog index, pinned unseen cards there, and sorted only seen cards among the remaining slots, under which only seen cards would have glided. The user ruled that Spec 2 means the full sort, unseen cards included; ticket #85, merged before this spec's tickets, implemented it, so every card whose slot changes glides. Story 48 and the acceptance of the leak stand under either reading. The fresh-card pop is unchanged and plays only on mount.

### Miss popover

- Open: the panel fades from 0 to 1 and scales from 95% to 100% over 120ms, animating the standalone `scale` property, which composes independently with the standalone `translate` property that the inline placement's centering below the small breakpoint already uses, with its transform origin at the top edge on the side the panel is anchored to: for the inline placement, top center below the small breakpoint and top right at and above it, matching its existing positioning; for the grid placement, top left, or top right in the last column.
- Close: the panel fades out over 80ms, opacity only, its scale held at 100%, then leaves the DOM. Both the open and the close are keyframe animations, not transitions; the component listens for the animation-end event only while closing, since the open needs no follow-up. The component keeps a closing state: when its derived open value turns false, the panel stays rendered with the exit animation until the animation-end event arrives, or after 80ms if it never does, whichever comes first, and then unmounts. Reopening during the exit cancels it: the closing state clears, its fallback timer and animation-end listener are torn down, the panel returns to its fully open static state at once, and the enter animation does not replay. A further close cause while the panel is already closing changes nothing. A close that lands while the open animation is still playing cuts it short: the exit keyframe replaces it and starts from full opacity with the scale snapping to 100%, a jump too brief to matter since the open lasts only 120ms. Pin, hover, focus, Escape, and outside-click behavior are unchanged; the closing panel accepts no pointer events and is inert, so nothing inside it can take focus during the exit. When the reduced-motion media query matches, read the way the reveal's scroll already reads it, the close skips the closing state and unmounts at once, as today, since the universal reduced-motion rule zeroes the exit keyframe and its end event would never arrive.

### Dialogs

- Both dialogs share one stylesheet rule set: on open the panel fades from 0 to 1 and scales from 95% to 100% over 150ms and the backdrop fades from 0 to 1 over 150ms, through the browser's starting-style rule; on close both fade out over 100ms through discrete transitions of the dialog's display and overlay. No JavaScript changes; the existing open and close calls stay as they are. Browsers without starting-style or discrete transitions get today's instant behavior.

### Round log disclosures

- The round log inside an open Rounds disclosure, on the arena's last run card and on each row of History's Blitz segment, plays the reveal's rise keyframe over 150ms with no delay when the disclosure opens. Closing is instant. Pure CSS on the disclosure's open state; no JavaScript. The end card has no disclosure: its round log is always visible and arrives with the end card's own phase transition.

### Nav and switcher colors

- Nav items and switcher items, on the Daily switcher and the History switcher, gain a 150ms color transition through the same utility class the pill radios already carry, so its duration and curve come from Tailwind's defaults rather than from the stylesheet. The sort toggle on the Codex, which borrows the switcher's look, gets the same. The theme toggle stays instant: its icon swap and the page's change of color scheme get no transition.

### Durations and easing

- Enter motions last 150ms, exits 100ms, the popover 120ms in and 80ms out, the reorder 200ms, the color transitions 150ms. Every keyframe this spec adds, the dialog transitions, the popover's open and close, and the screen, switcher, and phase view-transition animations use ease-out; the existing keyframes keep their curves, so the disclosure's rise inherits the rise keyframe's ease-out; the reorder keeps the browser's default easing for the cards' group tween and their crossfade alike, the `ease` keyword; the color transitions keep the timing curve the pill radios already use, Tailwind's default `cubic-bezier(0.4, 0, 0.2, 1)`. A view transition lasts as long as its longest animation, and the browser's default group tween and crossfade each run 250ms, so no default is left running on any named group under any type: under the `screen`, `switcher`, and `phase` types the animated group's own position and size tween is zeroed and only its snapshots' keyframes play, so the transition ends with the 150ms rise; under the `reorder` type the cards' group tween and their snapshots' crossfade are both shortened to 200ms, so the transition ends with the glide. The prototype left the defaults in. In one place, per type: the root carries the no-animation rule under every type through its untyped rule; under `screen` and `phase`, `screen`'s group is zeroed and its snapshots carry the fade-out and rise-in, and under `screen` alone `switcher-content` and the Codex cards carry the no-animation rule, since neither is present on the Blitz screen where `phase` plays; under `switcher`, `screen` carries the no-animation rule and `switcher-content`'s group is zeroed with its snapshots carrying the fade-out and rise-in; under `reorder`, `screen` carries the no-animation rule and each card's group tween and crossfade are shortened to 200ms. The keyframes and the transition rules this spec writes live in the global stylesheet next to the existing pop, shake, draw, and rise keyframes; the color transition is the one motion written nowhere, reused through the pills' utility class.

### Reduced motion and fallbacks

- The existing reduced-motion rule keeps zeroing animations and transitions, because every motion rule the stylesheet writes lives in the `components` cascade layer while the universal rule itself stays unlayered: an unlayered normal-importance rule always beats a layered one regardless of specificity. It gains the view-transition pseudo-elements, zeroing their animations and resetting the snapshots' blend mode to normal, and the router types function and the helper both skip view transitions when the media query matches, so wherever the types function runs nothing starts a transition that the CSS would then have to cancel; the untyped band below relies on the CSS alone. The popover, dialogs, disclosures, and colors are plain CSS in every band, zeroed by the same rule, the popover's reduced-motion close included.
- Browsers without the View Transitions API: screen, switcher, and Blitz state changes are instant, the Codex reorder jumps, and everything else (popover, dialogs, disclosures, colors) still animates, since those are plain CSS; reduced motion still zeroes them through the same universal rule, and the popover's close, the one plain-CSS motion whose unmount waits on an animation, unmounts at once under reduced motion, as the Miss popover decision says.
- Browsers with the API but without transition types (the router checks for the `:active-view-transition-type()` selector before passing types, and falls back to an untyped transition): the type-keyed rules never match, the root stays still because its rule is not type-keyed, and every named region present, `screen`, `switcher-content`, and the Codex cards alike, gets the browser's default crossfade. That is accepted; nothing detects this band, and it is not checked separately: reduced motion there rests on the same universal pseudo-element rule the other two bands exercise by eye. The helper mirrors the router's API-and-selector gate, so its transitions behave the same way in this band, except that its reduced-motion check runs before either form. In this band the router never consults the types function, so its reduced-motion check never runs; the CSS gate alone covers it, since the reduced-motion rule zeroes the view-transition pseudo-elements whatever the type, and the transition starts and finishes with nothing visible. The popover, dialogs, disclosures, and colors do not depend on the API and behave in this band as in the band without it, the popover's reduced-motion close included.

### Stylesheet and lint

- Every motion rule this spec's tickets write goes into the `components` cascade layer, and the universal reduced-motion rule stays unlayered so it always wins against it regardless of specificity. The linter's unknown-type-selector rule misreads the name inside a named view-transition pseudo-element as an element type. Only the rules that name `screen` trigger it; hyphenated names such as `switcher-content` and `codex-{id}` pass, and so do `root`, the universal `*`, and the type selector. The linter suppresses per line: an ignore comment covers only the line that follows it, and the formatter puts each selector of a selector list on its own line, so a list naming `screen` twice needs an ignore above each. Every selector that names `screen` therefore sits on its own line directly under its own targeted ignore comment, whether it is a rule of its own, a member of a selector list, or a nested rule, and the stylesheet carries exactly one ignore per such selector line. Under the `screen` and `phase` types the `screen` group is zeroed and its old and new snapshots carry the keyframes; under the `switcher` and `reorder` types all three are zeroed: twelve selector lines when each type has its own rules, nine when the `screen` and `phase` types share theirs through a type list on a parent rule; the shared layout is the default, the separate one is fine. Nothing else in the stylesheet loses linting or formatting and no ignore goes unused.

### Copy

- No new strings.

## Testing Decisions

A good test exercises a public seam with literal inputs and asserts what a player sees or what a pure function returns. How motion looks, and what it blocks while it plays (timing, keyframes, the view-transition pseudo-elements, pointer events and focus during the popover's exit), is checked by eye in the browser, not by tests, as the redesign decided; whether, and with which type, the router and the helper ask for a view transition is tested through a fake of the API. This spec touches one seam.

1. **App seam** (render the app with a memory store, memory history, injected day; prior art: the app, Blitz, miss popover, and Codex test files).
   - Every existing test keeps passing; the only edits to existing tests are the ones the Miss popover bullet below names. The test runner has no View Transitions API, so the router and the helper take their fallback paths in every test except the helper and router tests below, which install a fake for their own duration. The shared media-query stub in the test helpers, which today answers only the dark-scheme query, gains a reduced-motion switch, used wherever the Miss popover, Helper, and Router bullets below stub reduced motion.
   - Miss popover: after any close (the pointer leaving and the grace timer elapsing, a second click, focus leaving, Escape on the inline and on the grid placement, an outside click), the panel, which the Codex test finds by its note role and the miss popover tests by its text, is removed from the document; the existing tests that assert this synchronously are edited to wait for the removal, or to advance the clock where they already run on fake timers: six in the miss popover test file and the seen-card test in the Codex test file. A new test in the miss popover test file covers reopening while closing: the panel stays shown; another, with the reduced-motion media query stubbed to match, covers Escape removing the panel synchronously.
   - Helper (the arena start, Play again, and setup dialog cases in the Blitz arena test file; the last-life, timeout, and mid-run-commit cases in the Blitz test file, next to the flows that already end a run; the sort case in the Codex test file): with a fake `startViewTransition` installed on the document that accepts the object form, records its types, and runs the update callback at once, and a fake selector-support check that reports support, starting a run from the arena, spending the last life, letting the clock run out (driven with the fake timers the Blitz tests already use for the countdown), and pressing Play again each start one transition with the `phase` type, a round commit that leaves lives starts none, opening and closing the setup dialog start none, and changing the Codex sort starts one with the `reorder` type; with the reduced-motion media query stubbed to match, the same actions start none. The fake is removed after each test.
   - Router (in the app test file): navigating by nav link and by switcher still lands on the right screen, Daily category, or History segment with no API present; with a fake `startViewTransition` and a fake selector-support check installed, the way the router expects them, a nav tap from Daily to Blitz records the `screen` type, a Daily switcher tap and a History switcher tap each record `switcher`, a nav tap to Daily from Protocols records `switcher` (the History-from-Blitz-segment case goes through the same lookup and is not tested separately), a wordmark tap from Blitz records `screen`, and with the reduced-motion media query stubbed to match none is recorded.

Everything else is checked by eye on the dev server at phone and desktop widths, in a browser with the View Transitions API and in one without: each of the seven moments (screen change, switcher change, popover, dialogs, Rounds disclosures, Blitz state changes, Codex reorder) plays as decided, the nav items, switcher items, and sort toggle transition their colors, the closing popover ignores pointer events and focus and its 80ms exit reads as immediate, the switchers and the Codex headline hold still while their content moves, a switch to a finished category shows the region's rise followed by the reveal's own rise, every live region keeps its timing, the shell holds still, and nothing plays under reduced motion. No snapshot or visual regression tests. Story 33 is checked in code review against the Stylesheet and lint decision, with the existing lint step in CI catching a missing ignore; an unused per-line ignore is only a warning there and an unused file-wide ignore is not reported at all, so CI alone does not enforce it; story 31 is a code-organization property, checked in code review; story 32 holds because the only fake timers used are the ones the Blitz and miss popover suites already run on; story 30 holds because the helper in the Technique decision is the only caller of the API outside the router and the Helper bullet exercises it for both the Blitz phases and the Codex reorder.

## Out of Scope

- A crossfade or a directional slide for screen changes; the prototype settled on fade-and-rise.
- Animating the height of a Rounds disclosure.
- A theme-toggle crossfade or any transition on the change of color scheme.
- A polyfill for browsers without the View Transitions API.
- Any motion library or spring physics.
- Changes to the existing keyframes: the board's tile pop and row shake, the reveal's divider draw and delayed rise, and the fresh-card pop stay as they are. The board and the reveal still move as part of the `switcher-content` region on a category change.
