# Spec: Scheduled daily freeze workflow

Spec for #52. Tracker: https://github.com/mquesada02/portdle/issues/52

## Problem Statement

Every schedule cycle's tail eventually runs out of days, and `pnpm gen:schedule --check` (the guard already in `ci.yml`) then fails on the very first CI run after the UTC day rolls past the last day the committed schedules cover, because nobody has run `pnpm gen:schedule` to freeze the next prefix and commit the result. PR #46 shows this happening in practice: a maintainer had to notice CI failing on `master`, run the generator by hand, and open a single-commit PR (`chore(schedule): freeze Daily identities through 2026-09-11`, PR #46) just to unblock the pipeline. That manual step is easy to forget, and until someone does it, `master` is red and the public site cannot deploy a new build.

## Solution

A new scheduled GitHub Actions workflow runs `pnpm gen:schedule` shortly after every UTC midnight (and on manual dispatch), and — only when that run actually changed a committed schedule file — commits the result as a bot, pushes straight to `master`, and explicitly dispatches the existing `ci.yml` workflow so it builds and deploys the newly frozen schedule; when nothing changed, the workflow does nothing and exits cleanly. The existing `pnpm gen:schedule --check` step in `ci.yml` is untouched and keeps acting as the safety net that would fail a pull request or push if the frozen prefix were ever wrong. One short paragraph is added to the v1 design spec's §6.2 (where the generator's freeze/tail/coverage semantics already live) explaining that this freeze now runs automatically and how to trigger it by hand.

**Platform constraint (human decision):** a push authenticated with a workflow run's own default `GITHUB_TOKEN` never fires another workflow's `on: push` trigger — GitHub Actions suppresses that to prevent recursive runs; only `workflow_dispatch` and `repository_dispatch` events are exempt. So a bot push to `master` using the default token, on its own, would **not** cause `ci.yml` to build or deploy. This was raised as a GRILLING question during spec review and resolved by the human: add a single `workflow_dispatch:` trigger to `ci.yml`'s `on:` block, and have the freeze workflow dispatch that run via the GitHub API immediately after a successful commit and push. See Implementation Decisions and Further Notes for the full mechanism and one necessarily-linked consequence for `ci.yml`'s `deploy` job.

## User Stories

### Maintainer

1. As a maintainer, I want a workflow that runs `pnpm gen:schedule` daily shortly after 00:00 UTC, so that the frozen prefix is extended before CI on `master` can go red from a stale schedule.
2. As a maintainer, I want that same workflow runnable on demand (`workflow_dispatch`), so that I can freeze the schedule immediately instead of waiting for the next scheduled run.
3. As a maintainer, I want the workflow to check out `master`, install dependencies with pnpm the same way `ci.yml` does, and then run `pnpm gen:schedule`, so that the freeze uses the same toolchain and lockfile CI already trusts.
4. As a maintainer, I want the workflow to commit and push only when `pnpm gen:schedule` actually changed a file, so that a no-op day does not create an empty or noisy commit.
5. As a maintainer, I want the commit to use a conventional message in the form `chore(schedule): freeze Daily identities through <UTC date>`, so that the automated commits read exactly the same way as the manual commit the PR #46 maintainer actually typed, matching the issue's own example verbatim.
6. As a maintainer, I want the commit authored by a bot identity (`github-actions[bot]`), not a personal account, so that it's clear at a glance the commit was automated.
7. As a maintainer, I want the workflow's push to `master` to use the default token and not itself be re-triggered by that push, so that there is no infinite loop of workflow runs.
8. As a maintainer, I want the freeze workflow to explicitly dispatch `ci.yml` immediately after a successful commit and push (and only then), so that the public site picks up the newly frozen schedule without a separate manual deploy step, despite the bot push not auto-triggering `ci.yml` on its own.
9. As a maintainer, I want that dispatched `ci.yml` run to still deploy (not just build), so that dispatching accomplishes the same outcome a normal push would have.
10. As a maintainer, I want the workflow to request only the permissions it actually needs — `contents: write` to push the commit and `actions: write` to dispatch `ci.yml` — so that it has the minimum access for what it does and nothing more.
11. As a maintainer, I want the workflow to use the default `GITHUB_TOKEN` for both the push and the dispatch call, so that no additional secret, PAT, or deploy key has to be provisioned or rotated.
12. As a maintainer, I want `pnpm gen:schedule --check` to remain exactly where it already is in `ci.yml`, so that a pull request or a `master` push with an unfrozen or invalid schedule still fails CI the same way it does today.
13. As a maintainer, I want `ci.yml` changed only by the two minimal, necessarily-linked lines the chosen dispatch mechanism requires (the `workflow_dispatch:` trigger and widening the `deploy` job's event-name check to also allow a dispatched run), so that the automation's one required exception to "don't touch `ci.yml`" is as small as it can be and does not alter `ci.yml`'s behavior for its existing `push`/`pull_request` triggers.
14. As a maintainer, I want one short paragraph documenting the automated freeze added to the v1 design spec's §6.2 (next to the existing `pnpm gen:schedule` semantics), so that the automation is discoverable from the same place the generator's rules are already explained.
15. As a maintainer, I want that paragraph to say how to run the freeze manually, so that I don't have to read the workflow YAML to remember the on-demand trigger exists.
16. As a maintainer, I want this ticket to leave `src/`, `package.json`, and `scripts/gen-schedule.ts` untouched, and `ci.yml` untouched beyond the two lines in decision 13, so that the automation is additive and does not risk the existing CI/build/deploy pipeline or application code owned by other in-flight work.

## Implementation Decisions

- **New file**: `.github/workflows/daily-freeze.yml`, a workflow separate from `ci.yml`. Top-level `name: Daily Freeze` (matching `ci.yml`'s own `name: CI`, so the run shows a readable name in the Actions UI instead of falling back to the file name).
- **Triggers**: `schedule` with cron `5 0 * * *` (~00:05 UTC daily) and `workflow_dispatch` (no inputs).
- **Permissions**: job-level `contents: write` (to commit and push) and `actions: write` (to dispatch `ci.yml`) — no `pages`, no `id-token`; this workflow never builds or deploys the site itself, it only asks `ci.yml` to.
- **Concurrency**: `concurrency: { group: daily-freeze, cancel-in-progress: false }` at the workflow level, so an overlapping cron run and an ad-hoc `workflow_dispatch` (or two manual dispatches) queue instead of racing two `git push`es against `master`; a queued run simply re-reads `git status --porcelain` after the first finishes, so this is safe and self-healing rather than a source of missed freezes.
- **Job**: single job, `runs-on: ubuntu-latest` (matching both jobs in `ci.yml`), steps in order:
  1. `actions/checkout@v4` with `ref: master` explicit. `schedule` always runs against the default branch, and both `gh workflow run` (when `--ref` is omitted) and a manual dispatch also default to the repository's default branch — but the GitHub UI's "Run workflow" dropdown, and an explicit `--ref`/`-r` on `gh workflow run` or the REST API, let an operator pick *any* branch or tag. Pinning `ref: master` here removes that ambiguity so a dispatch aimed at some other ref can never check out, and then push the bot commit to, the wrong branch.
  2. `pnpm/action-setup@v4` — no pinned version, same as `ci.yml`, relying on the `packageManager` field in `package.json`.
  3. `actions/setup-node@v4` with `node-version: "22"` and `cache: pnpm` — identical to both jobs in `ci.yml`.
  4. `pnpm install --frozen-lockfile` — identical to `ci.yml`.
  5. `pnpm gen:schedule` (no `--check` — this is the writing run that may rewrite `src/catalogs/schedules/*.json`).
  6. A change-detection + commit step: check `git status --porcelain`; if empty, record "no change" (e.g. a step output) and do nothing further; if non-empty, set the git author/committer to the bot identity (`github-actions[bot]` / `41898282+github-actions[bot]@users.noreply.github.com`), `git add -A`, commit with message `chore(schedule): freeze Daily identities through <UTC date>` (see decision 5 above) where `<UTC date>` is that run's UTC-today date (`date -u +%F`, the same `YYYY-MM-DD` format `src/engine/utc.ts`'s `utcDateString` produces), `git push`, and record "changed" via that same step output.
  7. A dispatch step, run **only** when step 6 recorded "changed": call the GitHub API to fire `ci.yml`'s `workflow_dispatch` event on `master` (e.g. `gh workflow run ci.yml --ref master`), authenticated with the job's own default `GITHUB_TOKEN` explicitly wired into that step's environment (`env: GH_TOKEN: ${{ github.token }}`) — the `gh` CLI does not pick up the runner's ambient token automatically, it reads it from the `GH_TOKEN`/`GITHUB_TOKEN` environment variable. Skipped entirely on a no-op day — nothing to build or deploy.
- **Token and loop safety**: the default `GITHUB_TOKEN` is used throughout, no new secret. GitHub Actions never re-triggers a workflow from an event caused by that workflow run's own `GITHUB_TOKEN` — this applies to the bot's `git push` (so it can't cause a `push`-triggered run) and is precisely why step 7 is needed as an explicit dispatch rather than relying on the push to trigger `ci.yml` on its own. `workflow_dispatch`/`repository_dispatch` calls are the documented exception to that suppression, so the `gh workflow run` call in step 7 *does* successfully start a `ci.yml` run even though it's made with the same token. This workflow itself only listens for `schedule` and `workflow_dispatch`, so nothing it does — the push or the dispatch call — can trigger another run of itself; there is no loop.
- **Necessary, minimal exception to "don't touch `ci.yml`" (item 1 below is human-approved — see Further Notes; item 2 is an implementer judgment call flagged for review below):**
  1. Add `workflow_dispatch:` to `ci.yml`'s `on:` block, alongside its existing `push`/`pull_request` triggers. No other change to the `on:` block, and no change to the `build` job (it has no `if` guard, so it already runs the same way regardless of which trigger started it).
  2. Widen the `deploy` job's existing condition from `if: github.ref == 'refs/heads/master' && github.event_name == 'push'` to also accept a dispatched run: `if: github.ref == 'refs/heads/master' && (github.event_name == 'push' || github.event_name == 'workflow_dispatch')`. This is a logically required consequence of dispatching for deploy, not an independent decision: without it, `deploy`'s existing event-name check would skip a dispatched run, silently defeating the whole mechanism (`ci.yml` would build but never deploy the freeze). No other change to `deploy` — it still runs only after `build` succeeds, still only on `master`, still requests only its existing `contents: read`/`pages: write`/`id-token: write` permissions.
  These two lines were not spelled out verbatim in the human's GRILLING answer (which named "add a single `workflow_dispatch:` trigger... no other change to ci.yml"); line 2 is called out explicitly here, flagged for review, because it is the minimum necessary for line 1 to actually achieve the human-approved outcome ("dispatch that CI run... immediately after a successful commit and push").
- **Documentation**: one short paragraph appended to §6.2 of `docs/superpowers/specs/2026-09-08-portdle-design.md` (the section that already documents `pnpm gen:schedule`'s freeze/tail/coverage rules), stating that the freeze runs automatically once a day via `.github/workflows/daily-freeze.yml`, that a successful freeze dispatches `ci.yml` so the site redeploys, and that it can also be run on demand from the Actions tab (`workflow_dispatch`) or locally with `pnpm gen:schedule`. This is the "whichever the maintainer conventions prefer" location from the ticket, chosen because it sits with the generator semantics it describes rather than a new standalone doc file.
- **Scope boundary**: this ticket touches `.github/workflows/daily-freeze.yml` (new), the one paragraph in the v1 design spec, and exactly the two lines of `ci.yml` in the bullet above. It does not touch `src/`, `package.json`, or `scripts/gen-schedule.ts`, and touches nothing else in `ci.yml`.

## Testing Decisions

A workflow YAML file is not application code and has no Vitest seam; the existing project convention (see the Pages CI spec) is that CI/workflow contracts are proven by the YAML matching the written contract plus a local run of the underlying commands, not by a test suite or a GitHub Actions mock.

- **Seam 1 — the workflow YAML itself**: reviewed against this spec's Implementation Decisions (triggers, permissions, step order, commit message format, bot identity, no `--check` flag on the writing run, the conditional dispatch step) and against `ci.yml`'s existing conventions for checkout/pnpm/node/install, plus the two `ci.yml` lines described above reviewed against the same conditions.
- **Seam 2 — local dry run**: run `pnpm gen:schedule` followed by `git status --porcelain` on a clean tree to confirm the change-detection logic the workflow's commit step depends on behaves as expected (empty output when nothing changed; changed paths listed when it did). This dry run is not committed.
- No new automated tests are added or expected for this ticket. `pnpm lint`, `pnpm gen:schedule --check` (on a clean tree), and a post-push `gh workflow list` check that GitHub parsed both workflow files are the verification steps, not a test suite.

## Out of Scope

- Any change to `src/`, `package.json`, or `scripts/gen-schedule.ts`.
- Any change to `ci.yml` beyond the two lines described in Implementation Decisions (the `workflow_dispatch:` trigger and the `deploy` job's widened event-name check). In particular: no change to `ci.yml`'s existing `push`/`pull_request` triggers, its `build` job's steps or order, or `deploy`'s permissions, `needs`, or ref check.
- Any change to how the existing `pnpm gen:schedule --check` CI guard works.
- Provisioning a PAT or deploy key — the default `GITHUB_TOKEN` is sufficient for both the push and the dispatch call.
- Failure notifications, retry logic, or backfilling missed scheduled runs.
- A standalone new doc file under `docs/` — the documentation lands as a paragraph in the existing v1 design spec instead.
- Updating the v1 design spec's §10 ("Tooling and hosting"), which lists `deploy GitHub Pages` as a CI step without stating a trigger mechanism — silent on, and so readable as implying, push-only. That line remains true (a normal `master` push still deploys) but doesn't mention that a dispatched run can also deploy after this ticket; this ticket deliberately confines its documentation to the one §6.2 paragraph rather than touching §10.

## Further Notes

- Primary source: GitHub issue #52 ("Scheduled daily freeze workflow"), whose acceptance criteria this spec restates as decisions.
- Precedent: PR #46's actual, originating commit (`chore(schedule): freeze Daily identities through 2026-09-11`, per `gh api repos/mquesada02/portdle/pulls/46/commits` — distinct from the unscoped `chore: freeze Daily identities through 2026-09-11 (#46)` squash-merge title that landed on `master`, which took the PR's title rather than its commit message) is the manual version of exactly what this workflow automates. Since the freeze workflow pushes a single raw commit directly to `master` with no PR or squash step, its true structural analog is that original, scoped commit — same commit message shape, same single file family (`src/catalogs/schedules/*.json`, in practice usually just `identity.json`) affected.
- **Human decision (GRILLING, during spec review):** the ticket's original assumption — "the push is a normal master push, so the existing CI runs once and deploys" — does not hold under GitHub Actions' documented restriction that a push made with a workflow run's own `GITHUB_TOKEN` never fires another workflow's `on: push` trigger (only `workflow_dispatch`/`repository_dispatch` are exempt). Raised as a GRILLING question with three options (dispatch `ci.yml` via a one-line `workflow_dispatch:` addition; duplicate build+deploy inside the freeze workflow; or accept no automatic deploy). The human chose the first: add `workflow_dispatch:` to `ci.yml`'s `on:` block and have the freeze workflow dispatch that run via the GitHub API right after a successful commit and push, using the default `GITHUB_TOKEN`. This keeps deploy logic in exactly one place (`ci.yml`) instead of duplicating it.
