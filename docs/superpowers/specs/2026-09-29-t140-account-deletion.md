# Ticket spec: Account deletion (Spec 4, ticket #140)

Parent: Spec 4 (#127, `docs/superpowers/specs/2026-09-28-spec4-backend.md`). Map: #114. Ticket: #140. Blocked by #131 and #136, both merged.

## Problem Statement

A signed-in player has no way to leave. Their Codex, Bests, runs, and Dailies (and their preferences, once those sync) stay on the backend, and their display name stays on the Leaderboards, for as long as the project exists. Their device also keeps the local copy with no way to start clean.

## Solution

The Account menu of a signed-in player gains a Delete account action. It opens a confirm dialog that says what goes: the account, its synced data, and its Leaderboard rows, and that this device is cleared. On confirm, the backend removes the Account and everything tied to it. Only after that succeeds does the app drop the stored sign-in, clear every Portdle key on the device, remount, and open a signed-out Daily, as on a first visit (system theme, How-to opens). A failed delete shows a one-line error and changes nothing. Any other device still signed in to the deleted account signs itself out on its next sync and keeps its local data.

## User Stories

1. As a signed-in player, I want a Delete account action in the Account menu, so that I can leave and take my data with me.
2. As a signed-in player, I want Delete account to ask me to confirm in a dialog, so that I cannot delete by accident.
3. As a signed-in player reading the confirm dialog, I want it to say that the account, its synced data, and its Leaderboard rows are removed and that this device is cleared, so that I know the full effect before I confirm.
4. As a signed-in player, I want to cancel the dialog with a Cancel button, the Escape key, or a click on the backdrop, so that backing out is easy.
5. As a player who deletes the account, I want everything of mine on the backend removed, Leaderboard rows included, so that nothing of me stays public.
6. As a player who deletes the account, I want this device's local data cleared only after the backend confirms the delete, so that a failed delete never costs me my progress.
7. As a player who deletes the account, I want the app to start fresh afterwards, with a signed-out Daily, the system theme, and the How-to open, so that the device looks like a first visit.
8. As a player who deletes the account, I want nothing on screen to write the cleared data back, so that the deleted account's progress never reappears on the device.
9. As a player whose delete fails, I want a one-line error in the dialog and nothing changed, so that I can try again.
10. As a player with a delete in progress, I want the dialog buttons disabled until the call ends, so that I cannot send it twice.
11. As a player with another device still signed in to the deleted account, I want that device to sign itself out on its next sync and keep its local data, so that it becomes an ordinary signed-out device.
12. As the owner, I want the delete function callable only by a signed-in account and only for its own account, so that no visitor and no other account can delete a user.

## Implementation Decisions

- **Migration `20260930000006_account_deletion.sql`** (applied after the sibling tickets' migrations, whatever their numbers): one `SECURITY DEFINER` function written in `plpgsql` (`language sql` cannot raise conditionally): `public.delete_account()`, returning `void`, with an empty `search_path` (so `auth.uid()` and `auth.users` are schema-qualified). It raises an exception (`errcode` `28000`) when `auth.uid()` is null, so a call with no signed-in user fails and never silently deletes nothing. Otherwise it deletes the `auth.users` row of `auth.uid()`. A signed-in JWT whose user is already gone deletes zero rows without error; the app treats that as success (see the sync module). The cascades already in place (auth user, account row, every private table) remove the rest, and the future leaderboard views stop showing the player because their rows are gone. The function takes no argument, so a caller can only name themselves. It revokes as the existing function migrations do (`revoke all on function ... from public, anon, authenticated`), then runs `grant execute ... to authenticated` alone ("Automatically expose new tables" is off, and functions default to PUBLIC, so the revoke is explicit). It grants nothing else and touches no table grant.
- **`Remote` gains `deleteAccount()`**. The Supabase adapter works in this order: it reads the session (a `user_not_found` auth error rejects with `AccountGoneError`, as `getAccount` does; no session rejects with a plain error), calls the RPC, and only after the RPC succeeded drops the client library's stored sign-in, using the library's local sign-out, and removes the stored sign-in key by hand if that local sign-out throws or returns an error (the library returns an error for a failed local sign-out rather than throwing; the delete has already succeeded, so cleanup failure never fails the call). A rejected RPC rejects `deleteAccount()` and leaves the stored sign-in alone. The fake `Remote` records the call, can be made to fail or held, and on success signs the fake out and empties its account rows in place (devices sharing the rows see them gone).
- **The sync module gains `deleteAccount()`**, with an `onAccountDeleted` listener, as Spec 4 assigns account deletion to the sync module. While a delete is running, sync is paused by a `deleting` flag: `deleteAccount()` sets it and stops sync (the existing epoch reset drops in-flight pulls and pushes and the push timer). `refresh()` does nothing while the flag is set, and a sync task that was already queued when the delete began (it would start with the new epoch) checks the flag as its first step and returns, so no task can read the account or report it gone during the call. The flag is cleared when the call ends: on failure before the resume refresh, on success right before the device is cleared (the remount keeps this sync, so it works for the next sign-in; a refresh after a delete reads the signed-out account and pulls nothing). A second `deleteAccount()` call while the flag is set does nothing. That removes the race where a pull sees the account vanish and signs the device out while the delete is still finishing. It then calls `Remote.deleteAccount()`:
  - On success it clears every Portdle key through `Persist.clearAll()` (which keeps clearing when one key is stuck; that is accepted, since the account is already gone), then tells its listeners. It does not assume an active account is still set.
  - An `AccountGoneError` from the remote counts as success: the account is already gone, which is the outcome the player asked for. Sync first calls `Remote.signOut()` best-effort (a failure is ignored, as in the Account gone path) so the stored sign-in is dropped, then clears the device as above.
  - Any other rejection is rethrown. Nothing else changes: the local store, the sign-in, and the pending push list stay as they were. Sync resumes with a refresh (the same pull a focus event runs, so it may merge account rows into the store), which costs one full pull and pushes the pending changes. A refresh that a focus or visibility event asks for during the call is dropped; that resume refresh covers it.
  Its own writes never count as local changes, and after the stop nothing marks rows.
- **The app remounts on `onAccountDeleted`**, using the remount the device progress choice (#138) added (`App` bumps a generation that keys the router provider, so the shell, the screen, the theme, and the How-to start from the cleared store; the sync module and the router instance stay). `App` listens to `onAccountDeleted`: it first navigates the router to the Daily (a replace, with no view transition), so no screen mounts on the cleared store at the old location, and then remounts. A UTC day change still rebuilds the router as today.
- **Account menu**: a signed-in menu shows Delete account beneath Sign out. Opening the dialog closes the menu; Every way of cancelling the dialog returns focus to the Account button, and the dialog closes when the sync module reports the account gone. It is absent when signed out, while the account loads, and when the account failed to load. It opens the delete confirm dialog. The dialog is a native `dialog` in the app's compact card pattern (the How-to size), named "Delete account". It says what Spec 4's Account deletion says. It has Delete account (confirm) and Cancel; both are disabled while the call runs, and Escape and a backdrop click cancel it only when no call is running (while one runs, the native dialog's `cancel` event is prevented so the dialog and its React state agree), and the dialog renders outside the menu's container, as the name confirm does, because opening it closes the menu; and Escape and a backdrop click on the dialog reach neither the menu's nor the How-to's document handlers (the dialog stops Escape as the name confirm does). On failure it shows a one-line error ("Could not delete your account. Try again.") in the dialog and stays open with the buttons available again.
- **`Remote.deleteAccount()` failing early** (the client library cannot load, or the RPC is refused) rejects with nothing changed and the stored sign-in kept. The RPC alone cannot report a gone user, because the API checks only the token, so the function deletes zero rows and the call succeeds.
- **Other devices** need no new code: the existing Account gone path (a pull or push that reports the account missing, or the auth service refusing the stored sign-in) already signs the device out and keeps its local data, and the Supabase adapter already recognizes both. The ticket adds a test that proves it end to end for a deletion made elsewhere.
- **Copy**: the error and dialog text live in the existing display-name-copy style constants file next to the other account copy.
- **Not in this ticket**: the leaderboard views (#139) and the device progress choice (#138). The delete function does not reference the views.
- **Smoke script**: `supabase/tests/account-deletion.sql`, run by hand in the SQL editor like the existing ones. It creates two throwaway users, A and B, each with a row in each of the four private tables (Codex entries, Bests, runs, Dailies). It calls `delete_account()` as `anon` and asserts a privilege error, and as `authenticated` with no user claim and asserts the raised exception. It then calls it as `authenticated` with A's JWT claims (`set local role authenticated` plus `set_config('request.jwt.claims', ...)`, because the SQL editor role itself bypasses row-level security) and asserts, after `reset role` (as the SQL editor role, so row-level security hides nothing), that A's auth user, account row, and every private row are gone while B's are untouched. It follows the style of the existing scripts: a `do $$` block with `assert`, and a notice on success. It asserts the privileges with `has_function_privilege` for `anon` (no) and `authenticated` (yes); the `anon` result also proves the PUBLIC default is revoked, since `anon` inherits it. It cleans up B after itself.

## Testing Decisions

- A good test acts as the player through the highest seam (`App` with `memoryStore`, a memory history, and the fake `Remote`) and asserts what the player sees, the local store's contents, and the fake account's rows. It never asserts internal calls beyond the `Remote` calls the fake records.
- **App-level tests** (`account-menu` suite, new `account-deletion` test file): Delete account is absent signed out and present signed in; the dialog opens with the stated text; Cancel, Escape, and a backdrop click close it and delete nothing, every way of cancelling returns focus to the Account button, and the dialog closes when the account is reported gone; confirm calls `deleteAccount` once; on success the store holds none of the deleted account's data (no Codex, Best, run, Daily, preference, How-to seen flag, or sync bookkeeping; the remounted shell writes only what a first visit writes, the last seen UTC day), the fake account's rows are gone, the screen is a signed-out Daily with the How-to open and the system theme, and the Account menu offers sign-in; a failed delete shows the one-line error, keeps the dialog open, keeps every local value, the sign-in, and the account's rows; a delete held in flight disables both buttons; the location after deletion is the Daily even when the player deleted from another screen; Escape and a backdrop click on the dialog do not reach the How-to or the menu; a remote that reports the account already gone counts as a successful delete and leaves no stored sign-in; after a successful delete the Daily starts empty, and a guess typed on it stores one guess, not the guess the old screen held; a second device (a second store, the same account rows, a fake flagged as gone) signs out on its next pull and keeps its local data.
- **Sync module tests** (`sync.test.ts`): `deleteAccount` clears the store and notifies listeners only after the remote succeeded; a failed remote leaves the store, the timer, and the pending push list in place and sync working (the next write still pushes); an in-flight pull or push held across the delete does not write after the clear; an `AccountGoneError` from the remote clears the device like a success; after a delete a refresh reads the signed-out account and pulls nothing, and the next sign-in syncs again. A refresh asked for during the call does nothing, and a failed delete resumes sync with a refresh that pushes the pending changes; a sync task queued behind a held push when the delete starts does nothing and never signs the device out mid-delete; a second delete call during a delete does nothing.
- **Adapter test** (`supabase.test.ts`, existing injected-library style): `deleteAccount` calls the RPC `delete_account`, then drops the stored sign-in; a rejected RPC leaves the stored sign-in and rejects; a `user_not_found` session error rejects with `AccountGoneError`; a local sign-out that throws, and one that returns an error, after a successful RPC still resolve and remove the stored key; a retryable session error rejects as a plain error and changes nothing.
- Prior art: `account-menu.test.tsx` (menu flows, rename with error), `name-confirm.test.tsx` (native dialog tests), `row-sync.test.tsx` (two devices, one account), `sync.test.ts` (fake clock and fake remote).
- **Not in Vitest**: the SQL. It is checked by the hand-run smoke script above.

## Out of Scope

- The leaderboard views and the Leaderboards tab (#139); a deleted player's Leaderboard rows go through the cascade alone.
- The device progress choice dialog (#138), except that both use the same remount.
- Deleting only some data, an export before delete, a grace period, or an undo.
- Emailing or otherwise notifying the player.
- Any change to sign out, which keeps local data.

## Further Notes

- Author calls, listed so the owner can overrule them:
  - Delete account sits under Sign out in the Account menu and the confirm button reads "Delete account".
  - The dialog can be cancelled by Cancel, Escape, or a backdrop click, but not while a delete is running.
  - Account deletion lives in the sync module (as Spec 4 lists it) and the app remounts through a listener, so no screen calls the remote directly for deletion.
  - The function has no argument and deletes `auth.uid()` only, raising when there is no signed-in user; EXECUTE goes to `authenticated` alone.
  - A remote that reports the account already gone counts as a successful delete and clears the device (the player asked for the account to be gone).
  - If the RPC commits but its response is lost, the app shows the failure; the device then signs out through the Account gone path on the next refresh and keeps its local data.
  - Deleting in one tab clears the browser's shared local store under any other tab of the same browser; that tab signs out on its next sync with the data already gone. Spec 4 story 64 (story 11 here) promises kept local data on other devices.
  - If `Remote.signOut()` fails in the already-gone path, the stored sign-in stays; the next app load reads the stored sign-in again, and the existing Account gone detection (a refused session or a missing account row) signs the device out then, on an empty store.
  - A UTC day change during the call rebuilds the router and remounts the menu, which loses a shown failure or busy state; the name confirm has the same edge.
  - Sync pauses for the length of a delete call and resumes with a refresh if the delete fails.
  - The stored sign-in is dropped inside `Remote.deleteAccount()` after the RPC succeeds, so a failed RPC never signs the player out.
  - The stored sign-in key is removed by hand if the library's local sign-out fails after a successful delete.
- The hand steps for the owner (apply the migration, run the smoke script) go in the PR body.
