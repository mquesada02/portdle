# Ticket spec: Screenshot gate tracer bullet

Spec for #227. Tracker: https://github.com/mquesada02/portdle/issues/227. Parent: Spec 6 (tests, CI, and motion), https://github.com/mquesada02/portdle/issues/222 (`docs/superpowers/specs/2026-10-04-spec6-tests-ci-motion.md`, "Screenshot gate: data", "Screenshot gate: freezing frames", "Screenshot gate: matrix and engines", "Baselines", and the owner decision of 2026-10-04 on the merge-base baseline). Map: https://github.com/mquesada02/portdle/issues/212. Decisions: #213 (research), #216 (fixed data), #217 (frame prototype), #218 (baselines). Base branch: `master`. Blocked by: none.

## Problem Statement

A change to a motion (a duration, an easing, a keyframe) or to the look of a screen reaches review only when the owner opens the site. No test sees mid-motion frames. The functional suite runs against the local stack and cannot compare images.

## Solution

A new screenshot gate runs in CI (continuous integration) on every pull request and master push. It builds the site against a stub host, serves it with its own Playwright configuration, and answers every backend read from committed fixtures. It fixes the clock and the random source. It freezes the tile pop at fixed times and takes exact-compare screenshots in Chromium. On a master push it captures the frames and uploads them as the baseline. On a pull request it compares its frames with the baseline of the pull request's merge-base commit. A difference fails the job, unless the pull request carries the `visual-change` label.

This ticket proves the whole loop for one motion (the tile pop) and one screen (the fresh Daily at rest), in Chromium only. Later tickets widen the coverage and the engines. Ticket #233 adds the freeze route for `::details-content`.

## User Stories

1. As a developer, I want a stub build whose backend address is a stub host, so that the gate never reaches a real backend.
2. As a developer, I want the gate to have its own Playwright configuration and web server, so that the functional suite and the gate never share settings.
3. As a developer, I want one command, `pnpm gate`, to build the stub build and run the gate, so that I run locally what CI runs.
4. As a developer, I want one command, `pnpm gate:capture`, to write the baseline, so that CI and an agent create a baseline the same way.
5. As a developer, I want committed fixtures for the current Dailies, the catalog, the Schedule, and the Global stats, so that every frame shows the same data.
6. As a developer, I want the catalog fixture to be a snapshot of the real 74 entries, so that the frames show real content.
7. As a developer, I want the Schedule fixture to hold rows around 2026-10-10, so that the puzzle number and the Archive have rows before that day.
8. As a developer, I want every other request to the stub host, and to any other host, to fail the test, so that a frame never depends on an unseen request. The preview server's own files are the one exception.
9. As a developer, I want the device clock installed at a fixed moment, so that dates do not change the frames.
10. As a developer, I want a seeded `Math.random`, so that random choices do not change the frames.
11. As a developer, I want the ticket to record which page timers the installed clock fakes, so that later tickets know when they must poll from the test process.
12. As a developer, I want a freeze helper that waits for earlier motion to end, then for the named target animation, so that the helper never freezes the wrong animation (the prototype caught focus-ring transitions first).
13. As a developer, I want the helper to poll from the test process, so that a faked page timer never stalls it.
14. As a developer, I want the helper to pause every animation and take one screenshot per listed time, with `animations: "allow"`, so that each frame is the state at that time.
15. As a developer, I want the tile pop frozen at 0, 40, 75, 110, 150, and 190 ms, so that both staggered pops (the second starts at 40 ms and ends at 190 ms) show in the frames.
16. As a developer, I want the fresh Daily at rest as one frame, so that the first screen is guarded.
17. As a developer, I want these frames at 375 × 812 and 1024 × 768, in light and dark, so that the matrix of the spec is proven.
18. As a developer, I want the tile pop to run again with reduced motion, so that the reduced-motion rule is proven: no pop animation starts, and one end frame is taken.
19. As a developer, I want the compare to be exact (no pixel tolerance), so that a one-pixel change fails.
20. As a reviewer, I want a master push or a manual run on master to capture the frames and upload them as the Chromium baseline artifact, kept 30 days, with no compare, so that merging approves a frame change.
21. As a reviewer, I want a pull request to compare with the baseline of its merge-base commit, so that a pull request that is behind master fails only on its own changes.
22. As a reviewer, I want the job to download a baseline only when the whole master run for that commit succeeded, so that a red run never serves as a baseline.
23. As a reviewer, I want the job to capture the merge-base first when that baseline is missing, red, or expired, so that the first pull request after this change, and any pull request later, still gets a compare. This path must work on this pull request, because master has no baseline yet.
24. As a reviewer, I want the `visual-change` label to make the job upload its differences and pass, so that an intended change merges.
25. As a reviewer, I want adding or removing the label to start a new run, so that the check follows the label.
26. As an agent, I want a failed run to upload the expected, actual, and diff images, the report, and the traces, kept 14 days, so that I can read the frames and find the cause. A passing run uploads nothing.
27. As an agent, I want a local run to write its frames to `test-results/`, so that I can read them without CI.
28. As a developer, I want the screenshot job to run in the pinned Playwright Docker image with `--ipc=host`, with Node and pnpm set up, so that fonts and rendering match between runs.
29. As the owner, I want no baseline image committed to git, so that the repository does not grow.
30. As the owner, I want the proof in the pull request: a deliberate one-pixel change fails the job, and the label makes it pass, checked once and not committed.

## Implementation Decisions

- **Seams**: one seam, the stub build in a real browser (the same highest seam as the functional suite). The gate asserts frames, not internal functions. The only new pure code is the freeze helper and the stub routes; the proof that they work is the gate itself, run twice with no diff, plus the one-pixel proof.
- **Stub build**: `vite build` with `VITE_SUPABASE_URL` set to `http://stub.test` and `VITE_SUPABASE_ANON_KEY` set to a fixed dummy value, into `dist-gate`. The runner script (like `scripts/e2e.ts`) builds, then starts Playwright with the gate configuration. The runner takes an optional source directory, so the merge-base fallback builds an older commit with its own dependencies. The build skips `tsc -b`, which `pnpm typecheck` runs.
- **Gate layout**: a new configuration file at the repository root, a new test folder (`gate/`) that holds the specs, the fixtures, and the helpers, and the runner script in `scripts/`. The functional configuration `playwright.config.ts`, the `e2e/` folder, and the `sql-tests` job stay untouched (ticket #226 edits them).
- **Configuration**: its own web server (`vite preview` on `dist-gate`, a port that differs from the functional suite's, `strictPort`, no reuse of a running server). `workers: 1`, `retries: 0`, `trace: "retain-on-failure"`, the HTML reporter (never opened) and the list reporter. The matrix is Playwright projects, one per viewport, theme, and motion setting, named `chromium-<width>-<theme>` and `chromium-<width>-<theme>-reduced`. Each project sets its viewport, `colorScheme`, and `reducedMotion`. The tests that suit a setting (at rest: no reduced run; motion: both) select by the project's reduced-motion setting.
- **Compare**: `toHaveScreenshot` with `animations: "allow"`, `threshold: 0`, `maxDiffPixels: 0`. The snapshot path is `gate-baseline/<test file>/<name>-<project>.png`, with no platform part, because only the pinned image renders baselines. `pnpm gate` compares and never writes a baseline (`--update-snapshots=none`), so a missing baseline fails each frame and Playwright writes the frame to `test-results/`. `pnpm gate:capture` runs with `--update-snapshots=all` and writes `gate-baseline/`. `.gitignore` and `biome.json` list `dist-gate`, `gate-baseline`, and `gate-report`.
- **Stub routes**: one context-level route handler answers by path under the stub host: `rpc/current_dailies` (the app sends POST; the stub answers by path), `catalog_entries`, `schedule`, and `daily_global_stats`. The stats answer is a fixed row for the fixed day (from the Global stats fixture) when the query asks for that category and day, and an empty list otherwise. The paged reads answer the rows for `offset=0` and an empty list after. The handler continues requests to the preview server's origin. Each answer carries the CORS (Cross-Origin Resource Sharing) headers that the page needs, and the handler answers the preflight `OPTIONS` requests itself, because the page calls the stub host from another origin. `Access-Control-Allow-Headers` lists the headers that the Supabase library sends (`apikey`, `authorization`, `content-type`, `x-client-info`, and `prefer`). It aborts every other request and records its URL, so an unseen request is a failure, not a silent abort. The auth endpoints are not stubbed. A signed-out device is expected to call none of them, and a call fails the test. The empty unstubbed-request list at the end of each test is the confirmation of the auth list that Spec 6 asks this ticket for. A fixture fails the test when the list is not empty. The first run re-confirms it, and the pull request records the result. The signed-in stubs belong to later tickets.
- **Fixtures**: JSON files in the gate folder. The Global stats fixture is one hand-written row of `daily_global_stats` for the fixed day (players, wins, one count per number of tries, and lost). The catalog is the 74 rows read from the local stack's `catalog_entries` (as the migration `20261001000009` imports them), in the database row shape, ordered by `id`. The Schedule is hand-written for the three categories, from 2026-10-04 to 2026-10-10 (the real backend hides later rows from the public key). The current Dailies read answers `server_time` `2026-10-10T12:00:00+00:00` (the format of the real function) and `utc_date` `2026-10-10`, with the entries of the Schedule rows for that day. The tile pop test plays the Mixed Daily category, and the entry of its day has a two-digit port, so the guess has two digit slots and two tiles pop. The 40 ms stagger is a CSS `animation-delay` (set inline on each tile), and `currentTime` includes the delay, so one `currentTime` for all paused animations is right.
- **Clock and random**: `page.clock.install` at `2026-10-10T12:00:00Z`, and an init script that replaces `Math.random` with a seeded generator and stores the how-to flag and the theme (so no dialog covers the board, and the app theme matches the project). Verified with Playwright 1.63 in Chromium on 2026-10-05: after `install`, the page's `setTimeout`, `setInterval`, `requestAnimationFrame`, `requestIdleCallback`, `performance.now`, and `Date` are fakes; `MessageChannel` and CSS animations are not. Time still flows at the real rate after `install`, so page timers still fire. After `pauseAt`, a page `setTimeout` and `requestAnimationFrame` never fire (checked: none fired in 500 ms), while a `MessageChannel` message does. This ticket installs the clock and does not pause it. The helper's polls run in the test process, so they work with a paused clock. Its frame sync (two `requestAnimationFrame` ticks after each `currentTime` change) needs a running clock. A later ticket that pauses the clock must change that sync first.
- **Freeze helper**: before the interaction, the helper repeats a page evaluation from the test process until no animation runs (earlier motion ended). Then it runs the interaction, and repeats a page evaluation until an animation with the target name runs. The target is a keyframe name (`pop`) or a `::view-transition-*` pseudo-element (the helper supports both names, because the spec requires both; this ticket uses `pop`). It pauses every running animation, then for each time sets `currentTime` on each paused animation and takes `expect(page).toHaveScreenshot(name)`. The configuration supplies `animations: "allow"`. The helper fails with a clear message when the target does not start within 2 seconds. With reduced motion, the test does not use the helper. It asserts, with a separate check, that no animation with the target name exists after the guess row is visible, and takes one end frame.
- **Interaction**: the Mixed Daily category, a missed guess of two digits (typed into the digit slots, then submitted with the Enter key). The helper waits until no animation runs before the interaction, so earlier motion never reaches the freeze. Frame names: `daily-tile-pop-<time>ms`, `daily-tile-pop-end` (the one end frame with reduced motion; the project name already says `reduced`), and `daily-fresh`. No frame shows a live time (the Daily screen has no clock or countdown), so the flowing clock does not change a frame.
- **CI job**: a new job `screenshots-chromium` in `.github/workflows/ci.yml`, in the container `mcr.microsoft.com/playwright:v1.63.0-noble` with `--ipc=host` (a comment says: keep this tag equal to the `@playwright/test` version in `package.json`, like the supabase CLI comment). Steps: checkout with full history. The checkout ref is the pull request head commit on `pull_request` (not the merge commit that GitHub builds, because a newer master must not change the frames), and `github.sha` otherwise. The job branches on the event and the ref: capture when the event is `push` or `workflow_dispatch` and `github.ref` is `refs/heads/master` (as the `deploy` job guards its ref), compare when the event is `pull_request`. A manual run on another branch skips the job, because it has no merge-base rule and must never upload a baseline. Then pnpm and Node 22 as the other jobs, `pnpm install --frozen-lockfile`. Permissions of the new job only: `contents: read` and `actions: read`. The permissions of the other jobs do not change. The `pull_request` trigger adds `labeled` and `unlabeled` to the default types (`opened`, `synchronize`, `reopened`). The `build`, `sql-tests`, and `deploy` jobs stay as they are.
- **Master run** (`push` or a manual run, on `master`): build, `pnpm gate:capture`, upload `gate-baseline` as the artifact `gate-baseline-chromium`, 30 days. No compare.
- **Pull request run**: compute the merge-base with `git merge-base origin/master <head commit>`. A script step (`actions/github-script`) lists the runs of the workflow `ci.yml` with `branch` `master`, `head_sha` equal to the merge-base, and `status` `completed`. The script skips a run whose `conclusion` is not `success`. It then needs an artifact named `gate-baseline-chromium` with `expired` false in that run. The run's `conclusion` is `success` for the whole workflow. Today that means `build`, `sql-tests`, the screenshot job, and `deploy` all passed. `deploy` does not wait for the screenshot job yet (see the Author calls list in Further Notes), but a run is `completed` only when every job has ended, so the lookup stays correct. If it finds one, `actions/download-artifact` downloads it into `gate-baseline` with the run id, the `github-token`, and the `repository` (`actions: read`). If not found, the job builds the merge-base commit (a `git worktree`, its own `pnpm install`) with the runner's source option, and runs the pull request's own gate tests against that build with `pnpm gate:capture`, which writes `gate-baseline`. Before any git command, the job runs `git config --global --add safe.directory '*'`, because the container user may differ from the owner of the checkout. The job then builds the pull request's commit and runs `pnpm gate`. The compare step has `continue-on-error` when the pull request carries `visual-change` (read from the run's own event payload). With `continue-on-error`, a failed step has the outcome `failure` and the conclusion `success`, so the upload step has the condition `always() && steps.<compare>.outcome == 'failure'`. It uploads `test-results` and `gate-report` (the gate's own report folder), 14 days. A passing run with no difference uploads nothing.
- **Local run**: `pnpm gate` with no baseline fails each frame and writes the frames to `test-results/`. Compare against a downloaded baseline only inside the pinned image.
- **Side effects of the new files**: Vitest excludes the gate folder (as it excludes `e2e/`); a new `tsconfig` for the gate files (ES2023, DOM (Document Object Model), and Node types), added to the root `tsconfig.json` references, so `pnpm typecheck` covers them; the runner script joins the Node `tsconfig` file list; Biome and `.gitignore` as above. Nothing in `src/` changes.

## Testing Decisions

- A good test here drives the stub build as a player does and asserts frames. The gate is itself the test of itself. Its checks, run and recorded in the pull request:
  - `pnpm gate:capture`, then `pnpm gate` with the same baseline, passes with no difference, twice (determinism), inside the pinned Docker image;
  - the clock verification in "Clock and random" is re-run once and its result is in a comment of the helper or fixture file;
  - an unstubbed request fails a test (checked once with a temporary extra read);
  - on the pull request, the job takes the "missing baseline, capture the merge-base first" path and passes;
  - the proof: a temporary one-pixel change (not kept in the branch) makes the job fail and upload expected, actual, and diff images; adding the `visual-change` label makes the job pass and upload the differences; the change is then dropped;
  - `pnpm lint`, `pnpm typecheck`, `pnpm test`, and `pnpm build` pass; the functional suite and the `sql-tests` job are untouched.
- Unit tests: only for pure code. The runner's option parsing and the stub's paged-read answer are too small to need one. If a pure helper grows (for example the baseline lookup), it gets a Vitest test beside it. The baseline lookup is inline script in the workflow, so it has no unit test; the pull request run is its test.
- Prior art: the existing Playwright suite (`e2e/`, its how-to dismissal, its runner) and the frame prototype on branch `prototype/frame-gallery` (`capture.mjs`: stub build, stub routes, seeded random, wait for the named animation, pause, `currentTime`).

- The new Spec 6 motion (height and crossfade).
- A gallery page, Git LFS, committed baselines.

## Further Notes

### Author calls

1. File names: `playwright.gate.config.ts`, a `gate/` folder, `scripts/gate.ts`, `tsconfig.gate.json`; scripts `gate` and `gate:capture`.
2. The matrix is Playwright projects named `chromium-<width>-<theme>[-reduced]`, so a later engine adds projects with its own prefix and the snapshot names carry the project.
3. Baseline folder `gate-baseline/`, no platform in the snapshot path, artifact name `gate-baseline-chromium`.
4. The pull request job builds the pull request's head commit, not the merge commit that GitHub builds, so a newer master never shows in the frames.
5. The merge-base fallback builds the merge-base source in a worktree and runs the pull request's gate tests against it (the merge-base may have no gate at all, as on this pull request).
6. With reduced motion, the tile pop takes one end frame and asserts that no `pop` animation starts, not a frame per time.
7. `pnpm gate` never writes a baseline (`--update-snapshots=none`); only `pnpm gate:capture` does.
8. The clock is installed and not paused in this ticket; the verified fake-timer list is recorded.
9. The catalog fixture keeps the database row shape (so the shape check of ticket #226 can compare keys and types), taken from the local stack.
10. The `deploy` dependency on the screenshot job, the docs-only skip, and a `concurrency` group are not added here (listed in the Spec 6 "CI layout" section; later tickets).
11. For the proof, the developer pushes the temporary one-pixel change as a commit, then drops it from the ticket branch with a force push (`--force-with-lease`).
12. The artifact lookup uses `actions/github-script`, because the container has no `gh`.
13. A pull request that adds or changes frames fails without the label, because the merge-base capture runs the pull request's own tests and the master baseline comes from older tests. This is the "merging approves a change" rule.
14. With `continue-on-error`, a labelled run also passes when the compare step fails for a reason other than a difference (an unstubbed request, a helper timeout). The uploaded report shows the cause. Spec 6 accepts this.
15. The label events start a whole `ci.yml` run, so `build` and `sql-tests` run again too. Without a `concurrency` group, every label change starts a run beside the earlier one. A re-run of an old run reuses its old event payload, so it reads the old label state.
16. The `::details-content` freeze route is not chosen here. The owner approved the deferral to #233 (see Out of Scope).
17. Determinism needed three settings, found by running the gate five times in the pinned image: Chromium runs with `--disable-lcd-text` and `--font-render-hinting=none` (grayscale text), and with `--disable-threaded-animation`. Without the last one, a paused animation drew a stale compositor frame at 0 ms, and the same frame differed between runs. The freeze helper also waits for the `ready` promise of each paused animation, and for two drawn frames after each `currentTime` change.
18. The gate reports to `gate-report/`, not `playwright-report/`, so it never overwrites the functional suite's report.

### Facts checked

- Checked on 2026-10-05 with Playwright 1.63.0 in Chromium: after `clock.install`, the page's `setTimeout`, `setInterval`, `requestAnimationFrame`, `requestIdleCallback`, `performance.now`, and `Date` are fakes; `MessageChannel` and CSS animations are not. Time flows at the real rate. After `pauseAt`, a page `setTimeout` and `requestAnimationFrame` never fire in 500 ms, and a `MessageChannel` message does.
- The local stack's `catalog_entries` holds 74 rows (48 protocols, 26 applications).
- `@playwright/test` is pinned at exactly 1.63.0 in `package.json`, and the image tag `v1.63.0-noble` exists (research #213).
