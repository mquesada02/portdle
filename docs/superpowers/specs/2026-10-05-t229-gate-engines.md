# Ticket spec: Gate on WebKit and Firefox

Spec for #229. Tracker: https://github.com/mquesada02/portdle/issues/229. Parent: Spec 6 (tests, CI, and motion), https://github.com/mquesada02/portdle/issues/222 (`docs/superpowers/specs/2026-10-04-spec6-tests-ci-motion.md`, "Screenshot gate: matrix and engines", "Baselines", user story 22). Map: https://github.com/mquesada02/portdle/issues/212. Decisions: #213 (research), #218 (coverage and baselines). Base branch: `master`. Blocked by: #227 (merged, PR #240). Tracer spec: `docs/superpowers/specs/2026-10-05-t227-gate-tracer.md`.

## Problem Statement

The screenshot gate runs in Chromium only. Safari and Firefox players see frames that no test checks. Also, today a pull request with the `visual-change` label passes even when a gate test errors (an unstubbed request, a helper timeout), because the compare step ignores every failure.

## Solution

The gate runs in WebKit and Firefox too, in two new CI (continuous integration) jobs. The three jobs are matrix entries of one job and run in parallel. Each engine has its own projects and its own baseline artifact. Firefox takes only the end frame of a view transition. The gate runner exits with a distinct code when frames differ and no test errored. The `visual-change` label excuses only that code, in the three engine jobs. A frame that has no baseline (a new frame) counts as a frame difference. A frame that a test never takes counts as an error.

## User Stories

1. As a developer, I want WebKit and Firefox projects in the gate configuration, with the same matrix as Chromium (375 × 812 and 1024 × 768, light and dark, plus reduced motion), so that both engines get every frame that Chromium gets.
2. As a developer, I want the project names to start with the engine name (`webkit-`, `firefox-`), so that a frame name says which engine took it and the baselines of the engines never mix.
3. As a developer, I want the Chromium launch flags to apply to Chromium only, so that the other engines never receive flags that they do not know.
4. As a developer, I want to run one engine with `pnpm gate --project 'webkit-*'`, so that I run locally what one CI job runs.
5. As a developer, I want the freeze helper to take only the end frame of a view transition in Firefox, so that the gate never compares frames that Firefox draws wrongly (its screenshot seems to draw the live page, not the view-transition overlay; the cause is not verified).
6. As a reviewer, I want three screenshot jobs (Chromium, WebKit, Firefox) with the same baseline loop, so that each engine has a green or red check.
7. As a reviewer, I want one baseline artifact per engine (`gate-baseline-<engine>`), kept 30 days, so that a job downloads only its own frames.
8. As a reviewer, I want a failed or labelled-different run to upload an artifact per engine (`gate-failure-<engine>`), so that I read the frames of the engine that failed.
9. As the owner, I want the `visual-change` label to excuse only frame differences, so that an errored test still fails the job (an unstubbed request, a helper timeout, a frame that a test never takes), in every engine job, Chromium included.
10. As the owner, I want the runner to tell frame differences from errors with a distinct exit code, so that the label step can check it.
11. As an agent, I want a local `pnpm gate` run to give the same exit codes as the runner gives in CI, so that I find an error before I push.

## Implementation Decisions

- **Seams**: one seam, as in the tracer: the stub build in a real browser. The new pure code is the report classifier. Its proof is a Vitest test beside it. The rest is proven by the gate itself, in the pinned image.
- **Projects**: `playwright.gate.config.ts` gets a list of engines: name, device profile (`Desktop Chrome`, `Desktop Safari`, `Desktop Firefox`), and extra `use` options. The project list is the product of reduced motion, viewport, theme, and engine. Names are `<engine>-<width>-<theme>[-reduced]`. The Chromium flags (`--disable-lcd-text`, `--font-render-hinting=none`, `--disable-threaded-animation`) move from the global `use` to the Chromium entry. WebKit and Firefox run with the profile defaults. The first run in the pinned image checked that each engine matches its own baseline over three compare runs (checked on 2026-10-05, Playwright 1.63.0, `v1.63.0-noble`: 24 passed, 8 skipped, three times).
- **Snapshot path**: unchanged (`gate-baseline/<file>/<name>-<project>.png`). The project name carries the engine, so one folder holds all engines without a clash, and each artifact holds the files of its own engine only.
- **Engine selection**: the runner already passes extra arguments to Playwright, so a job selects its engine with `--project '<engine>-*'`. Every `gate` and `gate:capture` call in the job passes `--project '<engine>-*'` (the master capture, the merge-base capture, and the compare), because the default run now covers all three engines and each artifact must hold one engine only. The runner already forwards extra arguments for both commands, so `scripts/gate.ts` needs no change for engine selection. `pnpm gate` with no argument runs all engines (a local run needs the three browsers).
- **Firefox rule**: `shootMotion` in `gate/freeze.ts` takes only the last time of `times` when the engine is Firefox and the target starts with `::view-transition`. The last time is the end frame, and its frame name does not change (`<name>-<time>ms`). The helper reads the engine with `page.context().browser()?.browserType().name()`. A comment records that the cause of the Firefox draw is unverified. The theme crossfade test (ticket #242, on master after the first draft of this spec) reaches the rule: it takes five frames in WebKit and Chromium, and one in Firefox. A temporary local check on the first draft gave the same result.
- **Exit codes**: the configuration adds the JSON (JavaScript Object Notation) reporter (`gate-results.json`, listed in `.gitignore` and `biome.json`). A new `scripts/gate-report.ts` exports a pure function that reads the parsed report and answers `pass`, `differences`, or `errors`. `differences` means three things. At least one test failed. Every failed test has at least one error. Every error of every failed test is a frame error. A frame error is an error whose message, before the call log, contains `A snapshot doesn't exist` (a new frame), `N pixels (ratio R of all image pixels) are different` (a changed frame), or `Expected an image <W>px by <H>px, received` (a frame of another size). The call log is not read, because the log of a frame that never gets stable also lists pixel differences. That error is not a frame error. The classifier removes the ANSI (American National Standards Institute) colour codes from the message before it matches. Anything else is `errors`: any other error message, a timed-out or interrupted test, a report-level error. `scripts/gate.ts` deletes the old report before the run, runs Playwright, and, when Playwright fails, reads the report. When Playwright exits 0, the runner exits 0. When Playwright fails, the runner exits 2 for `differences`, and with the Playwright code otherwise. A missing or unreadable report gives `errors`, so the runner fails safe. A build error keeps exit code 1 (as today).
- **Capture of the merge-base**: `pnpm gate:capture --src <dir>` exits 0 when tests error and the report is readable (`isCaptureErrorsOnly` in `scripts/gate-report.ts`: only failed and timed-out tests, no report-level error, no interrupted run). A test that errors on the merge-base app, for example a test for a motion that only the pull request adds, takes no frame. Its frames are new frames in the compare step, which the `visual-change` label excuses. A capture of this checkout (no `--src`) and the compare step stay strict. The owner added this criterion on 2026-10-05 (defect found on PR #242).
- **Compare step**: in each screenshot job, the compare step runs `pnpm gate --project '<engine>-*'` in a way that does not stop the step (`code=0; pnpm gate ... || code=$?`, because the GitHub shell runs with `-e`). It writes the code to the step output `code`. Then it exits 0 when the code is 2 and the pull request carries `visual-change`, and with the same code otherwise. `continue-on-error` is removed from the compare step. The failure upload runs when the saved code is not 0 (so also for a labelled run that passes with differences). The upload condition is `always() && steps.compare.outputs.code != '' && steps.compare.outputs.code != '0'`. The upload path adds `gate-results.json` to `test-results` and `gate-report`. The label is read from the run's own event payload, as in the tracer.
- **Jobs**: the `screenshots-chromium` job becomes one job, with the id `screenshots`, and a matrix `engine: [chromium, webkit, firefox]` and `fail-fast: false`. The job `name` is `screenshots-${{ matrix.engine }}`, so the check names are `screenshots-chromium`, `screenshots-webkit`, and `screenshots-firefox` (the Chromium check keeps its name). The artifact names use the engine: `gate-baseline-<engine>`, `gate-failure-<engine>`; the baseline lookup script reads the engine from the job `env` variable `ENGINE` (set to `${{ matrix.engine }}`), and the `download-artifact` name is `gate-baseline-${{ matrix.engine }}`. The job `env` adds `ENGINE` and `HOME: /root`, the second because Firefox does not start in the container with the default `HOME` (author call 12). Image, permissions, other steps, and retention do not change. `sql-tests`, the deploy `needs`, the docs-only skip, and `concurrency` do not change (#235 owns them). The `pull_request` types stay.
- **Side effects of the new files**: `scripts/gate-report.ts` joins the Node `tsconfig` file list (`tsconfig.node.json`), so `pnpm typecheck` covers it. The other script tests are not in that list, so the new test stays out too. Vitest already runs `scripts/*.test.ts`. `gate-results.json` joins `.gitignore` and `biome.json`.
- **Gate files**: the fixtures, the stub, and the tests on master do not change, except for the engine fixes of author calls 9 to 11, 13, and 14 (`gate/theme.spec.ts`, `gate/daily-motion.spec.ts`, `gate/freeze.ts`, `gate/hide-shell-nav.css`). No test is added.
- **Baselines**: the first master push after the merge captures the three baselines. After the merge, the coordinator checks that this master run is green and that its three `gate-baseline-<engine>` artifacts exist (this is the ticket criterion "both jobs pass on master and produce baselines", three jobs here; a pull request cannot prove it). Until then, a pull request that finds no `gate-baseline-webkit` or `gate-baseline-firefox` artifact takes the merge-base capture path of the tracer. This pull request takes that path for both new engines, so its job shows that the path works for a new artifact name.
- **Frames of this pull request**: it adds frames for two new engines, and the merge-base capture runs the pull request's own tests, so those frames do not differ from their baseline. The theme frames change in every engine (author call 9), so the pull request carries the `visual-change` label, as the owner asked.

## Testing Decisions

- A good test drives the stub build as a player does and compares frames. The classifier is the one pure function, so it gets a Vitest test in `scripts/gate-report.test.ts` with these cases (the test file has twelve tests; the list names the kinds): a clean report; a report with only missing-frame errors; a report with only comparison errors; a report with one comparison error and one other error (`errors`); a timed-out test; a report-level error; a failed test with no error; a malformed report; a comparison error with ANSI colour codes in its message; a frame that never gets stable, whose call log lists a pixel difference (`errors`); a frame of another size.
- Checks run once and recorded in the pull request:
  - `pnpm gate:capture` then `pnpm gate` for each engine in the pinned image: no difference, three runs (done for WebKit and Firefox on 2026-10-05; repeated at the end for all three engines);
  - a run with no baseline exits with code 2, and a run with a temporary unstubbed request exits with code 1 (local, not committed);
  - the Firefox rule check above;
  - the three jobs on the pull request pass; a temporary commit with an unstubbed request in one test fails the job even with the `visual-change` label (dropped after the check, with `--force-with-lease`), and a temporary one-pixel change fails it without the label and passes it with the label;
  - `pnpm lint`, `pnpm typecheck`, `pnpm test`, and `pnpm build` pass.
- Prior art: the tracer's gate runner, `scripts/e2e-env.test.ts` and `scripts/stack-env.test.ts` (pure helpers beside the runner).

## Out of Scope

### Author calls

The owner accepted author calls 1 to 14 (through the coordinator), including the final form of call 13 (through the coordinator).

1. One matrix job, not three copies of the job. The check names stay `screenshots-<engine>`, so a required check on `screenshots-chromium` keeps working. The job id changes from `screenshots-chromium` to `screenshots`. Another ticket that wrote `needs: screenshots-chromium` must write `needs: screenshots` (ticket #235).
2. Engine selection with `--project '<engine>-*'` passed through the runner, not a new runner option, so the runner stays small.
3. One baseline folder with one artifact per engine, not one folder per engine. The project name already holds the engine.
4. The exit code for frame differences is 2. The classifier decides from the JSON report, by error message, because Playwright gives no other signal. A new Playwright message format could turn a difference into `errors` (the job then fails, which is the safe side). The version pin on Playwright and the test of the classifier limit this risk.
5. `continue-on-error` is removed from the compare step and replaced with a script that checks the code. This is the owner's criterion of 2026-10-05 (the owner comment on this ticket).
6. The Firefox rule keys on the target name (`::view-transition*`), not on a flag per test, so every later view-transition test gets the rule with no change.
7. No test is added for the Firefox rule: the ticket must not add coverage. When this spec was first written, no test had a view transition, and a temporary check was the proof. The theme crossfade test (#242) now reaches the rule on master.
8. A frame with no baseline (a new frame) is a frame difference, so the label excuses it. The owner criterion says "a missing frame" fails the job. This spec reads that as a frame that a test never takes (a helper timeout, a skipped step), which Playwright reports as a test error. The Spec 6 rule "a pull request that adds frames reports differences; the label approves them" needs the other reading for new frames. Work proceeds on this reading; the owner is asked to confirm it.
9. After a rebase on master, the theme crossfade test (ticket #242) gave a WebKit frame at 0 ms that differed between runs. The click blurs the focused digit slot and starts a border transition. In WebKit the view transition starts later than in Chromium, and the border transition can end before the freeze. The test now blurs the active element before the helper starts, so that transition ends first (`shootMotion` waits for quiet). The frames of this test change in every engine, and the merge-base capture of the pull request covers that. The change is a determinism fix and adds no coverage. The owner approved this change on 2026-10-05, with the `visual-change` label for the changed theme frames. Proof, in the pinned image: before the fix, three WebKit captures of `theme-crossfade-0ms` gave two different images, and a debug run showed the border transition of the digit slot running at the first poll while the view-transition animations were not there yet. After the fix, three captures give one image, and three compares per engine (Chromium, WebKit, Firefox, all tests) pass with no difference.
10. After the rebase on master (#245), three tests of `gate/daily-motion.spec.ts` (`How-to dialog closes`, `Miss popover closes`, `divider draw and Reveal rise of a won Daily`) failed in WebKit and Firefox, in every non-reduced project, and passed in Chromium. The owner chose the root-cause fix on 2026-10-05 and approved the change to that file. `shootMotion` gets the option `noMotionIn`: a list of engines where the target motion does not exist. There it takes only the end frame (the last time), so a missing motion in any other engine still fails. Only the `How-to dialog closes` test needs `noMotionIn` (the two others are call 11). It lists WebKit and Firefox, because both engines draw no exit transition on the dialog (a debug run in the pinned image showed no animation at all after the click, where Chromium showed `display`, `overlay`, `opacity`, and `scale` transitions).

Proof: three compares per engine of all tests, and ten loaded runs of the three affected tests (five in WebKit and five in Firefox, with one CPU burner per core, 8 cores): all green.
