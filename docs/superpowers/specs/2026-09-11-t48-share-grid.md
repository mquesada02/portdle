# Spec: Share line per-digit squares

Spec for #48. Tracker: https://github.com/mquesada02/portdle/issues/48

## Problem Statement

A player who finishes a Daily shares a line that only ever showed one square per try, standing in for whether that whole try was right or wrong. Now that every committed row carries a per-digit mark, the share line has fallen behind what the board itself shows: a friend reading the share can no longer see the same placed/present/absent story the player worked out digit by digit. The share line still needs to give nothing away beyond that shape — never the service name, never the port.

## Solution

The share line's header stays exactly as it is today. Below it, the share line grows one line per committed try, with one square per digit of that try: 🟩 for placed, 🟨 for present, ⬜ for absent. A win's last line is all 🟩, since a winning row is all placed. A loss shows all six committed lines and the header's try count reads `X/6`. Each line is built from the same per-digit marks the board itself computes, so the share can never disagree with what the player saw on screen, and it still leaks nothing but shape.

## User Stories

### Share line

1. As a player, I want the share header to read `Portdle · Mixed · 2026-09-10 · 3/6` as today, so that shares stay recognizable.
2. As a player, I want one line of squares per committed try, with one square per digit showing that digit's mark (placed, present, or absent), so that the share tells the same deduction story the board told me.
3. As a player who won, I want the share's last line to be all 🟩, so that a win reads as a win.
4. As a player who lost, I want six lines and `X/6` in the header, so that a loss reads honestly.
5. As a player, I want the share to leak only the digit count and the per-digit marks, never the service name or the port, so that friends can still play.

### Maintainer

6. As a maintainer, I want the share formatter to take each committed try's marks rather than a bare try count, so that the share line can never drift from what the marks engine function computes.
7. As a maintainer, I want the caller that builds the share text to derive those marks from the same stored data and the same marks function the board uses, so that UI and share never disagree.

## Implementation Decisions

### Share line

- The share formatter's input drops the bare committed-try count and instead takes one set of per-digit marks per committed try, in try order, alongside the game's outcome (won or lost) exactly as it is given today. The outcome, not a count or the marks themselves, is what the header's try-count token depends on: won reads the number of tries given over six (for example `6/6` for a win completed on the sixth try); lost is always `X/6` regardless of how many tries were given, exactly as today. A win completed on the sixth try and a loss both hand the formatter six sets of marks, so the outcome is the only thing that tells them apart.
- Below the header, the formatter renders exactly one line per set of marks it was given, each line built by turning that try's marks into one square per digit, in position order: 🟩 for placed, 🟨 for present, ⬜ for absent. No other text is added per line. The formatter does not decide how many tries to render beyond what it is told; it only turns the marks and the outcome it receives into the header token and the lines below it.
- The reveal derives each committed try's per-digit marks itself, using the same marks engine function the board's rows already use, from that try's stored port and the answer's port, padded to the answer's digit length the same way the board pads them. It passes one set of marks per committed try, in try order, to the share formatter to build the text that is copied to the clipboard or shown in the fallback textarea.
- Nothing about when the share text is built, how it reaches the clipboard, or the fallback textarea shown when the clipboard is unavailable changes from today's behavior — only the content of the text itself changes, to one line of per-digit squares per committed try.
- Nothing about what gets persisted for a Daily guess changes. The reveal derives marks the same way at every render, so a reload produces the identical share text.

## Testing Decisions

A good test exercises a public seam with literal inputs and asserts what a pure function returns or what a player can see through accessible roles and text — never internal state, class names, or styling. Expected values are literals from this spec.

- **Engine seam** (the share formatter, prior art: the existing share test file): a won game in three, given three literal sets of per-digit marks ending in an all-placed set, produces the exact three per-digit-square lines below the unchanged header, with the header's try count reading `3/6`; a lost game, given six literal sets of per-digit marks, produces all six lines below the header with `X/6`; a won game completed on the sixth try, given six literal sets of per-digit marks ending in an all-placed set, produces all six lines below the header with `6/6`, distinguishing it from the six-line loss case above by outcome alone; the header format itself (category label, date, separator) is otherwise unchanged from the existing tests. The existing share test file's own assertions, written against the old bare-count input, are rewritten to call the formatter with literal marks and an outcome instead.
- **App seam** (prior art: the existing Daily reveal and Mixed Daily test files, rendering the app with a memory store, memory history, and an injected day): Share after a win puts the per-digit-square text — not the old single-square line — on the clipboard; the fallback textarea still shows that same text when the clipboard is unavailable.
- The existing share assertions in the Mixed Daily test file that assert the old single-square-per-try line are updated to the exact per-digit-square lines the new formatter produces for those same tries.
- No snapshot tests, no visual regression, no Playwright. This ticket is proven done by `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm gen:schedule --check`, and `pnpm build` all passing, in addition to the coverage above.

## Out of Scope

- Marks, tiles, and the tracker strip themselves, their rendering, and their accessible text — covered by the Marks, tiles, tracker strip ticket (#47), already built.
- Any change to what gets persisted for a Daily guess, to the schedule, or to routes.
- Any change to the board, row captions, try counter, motion, or the miss popover.
- Fuzzy search and the Blitz end card's Best number — separate tickets, own files.
- Any change to Blitz, which never shows marks or a per-digit share line.
