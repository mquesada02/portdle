# Spec: Content descriptions and sources

Spec for #43. Tracker: https://github.com/mquesada02/portdle/issues/43

## Problem Statement

A player who wins, loses, or hovers a miss learns almost nothing about the service behind a port. Every reveal and every miss popover shows the entry's `description`, but most descriptions today are a single vague phrase — "File Transfer Protocol.", "Telnet protocol.", "MySQL database protocol." — that just expands the acronym or restates the name, with no source to read further. Only one entry, FTP, carries a `sources` list; the other 73 have none, so the miss popover's sources block never renders for them. The game's own glossary defines a Source as "a curated reference link for an entry" — that promise is unmet everywhere except FTP.

## Solution

Every entry in both catalogs — `src/catalogs/protocols.json` (48 entries) and `src/catalogs/applications.json` (26 entries), answer-eligible and miss-only alike — gets a rewritten `description` of one or two plain, factual sentences that says what the service or software is, what it is used for, and, when the reason is notable, why it sits on that port. No description that is only the entry's name or its bare expansion with nothing added. Every entry also gets at least one source (this ticket's own authored cap: at most three), each a short human label and an `https://` URL, preferring the defining RFC, the vendor or project's own documentation, and the IANA service-name registry entry when one exists. Entries that already carry a `blurb` for the crowded-port rule keep a valid one — updated only if the rule requires it, never otherwise. `id`, `name`, `port`, `aliases`, `transport`, `answerEligible`, and `retired` do not change on any entry, and no schedule file and no production code file changes. This is content-only, authored by hand against the schema and validation that already exist; the one narrow exception is `src/ui/miss-popover.test.tsx`, which hardcodes FTP's current literal description and source text and must be updated so it no longer breaks when that content changes (see Testing Decisions and Further Notes).

## User Stories

### Player

1. As a player who wins or loses a Daily, I want the reveal's description to teach me something specific about the answer, so that a vague one-line acronym expansion is no longer all I get.
2. As a player who hovers or taps an identified miss, I want the miss popover to show a real description and at least one source I can open, so that I can learn more about the service without leaving the game.
3. As a player reading a description, I want plain, factual English rather than marketing copy, so that the game reads like a reference, not an ad.
4. As a player who already knows the entry's name from its own description ("SSH (Secure Shell) is..."), I want the description to still tell me something beyond the name, so that reading it is worth my time.
5. As a player who opens a source, I want it to load the real page (a spec, vendor doc, or registry entry), not a dead source or an off-topic page, so that following through is worthwhile.
6. As a player facing a crowded-port miss (for example the several apps that all default to port 3000), I want the shown blurb to hint at the entry without naming it or any of its aliases, so that the port-8080/3000/5173 guessing game keeps working.

### Maintainer

7. As a maintainer, I want every entry's `description` to be one or two sentences covering what the service is, what it is used for, and — when notable — why it uses that port, so that content quality is consistent across all 74 entries.
8. As a maintainer, I want every entry to carry at least one `source`, each with a non-empty label and an `https://` URL, so that `validateCatalog`'s `invalid-source` check keeps passing and the popover has something to show.
9. As a maintainer, I want sources to prefer the defining RFC or the vendor/project's own documentation, plus the IANA service-name registry entry when one exists, so that sources are authoritative rather than arbitrary blog posts.
10. As a maintainer, I want every source URL to resolve (HTTP 200, or a redirect chain ending in 200) at authoring time, so that a source isn't dead the day it ships.
11. As a maintainer, I want the crowded-port blurb rule to stay intact — no entry's blurb contains its own name or alias — for every entry the rule already applies to (including across the Mixed union, per design spec 5.3), so that `missing-blurb` and `blurb-leaks-name` keep reporting zero issues.
12. As a maintainer, I want `id` and `port` untouched on every entry, so that the design spec's identity freeze (section 5.4) holds; I also want `aliases`, `transport`, `answerEligible`, and `retired` untouched, as a scope boundary this ticket sets for itself even though 5.4 already allows `aliases`/`transport` to change anytime — so that `pnpm gen:schedule --check` and every committed schedule stay valid and this ticket's diff stays content-only.
13. As a maintainer, I want no schedule file and no production code file touched, so that this ticket's diff is confined to the two catalog JSON files, this spec document, and the one narrow, disclosed test-file exception in story 16.
14. As a maintainer reviewing the PR, I want a table of every entry's id, its source labels, and a one-line note for anything factually uncertain, so that I can spot-check claims before merging without re-deriving them myself.
15. As a maintainer, I want the existing JSON formatting (tab indentation, key order) preserved and no entries reordered, so that the diff shows only content changes, not incidental reformatting.
16. As a maintainer, I want `src/ui/miss-popover.test.tsx` — which currently hardcodes FTP's literal `description` text and its source label/URL as test assertions, and hardcodes HTTP's literal description while relying on HTTP being the one production entry with no sources — updated so it derives FTP's expected description and source from the production catalog instead of a hardcoded string, and so its "no sources" case exercises the popover component directly against a fixture entry rather than assuming a production entry has none, so that rewriting FTP's and HTTP's descriptions (and giving every entry a source) doesn't break `pnpm test`, and so the test no longer needs updating on future content edits.

## Implementation Decisions

### Scope

- Both catalog files, all rows: 48 entries in `protocols.json` (40 answer-eligible, 8 miss-only: `echo`, `discard`, `daytime`, `chargen`, `whois`, `gopher`, `finger`, `ident`) and 26 in `applications.json` (25 answer-eligible, 1 miss-only: `mongo-express`). Every row gets a new `description` and a `sources` list; there is no "skip because it's miss-only" exception — the popover and reveal render for any identified entry regardless of `answerEligible`.
- Crowded, non-retired ports today: within `protocols.json` alone, none — every protocol port is unique. Within `applications.json` alone: port 3000 (`cra`, `next`, `nuxt`, `rails`, `grafana`), port 8080 (`webpack`, `jenkins`, `tomcat`), port 5173 (`vite`, `svelte`). But the blurb rule is also checked against the Mixed union (design spec 5.3: "Mixed inverted uses the selected Blitz category's catalog for crowding... For Mixed, crowding is union-wide"), and `catalog-load.test.ts` asserts `validateCatalog` on that union. Under the union, port 8080 has four non-retired entries — `http-alt` (protocols) plus `webpack`, `jenkins`, `tomcat` (applications) — so `http-alt` **is** subject to the blurb rule via Mixed-category crowding, not exempt from it; it already carries a valid blurb ("Common alternate web port.") that satisfies the rule today, and that blurb is left as-is unless its wording needs a factual fix.

### Description shape

- One or two sentences per entry. Plain, factual English (this ticket's own authored quality bar, not itself stated in issue #43 — see Further Notes: avoid marketing adjectives like "blazing fast", "industry-leading", "seamless").
- Must state what the service or software is and what it is used for. Add why it uses that port only when the reason is notable — a historical IANA assignment, a well-known framework convention, an "avoid the standard port" workaround — and omit that clause when there is nothing notable to say.
- The entry's own name may appear in the prose (for example "SSH (Secure Shell) is a protocol for..."), but a description must never be only the bare name, only an acronym expansion, or otherwise content-free — this replaces every current description of the form `"<Expansion>."` (for example "File Transfer Protocol.", "Telnet protocol.", "MySQL database protocol.") with something that adds real information.
- A `blurb` changes only when required to keep the crowded-port rule intact (a factual correction, or a newly-required blurb if crowding is discovered to have changed — it hasn't, per the audit above). Per design spec 5.3 and `blurbLeaks()` in `src/engine/catalog.ts`, a blurb must never contain that entry's own `name` or any of its `aliases` as a case-insensitive substring; the rule as coded does not check other entries' names. As an additional, disclosed author call beyond the coded rule (see Further Notes), a blurb should also avoid naming a *different* crowded entry sharing the same port, since that would functionally give away the answer to that entry's own puzzle even though validation would not catch it.

### Source rules

- At least one source per entry, per issue #43's acceptance criteria. `validateCatalog`'s `invalid-source` check (`src/engine/catalog.ts`) enforces the shape of each source present but imposes no minimum or maximum count on its own; the floor of one and the cap of three below are this ticket's own authored content policy, not something the check enforces (disclosed as an author call in Further Notes). Each source is `{ label: string, url: string }` — the schema already defined in `src/engine/types.ts`, unchanged by this ticket.
- Label: short and human — "RFC 5321", "PostgreSQL docs", "IANA port 5432" — not a raw URL or a sentence.
- URL: starts with `https://`. Prefer, in order: the defining RFC (`www.rfc-editor.org`) when one exists; otherwise the vendor's or project's own documentation; add the IANA service-name registry entry (`https://www.iana.org/assignments/service-names-port-numbers/service-names-port-numbers.xhtml`) as an additional source when the name/port pair has a registry entry worth citing. A source list may mix an RFC or vendor doc with an IANA source, up to three total.
- Every URL must resolve at authoring time: HTTP 200, or a redirect chain that ends in 200, checked with `curl -sSI -L -o /dev/null -w "%{http_code} %{url_effective}"`. A URL that 404s or times out is not shippable — find a working replacement rather than leaving it.

### Freeze and diff shape

- `id` and `port` are unchanged on every entry, on both files. `name` and `port` are "Forbidden" to change per design spec 5.4's identity-freeze table; `id` is separately guaranteed stable by 5.2's entry-schema note ("stable slug, unique globally, never reused"). Of the remaining fields, 5.4's "Anytime" row names only `description`, `aliases`, `blurb`, and `transport` as flavor that may change anytime; `answerEligible` and `retired` get their own row instead ("Flags may change, but the id stays in the order file... Same `gen:schedule` trigger as adding ids"), since flipping either can move an id in or out of a future schedule tail. This ticket leaves `aliases`, `transport`, `answerEligible`, and `retired` all untouched regardless — for `aliases`/`transport` that's a scope boundary this ticket sets for itself (5.4 would allow changing them); for `answerEligible`/`retired` it also avoids triggering `gen:schedule`'s tail-reshuffle behavior, which is out of scope here. This ticket's job is description and sources only.
- No schedule file (`src/catalogs/schedules/*.json`) changes — schedules reference entries by `id`, which does not move.
- No production code file changes — `validateCatalog`, its `missing-blurb` / `blurb-leaks-name` / `invalid-source` checks, and `src/ui/miss-popover.tsx` itself already implement everything this content needs; this ticket supplies content only, with one narrow, disclosed exception: `src/ui/miss-popover.test.tsx` hardcodes FTP's current literal description and source text and, for its "no sources" case, relies on HTTP being the one production entry without a source. Both assumptions break once every entry gets a description rewrite and a source, so this one test file is updated (see Testing Decisions and Further Notes) — no other test file, and no `src/engine/`, `src/persist/`, or `scripts/` file, changes.
- Existing JSON formatting (tab indentation, key order) is preserved. No entry is reordered within its file. The existing FTP entry's own key order is `id, name, port, transport, description, answerEligible, sources` — `sources` last, after `answerEligible` — and every entry that gains a `sources` list follows that same placement (last key) for consistency, rather than placing it right after `description`.

## Testing Decisions

This is a content ticket with no new code path, so there is no new test to write for new behavior. The existing validation seam is the proof the content is well-formed; a manual, local check proves every source resolves; and one existing test file needs updating because it hardcodes content this ticket rewrites.

- **Catalog validation seam** (existing, unchanged): `src/engine/catalog-load.test.ts`'s `"production catalogs meet floors and validation"` test calls `validateCatalog` on `protocols`, `applications`, and their `mixed` union and asserts an empty issue list — this is what makes a bad or missing source, or a blurb that leaks a name, fail `pnpm test`. `src/engine/catalog.test.ts` already unit-tests `validateCatalog`'s `invalid-source`, `missing-blurb`, and `blurb-leaks-name` rules directly against synthetic fixtures in `src/engine/test-fixtures.ts` (not the production catalogs); neither file is touched.
- **Miss popover App-seam test** (existing, updated — the one disclosed exception to "content-only"): `src/ui/miss-popover.test.tsx` renders the real `App` against the real production catalogs and today asserts FTP's literal current description text (`"File Transfer Protocol."`, 13 times) and its literal source label/URL (`"RFC 959"` / the RFC 959 URL), and separately asserts HTTP has no sources block, relying on HTTP being the one production entry without a source. Once this ticket rewrites every description and gives every entry a source, both assumptions break. The fix: look up the FTP entry from the imported `protocols.json` at the top of the test file and assert against its live `description` and first `sources[0]` (label and url) instead of literal strings, so the test tracks catalog content instead of hardcoding it and needing updates on future content edits; and change the "no sources" case to render `MissPopover` directly against a small fixture `CatalogEntry` with no `sources`, since after this ticket no production entry is in that state. No other test in this file changes, and no other test file is touched.
- **Schedule-generator check** (existing, unchanged): `pnpm gen:schedule --check` re-validates the catalogs and every committed schedule file against them; a passing run is evidence that content changes did not disturb any frozen identity.
- **Local URL check** (new, one-off, not part of CI or the build): a short script or curl loop run by hand over every `sources[].url` in both files, using `curl -sSI -L -o /dev/null -w "%{http_code} %{url_effective}\n"`, confirming each resolves to 200. Its output (pass/fail counts) is pasted into the PR body as evidence; it is not committed as a project script and does not run in `pnpm test` or CI.
- Proof of done: `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm gen:schedule --check`, and `pnpm build` all pass, plus the local URL check showing every source resolves, plus a diff confined to the two catalog files, `src/ui/miss-popover.test.tsx`, and this spec document.

## Out of Scope

- Any change to `validateCatalog`, the catalog schema (`src/engine/types.ts`), or the miss popover component itself (`src/ui/miss-popover.tsx`) — only its test file changes, and only as described in Testing Decisions.
- Any test file other than `src/ui/miss-popover.test.tsx`, and any change to that file beyond making its FTP assertions catalog-derived and its "no sources" case fixture-based.
- Any change to `id`, `name`, `port`, `aliases`, `transport`, `answerEligible`, or `retired` on any entry.
- Adding, removing, retiring, or reordering catalog entries.
- Any schedule file change.
- Adding a committed, repo-owned URL-check script — the check for this ticket is run locally and its output is pasted into the PR, not landed as tooling.
- Raising or changing the v1 content floors (≥40 answer-eligible protocols, ≥25 answer-eligible applications) — already met, unaffected by this ticket.

## Further Notes

- Primary sources: issue #43's body (acceptance criteria: one-or-two-sentence descriptions with no bare-name-only description; at least one source per entry with non-empty label and `https://` URL, preferring the defining RFC/vendor docs/IANA; blurb rule intact; `pnpm gen:schedule --check` passing since content is flavor; a review table in the PR); the v1 design spec (`docs/superpowers/specs/2026-09-08-portdle-design.md`) sections 5.2 (Entry schema), 5.3 (Blurb rule), 5.4 (Identity freeze); the UI redesign spec (`docs/superpowers/specs/2026-09-10-ui-redesign.md`) Catalog schema decision, which introduced `sources` and its `invalid-source` validation and explicitly deferred "populating sources across the catalogs" to "its own ticket" — this is that ticket.
- Glossary (`CONTEXT.md`): **Entry** (a named service with one port number — avoid "item", "record", "service row"), **Source** ("a curated reference link for an entry, such as an RFC, the IANA registry, or vendor docs" — avoid "link", "citation", "reference"), **Miss popover** (avoid "tooltip", "hint card", "hover card"). This spec also uses **Blurb**, which is not in CONTEXT.md's glossary — it is a schema-field term defined in the design spec (5.2's entry schema, 5.3's crowded-port rule). This spec reuses these terms and introduces none new.
- Product and architecture authority remains the v1 design spec and the UI redesign spec; this ticket is pure content authored against schema and validation both specs already settled.
- The PR's review table (id, source labels, a one-line note for anything factually uncertain — "—" when nothing is uncertain) is the acceptance evidence issue #43 itself asks for; it is pasted into the PR body, one row per entry, covering both files.
- Author calls not covered by the parent specs or issue #43, listed so they can be overruled: (1) miss-only entries (`echo`, `discard`, `daytime`, `chargen`, `whois`, `gopher`, `finger`, `ident`, `mongo-express`) are in scope for description and sources exactly like answer-eligible entries, since the miss popover and reveal do not distinguish by `answerEligible` when rendering an identified entry, and issue #43 says "every entry" without exception; (2) where an entry's canonical documentation is a Wikipedia-quality general reference rather than an RFC or vendor doc (rare, mostly for very old or informal protocols), the vendor/registry preference is relaxed to the best available authoritative page rather than leaving the entry under-sourced; (3) the IANA registry source is added only when it meaningfully corroborates the port/name pairing (i.e., the name is actually registered under that port), not mechanically on every row, to avoid three low-value sources on simple entries; (4) a hard cap of three sources per entry — issue #43 states only a floor ("at least one source"), no ceiling; three is chosen so the popover, at 16rem wide, doesn't get crowded with low-value sources; (5) "plain, factual English, no marketing adjectives" as the tone bar for descriptions — issue #43 doesn't state a tone requirement explicitly, but its Problem Statement's complaint (vague, information-free descriptions) and CONTEXT.md's framing of the game as a reference-like tool both support it; (6) a blurb should also avoid naming a *different* crowded entry at the same port, beyond the own-name/alias check `blurbLeaks()` actually performs — a stricter, disclosed addition in the same spirit as design spec 5.3, not itself required by the coded rule or by issue #43.
- Coordinator-approved exception to "content-only, no code or test files": `src/ui/miss-popover.test.tsx` hardcodes FTP's current literal description and source text, and separately relies on HTTP being the one production entry with no sources, for its "no sources" test case. This was surfaced as a blocking conflict during spec review (rewriting FTP's and HTTP's content as issue #43 requires would otherwise break `pnpm test`, but this ticket's ownership is content-only). The coordinator resolved it: rewrite FTP's description like every other entry, and widen this ticket's ownership to `src/ui/miss-popover.test.tsx` alone, for the sole purpose of making its assertions derive from the production catalog (FTP's description and first source) rather than hardcoding them, with the "no sources" case restructured to render the popover against a fixture entry instead of a production one. No other code or test file is in scope under this exception.
