# Ticket spec: Fixture shape check

Spec for #228. Tracker: https://github.com/mquesada02/portdle/issues/228. Parent: Spec 6 (tests, CI, and motion), https://github.com/mquesada02/portdle/issues/222 (`docs/superpowers/specs/2026-10-04-spec6-tests-ci-motion.md`, "Screenshot gate: data" and user story 16). Map: https://github.com/mquesada02/portdle/issues/212. Decision: #216 (fixed data). Base branch: `master`. Blocked by: #227 (merged, PR #240).

## Problem Statement

The screenshot gate answers every REST (Representational State Transfer) read from committed fixtures. When the real response changes (a column is added, renamed, or changes type), the fixture is silently wrong. The frames then show data that the real app can never receive, and nothing fails.

## Solution

A shape check reads each stubbed REST endpoint from the local stack and compares the keys and the value types (never the values) with the committed fixture. It runs in the `sql-tests` job of CI (continuous integration), which already starts the stack. A difference fails the job and names the endpoint, the key, and both types.

## User Stories

1. As an agent, I want CI to fail when a fixture lacks a key that the real response has, so that a new column shows up in the gate data.
2. As an agent, I want CI to fail when a fixture has a key that the real response lacks, so that a removed or renamed column does not stay in the gate data.
3. As an agent, I want CI to fail when a fixture value has another type than the real value, so that a type change is seen.
4. As an agent, I want the failure message to name the endpoint, the key, and the two types, so that I fix the right fixture without a debugger.
5. As a developer, I want one command, `pnpm check:fixtures`, so that I run locally what CI runs.
6. As a developer, I want the check to cover all four stubbed endpoints (`rpc/current_dailies`, `catalog_entries`, `schedule`, `daily_global_stats`), so that no stub is unchecked.
7. As a developer, I want the check to fail with a clear message when the local stack does not answer, or answers with an error status, so that I know to run `pnpm dev` and `pnpm dev:schedule`.
8. As a reviewer, I want the check to run on every pull request, docs-only pull requests included, so that the check never skips.
9. As the owner, I want proof that breaking one fixture by hand fails the check, checked once and not committed.

## Implementation Decisions

- **Files**: `scripts/fixture-shapes.ts` (pure functions: the shape of a list of rows, the shape of an OpenAPI definition, and the comparison), `scripts/fixture-shapes.test.ts` (Vitest tests of those functions), and `scripts/check-fixture-shapes.ts` (the runner). `package.json` gets the script `check:fixtures`. `tsconfig.node.json` lists `scripts/check-fixture-shapes.ts` and `scripts/fixture-shapes.ts` (as it lists `scripts/e2e.ts` and `scripts/e2e-env.ts`). The test file is not listed, like the other script tests, and Vitest runs it.
- **Stack access**: the runner reads the API (Application Programming Interface) URL and the publishable key with `supabase status -o env` and `parseStackEnv`, as `scripts/e2e.ts` does. It never starts, stops, or changes the stack. It only sends reads. When the status command fails, or an endpoint answers with a status other than 2xx, the runner stops with its own message that names `pnpm dev` and `pnpm dev:schedule` (the message of `scripts/e2e-env.ts` names `pnpm test:e2e`, so it is not reused). Every read sends the publishable key as `apikey` and as `Authorization: Bearer`.
- **Reads**: the runner sends the request that `src/remote/supabase.ts` sends, without the paging parameters (`limit` and `offset`), which the shape does not need. The local `max_rows` is 1000, which covers the 74 catalog rows.
  - `current_dailies`: `POST rpc/current_dailies` (a Remote Procedure Call: a database function) with body `{}` and the header `Content-Type: application/json`.
  - `catalog_entries`: `GET catalog_entries?select=*&order=id`.
  - `schedule`: `GET schedule?select=category,day,entry_id&order=day,category`.
  - `daily_global_stats`: see the next point.
- **The Global stats view has no rows on a fresh stack**: the view counts finished `dailies`, and CI has none. A row read cannot compare a view with no rows, so the runner uses the schema for it.
  - It reads the OpenAPI (a machine-readable description of the API) document at `GET /rest/v1/`. PostgREST (the REST server of the stack) serves it.
  - It takes the columns of `definitions.daily_global_stats.properties` and compares them with the fixture.
  - It fails with a message when the document or that definition is absent, and when a property has a type that the mapping below does not list.
- **The other three endpoints have rows in CI**: the catalog comes from the migration import, the Schedule from `pnpm dev:schedule`, and the Dailies from the Schedule. A row read that returns no rows fails the check with a message, because it cannot prove a shape.
- **Fixtures**: the runner reads `gate/fixtures/current-dailies.json`, `catalog.json`, `schedule.json`, and `daily-global-stats.json`. Each must hold a JSON array of rows, or the runner fails with a message. It does not change them and does not import `gate/stub.ts` (the stub keeps its reader private, and the ticket does not own that file).
- **Shape of a list of rows**: for each key, the set of JSON types of the non-null values over all rows: `string`, `number`, `boolean`, `array`, or `object`. The types are the top-level types only. A key that holds only `null` has an empty set.
- **Shape of an OpenAPI definition**: for each property, `string` for `string`, `number` for `integer` and `number`, `boolean`, `array`, and `object`; a property with no `type` (a `jsonb` column, the JSON column type of Postgres) has an empty set. Any other type fails the check.
- **Comparison**: the two key sets must be equal. For each key, the two type sets must be equal, unless one set is empty (a column that is `null` in every row on one side, or `jsonb` in the schema, says nothing about the type). Values are never compared.
- **Report**: the runner checks every endpoint, prints one line per difference (`<endpoint>: <key>: fixture <types>, backend <types>`, or `<endpoint>: <key> is missing in the fixture` / `in the backend`), and exits with code 1 when any difference exists. It prints one `ok` line per endpoint that matches.
- **CI**: one new step in the `sql-tests` job, `pnpm check:fixtures`, after `pnpm dev:schedule` and before `scripts/run-sql-tests.sh`. The job has no docs-only skip today, so the step runs on every pull request. This ticket changes no other job and does not touch the screenshot jobs.

## Testing Decisions

- A good test checks the comparison, not the stack. Vitest tests of the pure module: equal shapes pass; a missing key, an extra key, and a changed type each fail with the right message; a `null` value or an empty type set does not fail; an array of rows with mixed `null` and `string` values has the type `string`; an OpenAPI definition maps `integer` to `number` and a typeless property to the empty set.
- The runner is checked against the local stack: `pnpm check:fixtures` passes now. Once, and not committed: add a key to one fixture, then change the type of one value in another; each makes the command fail with the expected line. The pull request records both results.
- `pnpm lint`, `pnpm typecheck`, `pnpm test`, and `pnpm build` pass. The `sql-tests` job passes on the pull request with the new step.
- Prior art: `scripts/e2e-env.ts` and its test (a runner helper split from its runner), and `scripts/stack-env.ts`.

## Out of Scope

- The auth storage format (Spec 6 names it as not covered).
- Stubs that later tickets add (signed-in, Account, Sync, Leaderboard): the ticket that adds a stub adds its endpoint to the check.
- Nested shapes (the elements of `sources` or `aliases`) and values.
- A change to any fixture, unless the check proves one wrong.
- The screenshot jobs, the other `ci.yml` jobs, and the docs-only skip rule.

## Further Notes

### Author calls

The owner accepted all six calls on 2026-10-05.

1. **The view is checked from the OpenAPI document, the other three from rows.** Cost: two code paths. The alternative (rows for all four) fails in CI, because the view is empty there. The alternative of seeding a `dailies` row writes to the shared stack, which the rules forbid.
2. **The comparison is two-way (an extra fixture key fails too).** The ticket and Spec 6 name only the missing key and the changed type. An extra key means the column was removed or renamed, which is the same drift.
3. **Top-level types only, with `null` ignored.** A nested check needs a schema language and the ticket asks for keys and value types. The cost: a change inside `sources` is not seen, and a column that is `null` in every real row (or typeless `jsonb`) hides a type change.
4. **Names**: a `check-` prefix for the runner and the script (`check:fixtures`), because the check reads and does not build or run the gate. The pure module is `fixture-shapes.ts`.
5. **The runner reads the fixture files itself** and does not export the reader from `gate/stub.ts`, to keep the shared gate files untouched.
6. **The step goes after `pnpm dev:schedule`**, because the Schedule and the Dailies need its rows.

### Facts checked

- On 2026-10-05, on the local stack, `GET /rest/v1/` with the publishable key returns the OpenAPI document. `definitions.daily_global_stats.properties` holds the 11 columns of the fixture: `category` and `day` as `string`, and nine `integer` counts. `catalog_entries.sources` has no `type` (`jsonb`), and `aliases` is `array`.
- The three row reads return rows, and the shapes equal the committed fixtures today.
- The local `max_rows` is 1000 (`supabase/config.toml`).
