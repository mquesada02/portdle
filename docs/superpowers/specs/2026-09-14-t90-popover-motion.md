# Spec: Miss popover open and close motion

Spec for #90. Tracker: https://github.com/mquesada02/portdle/issues/90. Parent: Spec 3 (Motion polish), #87.

## Problem Statement

Today the miss popover — the panel on a Daily miss identification or a seen Codex card — appears and disappears in a single frame: `MissPopover` (`src/ui/miss-popover.tsx`) renders its panel with a plain `{open ? <span>...</span> : null}`, so React mounts and unmounts it the instant the derived `open` boolean (`pinned || hovered || (focusOpens && focused)`) flips. Every other piece of motion this game already has — the tile pop, the row shake, the reveal's divider draw and delayed rise — animates; the popover is the one interactive surface that still cuts.

## Solution

The panel fades and scales in from its trigger when it opens, and fades out before it actually leaves the DOM when it closes, so Escape, an outside click, a second click, the pointer leaving, or focus leaving all still feel immediate while the close no longer cuts off mid-motion. `MissPopover` gains one small local phase state — entering, open, or exiting — layered on top of its existing `pinned`/`hovered`/`focused` state and derived `open` boolean, which neither of those changes. Two new keyframe classes in the global stylesheet drive the visuals; no new library, no transitions (both motions are keyframe animations, matching the ticket's "listens for the animation-end event only while closing" requirement). Under reduced motion, the close skips the fade entirely and unmounts at once, exactly as it does today.

## User Stories

1. As a Daily player, I want the miss popover to fade and scale in from its trigger when it opens, so that it reads as attached to the miss I tapped.
2. As a Codex reader, I want a seen card's popover to open with the same motion, so that the popover feels the same on every surface.
3. As a player, I want the popover to fade out whenever it closes — Escape, an outside click, a second click, the pointer leaving and the grace timer elapsing, or focus leaving — so that it never vanishes in one frame.
4. As a player, I want the popover's close to still feel immediate even though it fades, so that Escape never feels laggy.
5. As a keyboard player, I want the popover's open and close motion to change nothing about focus, pinning, hover, or Escape, so that the existing behavior is untouched.
6. As a player, I want the popover's transform origin to sit at the top edge on the side it's anchored to (centered below the small breakpoint and right-aligned above it inline; left-aligned in the grid, or right-aligned in the grid's last column), so that the scale-in reads as growing out of the trigger rather than the page corner.
7. As a player who reopens the trigger while the popover is still fading out, I want the panel to snap back to fully open at once with no replayed enter animation, so that fast hovering in and out doesn't stutter.
8. As a player who closes the popover while it's still fading in, I want the close to cut the open motion short and fade out from full opacity, so that a fast tap-and-dismiss never looks stuck mid-animation.
9. As a player who has asked my system to reduce motion, I want the popover's close to skip the fade and unmount immediately, exactly as it does today, so that the app respects my setting as it already does for the board and the reveal's scroll.
10. As a screen reader user, I want the closing popover to be inert and to accept no pointer events, so that nothing inside a panel that's on its way out can be focused, clicked, or announced.
11. As a maintainer, I want the six existing miss-popover tests and the Codex seen-card test that assert synchronous removal to keep passing by waiting for the removal (or advancing the clock where they already run on fake timers), so the close's new asynchrony doesn't break coverage that only ever cared about the end state.
12. As a maintainer, I want a test proving a reopen during the exit cancels it and keeps the panel shown, so the cancel-on-reopen behavior is protected against regression.
13. As a maintainer, I want a test proving Escape unmounts the popover synchronously under reduced motion, so the reduced-motion bypass is protected against regression.

## Implementation Decisions

- **Phase state.** `MissPopover` (`src/ui/miss-popover.tsx`) gains one new piece of local state, `phase: "entering" | "open" | "exiting" | null`, initialized to `null`, alongside the existing `pinned`, `hovered`, and `focused` state. It does not replace or change the meaning of the derived `open` boolean, `aria-expanded`, `aria-controls`, or any pin/hover/focus/Escape/outside-click logic — those are unchanged. The panel renders whenever `phase !== null` (today it renders only `if (open)`), and holds a `useRef<HTMLSpanElement>` on that panel element (the same ref pattern the component already uses for `leaveTimer`), so the exit effect below can attach its `animationend` listener directly to the node.
- **Driving the phase from `open`.** One effect keyed on `[open]` drives entry and exit:
  - `open` becomes `true`: phase becomes `"entering"` if it was `null` (a fresh open — plays the enter keyframe), or `"open"` if it was `"exiting"` (a reopen during the exit — cancels it, returns to the fully-open static look at once, does not replay the enter keyframe). This is the "reopening during the exit" behavior; nothing else needs to change for it, because the fallback timer and the animation-end listener both live in the second effect below, keyed on `phase`, and its cleanup tears them down the moment `phase` stops being `"exiting"`.
  - `open` becomes `false`: a no-op if `phase` is already `null` (nothing open) or `"exiting"` (a further close cause while already closing changes nothing). Otherwise (`"entering"` or `"open"`), the media query is read the same way `daily-reveal.tsx` already reads `(prefers-reduced-motion: reduce)`: if it matches, `phase` goes straight to `null` (instant unmount, no closing state — today's behavior, and the Miss popover decision's reduced-motion bullet); otherwise `phase` becomes `"exiting"`.
  - A close that lands while `phase` is `"entering"` (the open animation still playing) is handled by this same branch — it goes straight to `"exiting"`. No extra bookkeeping is needed for "cuts it short and starts the exit from full opacity with the scale snapping to 100%": swapping the CSS class from the enter animation to the exit animation is what does it (see the keyframe decision below).
- **Exit timing.** A second effect, keyed on `[phase]` and active only while `phase === "exiting"`, starts an 80ms `window.setTimeout` fallback and adds an `animationend` listener on the panel's own DOM node (the component "listens for the animation-end event only while closing"); whichever fires first sets `phase` back to `null` (unmount) and the effect's cleanup — which also runs the instant `phase` changes away from `"exiting"`, i.e. on a reopen — clears the timer and removes the listener. This is the concrete shape of the ticket's "tears down the fallback timer and the listener" on a reopen.
- **Keyframes** (`src/styles.css`, appended as one clearly delimited block — a header comment naming the ticket — directly above the existing `@media (prefers-reduced-motion: reduce)` rule, matching the file's existing `pop`/`shake`/`draw`/`rise` pattern):
  - `popover-in`: `opacity` 0 to 1 and the standalone `scale` property 95% to 100%, 120ms, `ease-out`. New class `.animate-popover-in { animation: popover-in 120ms ease-out both; }`, applied while `phase === "entering"`. Animating `scale` rather than `transform: scale(...)` is what lets it compose independently with the standalone `translate` the inline placement's centering below the small breakpoint already uses (Tailwind 4 emits `scale` and `translate` as independent CSS properties).
  - `popover-out`: `opacity` 1 to 0 only, 80ms, `ease-out`. New class `.animate-popover-out { animation: popover-out 80ms ease-out both; }`, applied while `phase === "exiting"`. Because this keyframe never touches `scale`, `scale` simply falls back to its unanimated 100% resting value whenever this class is in effect — including the moment it replaces `.animate-popover-in` mid-enter — which is what gives "scale snapping to 100%" with no JS of its own. Because its `0%` frame is `opacity: 1`, swapping directly from the enter class also gives "starts from full opacity" for free, with no special-casing of the cut-short case.
  - `phase === "open"` is reached only by a reopen that cancels an exit (the "`open` becomes `true`" branch above); it gets neither class, so no animation is running, and the panel's ordinary resting styles (nothing sets `opacity` or `scale` outside these two animations) already read as fully visible and unscaled — which is what the ticket's "does not replay the enter animation" requires. A popover that is opened and never closed stays in `phase === "entering"` for as long as it's open: nothing transitions it to `"open"`, because — per Spec 3's Miss popover decision — "the component listens for the animation-end event only while closing, since the open needs no follow-up", so there is deliberately no listener that would flip `"entering"` to `"open"` once the 120ms enter animation finishes. This is harmless: `.animate-popover-in`'s `both` fill mode holds its final frame (`opacity: 1`, `scale: 100%`) indefinitely, the same way `.animate-pop`/`.animate-rise` never have their classes removed either, and the class isn't toggled off and on again, so nothing replays.
- **Transform origin,** expressed as Tailwind `origin-*` utilities alongside the existing `positionClasses` computation: for `placement="inline"`, `origin-top` below the small breakpoint and `origin-top-right` at and above it (mirroring `positionClasses`'s own breakpoint split there); for `placement="grid"`, `origin-top-left`, or `origin-top-right` when `lastColumn`.
- **Inert and no pointer events while exiting.** While `phase === "exiting"`, the panel gets the `pointer-events-none` Tailwind class and the native `inert` boolean attribute (React 19 passes it straight through as a real DOM attribute), matching the ticket's "the closing panel accepts no pointer events and is inert" bullet word for word. Neither is read anywhere else in the component; the panel's own `onMouseEnter`/`onMouseLeave` handlers stay wired exactly as today (they simply won't fire while the node is inert).
- **Test helper.** `stubMatchMedia` (`src/test/helpers.ts`) gains a second, optional, positional parameter `prefersReducedMotion = false`, mirroring the existing `prefersDark` one exactly: `matches` becomes `true` when either the dark-scheme query is asked and `prefersDark`, or the reduced-motion query is asked and `prefersReducedMotion`. This is the smallest addition that answers `(prefers-reduced-motion: reduce)` from an option the way the function already answers the dark-scheme query; every existing call site (ten other test files) keeps working unchanged since the new parameter is optional and positional after the existing one.
- Nothing else in `miss-popover.tsx` changes: the trigger element, `MissPopoverTriggerProps`, the pin/hover/focus/Escape/outside-click effects, the panel's content, and its non-motion styling are all untouched.

## Testing Decisions

A good test here exercises a public seam and asserts what a player sees — role, accessible name, or visible text — never CSS, class names, or the phase state itself; how the motion looks is checked by eye, per Spec 3's Testing Decisions section, not by these tests. Expected strings are literals already used by the existing suites.

1. **App seam** (`src/ui/miss-popover.test.tsx`, `src/ui/codex-page.test.tsx`; prior art: both files already render `<App>` with a memory store, a memory history, and an injected UTC day).
   - Five of the six existing `miss-popover.test.tsx` tests that assert synchronous removal are edited to accommodate the close now staying mounted through its 80ms exit:
     - "moving off and letting the grace timer elapse closes the popover" already runs on fake timers (`vi.useFakeTimers()`); it gets one more `await act(async () => { await vi.advanceTimersByTimeAsync(80); })` immediately after its existing 150ms advance, before the final `queryByText(...)).toBeNull()` assertion.
     - "clicking the trigger toggles a pinned-open state that persists independent of hover" also runs on fake timers; nothing changes about its existing 150ms advance (the popover stays pinned open through it). The new `await act(async () => { await vi.advanceTimersByTimeAsync(80); })` goes after the test's second `fireEvent.click(trigger)` (the click that unpins and starts the close) and before the final `queryByText(...)).toBeNull()` assertion — not after the earlier 150ms advance, since nothing starts exiting until that second click.
     - "focusing the trigger with the keyboard opens the popover and blur closes it", "Escape closes an open popover", and "a pointer-down outside the trigger and panel closes it" run on real timers; each replaces its final synchronous `expect(screen.queryByText(ftpDescription)).toBeNull()` with `await waitForElementToBeRemoved(() => screen.queryByText(ftpDescription))` from `@testing-library/react`.
   - The existing `codex-page.test.tsx` test "clicking a seen card opens a note with its description and sources; Enter opens it and Escape closes it" closes the popover twice (a second click, then Escape); both `expect(screen.queryByRole("note")).toBeNull()` assertions become `await waitForElementToBeRemoved(() => screen.queryByRole("note"))`.
   - New, in `miss-popover.test.tsx`: "reopening the popover while it's closing cancels the exit and keeps it shown" — open the popover (hover), start a close (Escape), then immediately hover the trigger again before the 80ms exit elapses, and assert the description text is still present with no wait — proving the cancel-on-reopen path without needing to await anything, since the panel never actually leaves.
   - New, in `miss-popover.test.tsx`: "under reduced motion, Escape removes the popover at once" — call `stubMatchMedia(false, true)` (the new reduced-motion switch) after opening the popover but before closing it, then fire Escape and assert the description is gone with no wait, proving the reduced-motion bypass skips the exiting phase entirely.
   - Every other existing test in both files (the ones that only open the popover, or that assert content/positioning rather than a close) is unchanged.
2. **Component-level, direct render** (`src/ui/miss-popover.test.tsx`; prior art: the file's existing "an entry with no sources shows no sources block" and "grid placement..." tests, which already render `<MissPopover>` directly with a fixture entry rather than through `<App>`, per t74's spec).
   - "grid placement with a custom trigger drops focus-opens; Enter toggles it and Escape closes it" is the sixth of the ticket's six existing tests that assert synchronous removal; unlike the App-seam tests above, it never calls `renderDaily()`, so nothing has stubbed `window.matchMedia` for it. Because a close now reads that media query (the `open` becomes `false` transition, Implementation Decisions), this test gains an explicit `stubMatchMedia()` call (no arguments, matching the App-seam tests' default) right after its `render(...)` call, so it doesn't depend on a same-file, run-order accident of an earlier test's stub leaking into it. Its final synchronous `expect(screen.queryByText(entry.description)).toBeNull()` becomes `await waitForElementToBeRemoved(() => screen.queryByText(entry.description))`, same as the App-seam real-timer tests above.
   - "an entry with no sources shows no sources block" only opens the popover and never closes it, so it needs no edit.

No snapshot tests, no visual regression, no Playwright, and no new fake-timer use beyond the two existing fake-timer tests' extra advance — matching Spec 3's "the seam tests to keep passing with no new fake-timer use" maintainer story. This ticket is proven done by `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm gen:schedule --check`, and `pnpm build` all passing, plus the coverage above.

## Out of Scope

- View transitions for screen, switcher, or Blitz-phase changes, and the Codex reorder glide — ticket #89 and the rest of Spec 3.
- Dialog and disclosure motion, and the nav/switcher/sort-toggle color transitions — ticket #91.
- Any change to the popover's content, its pin/hover/focus/Escape/outside-click state model, its positioning breakpoints, `MissPopoverTriggerProps`, or any non-motion styling.
- Any change to the reduced-motion CSS rule (`@media (prefers-reduced-motion: reduce)`) itself — the popover's reduced-motion behavior is handled in JS, reading the media query directly, exactly as `daily-reveal.tsx` already does; the CSS rule is shared with tickets #89/#91 and is left alone here.
- Adding `waitForElementToBeRemoved`-style waits to any test outside the six named in the ticket plus the Codex seen-card test.
