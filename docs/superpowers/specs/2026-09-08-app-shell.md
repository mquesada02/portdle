# Spec: App shell

Spec for #1. Tracker: https://github.com/mquesada02/portdle/issues/8

## Problem Statement

A player opening Portdle today finds no app they can run in the browser. There is a product spec but no Vite SPA, no navigation between Daily categories and the other v1 surfaces, no theme, and no How-to. They cannot yet play a Daily or Blitz; they should still be able to land on the site, move between Mixed, Protocols, Applications, Blitz, History, and Help, choose light or dark, and read the rules.

## Solution

Portdle ships as a static SPA the player can open in the browser. A persistent shell shows English nav (Mixed · Protocols · Applications · Blitz · History · Help) and a theme control. First visit on any route shows a How-to dialog; dismissing it is remembered in this browser. `/help` always shows the same rules. Theme follows the system until the player clicks, then light ↔ dark persists. Route pages are placeholders (one `h1` each). There is no puzzle, catalog, or engine yet.

## User Stories

1. As a player, I want to open Portdle in the browser, so that I can use the game without installing anything.
2. As a player, I want the app to load under the `/portdle/` base path, so that GitHub Pages hosting works.
3. As a player, I want to see a nav of Mixed, Protocols, Applications, Blitz, History, and Help, so that I know which surfaces exist.
4. As a player, I want Mixed to be the landing route, so that the default Daily category is the first thing I reach.
5. As a player, I want a Protocols route, so that I can later play that Daily category.
6. As a player, I want an Applications route, so that I can later play that Daily category.
7. As a player, I want a Blitz route, so that I can later start a timed run.
8. As a player, I want a History route, so that I can later review past Dailies.
9. As a player, I want a Help route, so that I can re-read the rules after the first visit.
10. As a player, I want each route to have a clear English heading, so that I know which surface I am on even before puzzles exist.
11. As a player visiting for the first time, I want a How-to dialog on whatever route I landed on, so that I learn the rules without hunting for Help.
12. As a player who landed on Help on a first visit, I want the How-to dialog as well as the Help page, so that first-visit teaching is consistent on every route.
13. As a player, I want to dismiss How-to with a control named "Got it", so that I can reach the rest of the app.
14. As a player who dismissed How-to, I want it not to appear again in this browser, so that returning visits are not blocked by the same dialog.
15. As a player who already dismissed How-to, I want Help to still show the same rules, so that I can re-read them later.
16. As a player on a later visit, I want How-to to stay dismissed if this browser already recorded that I saw it, so that refresh does not reset teaching.
17. As a first-time player, I want theme to follow my system light or dark preference, so that the app matches the rest of my device until I choose.
18. As a player, I want a theme control with an accessible name, so that I can switch appearance without guessing what the control does.
19. As a player who has not yet clicked theme, I want the stored preference to remain `system`, so that OS changes still apply.
20. As a player, I want the first click on the theme control to leave `system` and persist an explicit `light` or `dark` choice, so that my choice survives reload.
21. As a player whose stored theme is `light`, I want a click to persist `dark`, so that I can switch to dark.
22. As a player whose stored theme is `dark`, I want a click to persist `light`, so that I can switch to light.
23. As a player whose stored theme is still `system`, I want a click to persist `light` (the same as a click from `dark`), so that leaving `system` has one deterministic rule.
24. As a player, I want no control that returns theme to `system`, so that v1 stays a single toggle.
25. As a player with an explicit `dark` preference, I want the document to use a `dark` class on `html`, so that dark styles apply.
26. As a player with stored `system` and an OS dark preference, I want the document to use a `dark` class on `html`, so that the app follows the system.
27. As a player with stored `light` or with stored `system` and an OS light preference, I want `html` not to have `dark`, so that light styles apply.
28. As a player, I want my theme choice remembered in this browser, so that I do not re-toggle every visit.
29. As a player, I want How-to dismissal remembered in this browser, so that I do not dismiss it every visit.
30. As a keyboard-only player, I want to Tab to nav links, so that I can change routes without a pointer.
31. As a keyboard-only player, I want to Tab to the theme control and activate it, so that I can change appearance without a pointer.
32. As a keyboard-only player, I want to Tab to How-to's dismiss control and activate it, so that I can clear the first-visit dialog without a pointer.
33. As a keyboard-only player, I want to reach Help via nav, so that I can open the rules without a pointer.
34. As a player, I want all of this UI in English, so that copy matches v1 (no extra locales).
35. As a player who prefers reduced motion, I want non-essential transitions disabled, so that the shell does not animate against my OS setting.
36. As a player, I want a quiet, Wordle-cousin chrome (light and dark), so that the shell does not compete with a future puzzle board.
37. As a player, I want each screen to have one `h1`, so that the page has a single main heading.
38. As a player, I want How-to to be a dialog with an accessible name, not a second page `h1`, so that heading structure stays one `h1` per screen.
39. As a player whose browser cannot write local storage, I want a non-blocking "Progress may not save." message, so that I know dismissal or theme may not stick, without being locked out.
40. As a player whose theme or How-to storage is corrupt JSON, I want that key ignored (theme falls back to `system`; How-to treated as unseen), so that one bad key does not break the app.
41. As a player who deep-links to `/protocols`, `/applications`, `/blitz`, `/history`, or `/help`, I want that surface's placeholder to render under the same shell, so that URLs are shareable.
42. As a player, I do not want a Daily board, digit slots, or catalog names on these placeholders, so that this ticket does not pretend puzzles exist yet.
43. As a player, I do not want Blitz setup or a timed run on `/blitz`, so that Blitz gameplay stays a later ticket.
44. As a player, I do not want History rows of past answers yet, so that History stays a later ticket.
45. As a maintainer, I want pnpm with a pinned `packageManager` and strict peer dependencies, so that installs are reproducible.
46. As a maintainer, I want TypeScript `strict` plus `noUncheckedIndexedAccess`, so that indexed access is honest.
47. As a maintainer, I want Biome for lint and format (unused and `any` are errors; imports organized), so that style is mechanical.
48. As a maintainer, I want Vite + React + Tailwind v4, so that the stack matches the v1 spec.
49. As a maintainer, I want TanStack Router with path URLs and `basepath: '/portdle'`, so that routes match GitHub Pages.
50. As a maintainer, I want `pnpm dev`, `pnpm build`, `pnpm preview`, `pnpm lint`, `pnpm format`, `pnpm test`, and `pnpm typecheck`, so that local workflows exist without schedule generation or CI yet.
51. As a maintainer, I want an MIT license and package description “Wordle-like daily game for network ports.”, so that the app metadata matches the v1 spec.
52. As a player, I want no cookies, analytics, accounts, or network besides static assets, so that v1 stays a local static SPA.

## Implementation Decisions

- New static SPA: Vite, React, TypeScript, Tailwind v4, Biome, pnpm. `packageManager` is pinned; peer dependencies are strict. TypeScript uses `strict` and `noUncheckedIndexedAccess`. Biome lint + format; unused locals and `any` are errors; organize imports. Package `name` is `portdle`; `description` is “Wordle-like daily game for network ports.”; `repository` is `https://github.com/mquesada02/portdle`; license MIT (copyright 2026).
- Vite `base` is `/portdle/`. TanStack Router is code-based with `basepath: '/portdle'`. Routes and their placeholder `h1` text:

  | Path | `h1` |
  |---|---|
  | `/` | Mixed |
  | `/protocols` | Protocols |
  | `/applications` | Applications |
  | `/blitz` | Blitz |
  | `/history` | History |
  | `/help` | Help |

- Shell wraps every route: nav links labelled Mixed · Protocols · Applications · Blitz · History · Help, plus a theme control whose accessible name is `Toggle color theme`. No UI kit and no state library. English copy only. Visual tone: quiet Wordle-cousin chrome; `prefers-reduced-motion` disables non-essential transitions. One `h1` per screen (the placeholder heading). How-to is a `dialog` with an accessible name, not a second `h1`.
- Persist is a small adapter over an injected store (browser uses `localStorage`). Only two keys this ticket, prefix `portdle:v1:`:

  | Key | Value |
  |---|---|
  | `portdle:v1:theme` | `system` \| `light` \| `dark` (default `system`) |
  | `portdle:v1:howToSeen` | boolean |

  Public shape (injected store, so tests do not touch `window.localStorage`):

  ```ts
  type MemoryStore = {
    getItem(key: string): string | null;
    setItem(key: string, value: string): void;
  };

  type Theme = "system" | "light" | "dark";

  createPersist(store: MemoryStore): {
    readTheme(): Theme;
    writeTheme(value: Theme): { ok: true } | { ok: false };
    readHowToSeen(): boolean;
    writeHowToSeen(): { ok: true } | { ok: false };
  };
  ```

  Corrupt JSON for one key is ignored (that key only). `readTheme` missing/corrupt → `"system"`. `readHowToSeen` missing/corrupt → `false`. `setItem` throw → `{ ok: false }`. No Daily, stats, lastPlayed, blitzBests, or lastSeenUtc keys. No `engine/` module.

- Theme: stored `system` until the player clicks. Effective theme is the stored `light`/`dark`, or `prefers-color-scheme` when stored `system`. Apply `html` class `dark` when effective theme is dark. Click rule: if stored is `light`, write `dark`; otherwise (`system` or `dark`) write `light`. No control returns to `system`.
- How-to: on first visit ( `readHowToSeen()` is false) of any route, open a dialog. Copy (English):

  - Guess the port for the named service.
  - Digit slots show how many digits.
  - 6 tries. A miss names the port if it is in this catalog.
  - Three Dailies: Mixed, Protocols, Applications.
  - Blitz is a separate timed mode.

  Dismiss control: `Got it`. Dismiss calls `writeHowToSeen()`. `/help` always shows the same rules as page content. After `howToSeen` is true, the dialog does not auto-open.
- If `writeTheme` or `writeHowToSeen` returns `{ ok: false }`, show a non-blocking “Progress may not save.” The app stays usable.
- Scripts this ticket: `dev`, `build`, `preview`, `lint`, `format`, `test`, `test:watch`, `typecheck`. No `gen:schedule`. No GitHub Actions. No Playwright. No `404.html` copy (Pages ticket). Placeholder routes must not render Daily boards, Blitz runs, catalogs, or History rows.

## Testing Decisions

A good test checks observable behavior through a public interface. It does not inspect private helpers, mock internal collaborators, or recompute the expected value the way the production code does. Expected values are literals from this spec (key names, `"system"`, `"Got it"`, `h1` text).

Two seams only:

1. **Persist** — `createPersist(injected MemoryStore)`. Cover: theme default `system`; theme round-trip `light`/`dark`; How-to unseen by default; `writeHowToSeen` then `readHowToSeen` is true; corrupt JSON for a key is ignored without affecting the other key; `setItem` throw returns `{ ok: false }`. Do not test Daily/stats/Blitz keys. Do not use `window.localStorage` in unit tests.

2. **UI (How-to + theme + shell)** — Vitest + Testing Library + jsdom, no Playwright. Cover: first visit shows How-to; dismiss via `Got it` writes How-to seen (assert through persist, not a boolean the test itself mutates unless that boolean is the persist write); after seen, How-to does not auto-open; Help still shows the rules; theme control is a named button the keyboard can activate; a click from `system` persists `light` and a click from `light` persists `dark`; `html.dark` follows effective theme; nav links for Mixed, Protocols, Applications, Blitz, History, and Help exist and are focusable. Placeholder `h1`s exist. Do not assert file structure, CSS class names except `html.dark`, or gameplay.

Scaffold is proven by `pnpm test`, `pnpm lint`, `pnpm typecheck`, and `pnpm build` succeeding — not by a tautological `1 + 1` smoke test unless that is the first red of scaffolding.

There is no prior-art test suite in this repo; these are the first tests.

## Out of Scope

- Daily, Blitz, and catalog gameplay (boards, digit slots, guesses, timers, catalogs, schedules, History rows)
- Full persist adapter: Daily persist, stats, lastPlayed, blitzBests, lastSeenUtc
- `engine/` (types, UTC, guess, search, streaks, schedule generator)
- GitHub Actions, GitHub Pages deploy, `index.html` → `404.html` copy
- Playwright, PWA, accounts, leaderboards, inverted Daily, archive play, skip, i18n, custom domain, IANA scrape
- A control to return theme to `system`
- Cookies, analytics, backend, UI kit, Redux/Zustand

## Further Notes

- Product and architecture authority is `docs/superpowers/specs/2026-09-08-portdle-design.md`. This spec is ticket #1 only.
- Glossary used as in that design: Daily category (`mixed` \| `protocols` \| `applications`), Mixed, Daily, Blitz, How-to. Do not introduce synonyms (e.g. “mode” for Daily category, “tutorial” for How-to).
- Theme stored union is `system` \| `light` \| `dark` even though v1 has no UI to write `system` after the first click.
- `writeHowToSeen` takes no argument: seeing How-to is a one-way latch this ticket.
