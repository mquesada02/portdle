# Spec: Codex sort — every card, unseen included, in both sorts

Spec for #85. Tracker: https://github.com/mquesada02/portdle/issues/85. Parent: Spec 2, #70.

## Problem Statement

A player browsing the Codex expects a `???` card to sit exactly where its entry will land once seen, and expects the whole group to reorder when they switch Name/Port sort. Today, `groupCards` in `src/engine/codex.ts` sorts only the seen entries among themselves, then drops them back into the catalog-array index positions that seen entries happen to occupy; every unseen entry stays pinned to its own raw catalog-array index. Because the catalog JSON files are in neither name nor port order, this means a `???` card sits wherever the catalog file happens to place it rather than where the chosen sort would put it, and the set of index positions available to seen entries is fixed by the catalog array rather than by the sort — so a card can land in a different position than it will occupy once it, or a neighbor, becomes seen. This is a deviation from Spec 2's Codex grouping decision, found while writing Spec 3, and fixed here ahead of it.

## Solution

`groupCards` sorts the entire group — seen and unseen entries together — by the chosen key, using the entry's real name or port even for an unseen entry (the engine already has the full catalog entry; only the rendered card hides it behind `???`). This is a single sort over the whole array rather than a sort-then-reinsert over a subset, so: name sort orders every card by case-folded name, unseen included; port sort orders every card by port ascending with ties broken by case-folded name, unseen included; the position an entry occupies depends only on its own name/port relative to the rest of the group and the active sort, never on which entries happen to be seen — so encountering an entry only changes its card's content (from `???` to its name and state), never its position, and switching the sort reorders the whole group, unseen cards included, exactly as it would if every card were already seen.

## User Stories

1. As a player, I want the Codex to order every card in a group by the chosen sort key, unseen cards included, so that a `???` card sits in the position its entry will occupy once seen.
2. As a player, I want Name sort to order every card in a group by case-folded name, unseen cards included, so that the alphabetical gaps in what I've seen sit in their true alphabetical place.
3. As a player, I want Port sort to order every card in a group by port ascending, ties broken by case-folded name, unseen cards included, so that the gaps in what I've seen sit in their true port order.
4. As a player, I want encountering an entry to change its card from `???` to its name and state without moving any card in the group, so that filling in the Codex never reshuffles what I've already seen.
5. As a player, I want switching the sort toggle to reorder the whole group, unseen cards included, so that the toggle always reflects the order I chose.
6. As a maintainer, I want engine tests covering an unseen card's position in both sorts (for example a `???` sorting between ports 22 and 25) and a card's position staying put when it becomes seen, so the fix is proven and protected against regression.
7. As a maintainer, I want the existing Codex engine tests to keep passing, edited only where they asserted the old, incorrect order, so the change stays minimal and reviewable.
8. As a player, I want no change to what a card shows, to the headline counts, or to the sort toggle itself, so this fix touches ordering only.

## Implementation Decisions

- Scope is one function: `groupCards` in `src/engine/codex.ts` (private to the module, called only by `codexGroups`). No exported signature in `codex.ts` changes: `codexGroups`, `codexCounts`, `applyCodexEncounter`, `clearCodexFresh`, and every exported type (`CodexCard`, `CodexGroup`) keep their current shape and behavior. The module's other private helpers, `compareEntries` and `foldedName`, are reused as-is with no change to their own behavior. `src/ui/codex-page.tsx` is unchanged — it already renders whatever order `codexGroups` returns.
- `groupCards`'s current body computes `seenIndices`/`seenEntries` (the catalog-array indices and entries that are seen), sorts only `seenEntries` via `compareEntries`, and reassigns the sorted seen entries back into `seenIndices` in order; every other index keeps its original catalog entry as `{ status: "unseen", entry }`. This is the bug: the set of index positions available to seen entries is fixed by the catalog array's own order, not by the sort, and an unseen entry's position is its raw catalog-array index, which is neither name nor port order.
- The fix replaces that body with a single sort over the full `entries` array using the existing `compareEntries(a, b, sort)` comparator, unchanged, then a map from the sorted array to `CodexCard`s: an entry with no record in `map` becomes `{ status: "unseen", entry }`; an entry with a record becomes `{ status: record.state, entry, fresh: record.fresh }`. Matching this codebase's own existing convention for sorting a copy rather than mutating the input array — already used one line above the code being replaced (`groupCards`'s own current `[...seenEntries].sort(...)` at line 78) and elsewhere in the engine (`src/engine/schedule-gen.ts`) — the sort is written as `[...entries].sort((a, b) => compareEntries(a, b, sort))`.
- `compareEntries` already compares any two `CatalogEntry` values by their real `port`/`name` regardless of Codex state, so no change to it is needed to make it usable on unseen entries — the module already holds every entry's real name and port; only the rendered card, not the sort, hides that data behind `???`.
- This still produces exactly Spec 2's accepted behavior: "unseen cards keep their position in both sorts" means an unseen card's position follows from its own true name/port under the active sort — the same position it would hold once seen — not that it is pinned to a fixed index independent of the sort. A port-sorted `???` between two ports still gives away roughly what the unseen entry's real port is; Spec 2 and the t76 ticket spec already accept this leak and it is not being changed or removed here.

## Testing Decisions

A good test exercises `codexGroups`/`groupCards` through the engine seam with literal `CatalogEntry` and `CodexMap` inputs and asserts the returned `CodexCard[]` order and contents — no DOM, no UI.

1. **Engine seam** (`src/engine/codex.test.ts`; existing file, no new file needed).
   - New: a port-sort case with three protocol entries at ports 22, 23, and 25 given to `codexGroups` in scrambled input order, only the port-22 and port-25 entries seen — the port-23 entry's `???` card sorts strictly between them, mirroring the ticket's own example.
   - New: a "card becoming seen keeps its position" case — call `codexGroups` twice with the same three entries and sort, once with an entry unseen and once with that same entry added to the map as seen; the entry's index in the returned card array is identical across both calls, and only its `status` (and `fresh`) changes.
   - Edited: the existing test `"an unseen entry keeps its original catalog-array index in both the name sort and the port sort"` asserts the old, incorrect behavior (the unseen entry staying at its raw input-array index, index 1, under both sorts). It is rewritten to assert the corrected behavior for the same three-entry fixture (`s1` "Bravo"/100 seen, `u1` "Unseen One"/999 unseen, `s2` "Alpha"/300 seen): under name sort the true order is Alpha, Bravo, Unseen One, so `u1` sorts last (index 2), and under port sort the true order is 100, 300, 999, so `u1` also sorts last (index 2) — in both cases `u1` remains unseen and its position is determined by its own name/port, not by the input array's index.
   - Unaffected, left as-is: `"codexGroups puts the Protocols group before the Applications group"` (seeds an empty map, so both its entries are unseen — the fix does not change output when every entry shares one status, since only the kind order is asserted), and `"name sort (case-folded) sorts chargen between BGP and Daytime"` and `"port sort breaks ties by case-folded name"` (both seed every entry as seen) — none of the three mixes seen and unseen entries in a way the fix's ordering change would affect, so their expected output is unchanged.
2. **App seam** (`src/ui/codex-page.test.tsx`; existing file, no changes expected).
   - The existing `"Sort toggle reorders by port and persists across a remount; Name restores the default order; an unseen card keeps its position"` test seeds only `dns` and `smtp` in a 48-entry Protocols catalog and asserts the first rendered card is unseen under both sorts. Verified against the production catalog: the true alphabetically-first Protocols entry is `amqp` and the true lowest-port entry is `echo` (port 7) — neither is `dns` nor `smtp` — so this assertion holds unchanged under the fix and needs no edit.
   - No other test in this file asserts card order beyond this one, so no further changes are expected here; run the suite to confirm.

No snapshot tests, no visual regression, no Playwright. This ticket is proven done by `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm gen:schedule --check`, and `pnpm build` all passing — the full checklist this repo's ticket specs consistently require, regardless of this ticket's own scope, since it touches no catalog or schedule data — plus the engine-seam coverage above.

## Out of Scope

- Any change to `src/ui/codex-page.tsx`, the Sort toggle's markup or behavior, the headline text, or group-heading counts — Spec 2 and this ticket both require these stay exactly as they render today.
- Any change to `codexCounts`, `applyCodexEncounter`, `clearCodexFresh`, or any type in `src/engine/types.ts`.
- Removing the accepted port-order leak of an unseen Codex card (Spec 2: "this is accepted for a single-player game. Do not 'fix' it.") — this ticket corrects *where* a `???` card sits relative to its true sort key; it does not hide or further obscure that position.
- Any change to Daily or Blitz rules, the schedule, the catalog, or the miss popover's content.
- Retroactively editing the #73 (`2026-09-12-t73-codex-engine.md`) or #76 (`2026-09-12-t76-codex-screen.md`) ticket specs, which describe the now-corrected behavior as it was understood at the time; they stand as the historical record and are not amended by this fix.
