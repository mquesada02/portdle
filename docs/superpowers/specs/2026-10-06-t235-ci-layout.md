# Ticket spec: CI layout

Spec for #235. Tracker: https://github.com/mquesada02/portdle/issues/235. Parent: Spec 6 (tests, CI, and motion), https://github.com/mquesada02/portdle/issues/222 (`docs/superpowers/specs/2026-10-04-spec6-tests-ci-motion.md`, "CI layout and schedule", user stories 6 to 9). Map: https://github.com/mquesada02/portdle/issues/212. Base branch: `master`. Blocked by: #226, #228, #229 (all merged).

## Problem Statement

CI (continuous integration) now has four kinds of job:

- `build`.
- `sql-tests`. It runs the fixture shape check and the functional suite on five projects.
- `screenshots`. It is one matrix job with three engines.
- `deploy`.

Three things are missing:

- A pull request that changes only documents still pays for the full run (about 25 to 35 runner-minutes).
- A new push to a pull request does not stop the older run of that pull request.
- `deploy` waits for `build` only. A red `sql-tests` or `screenshots` job does not block it.

## Solution

Three changes in `.github/workflows/ci.yml`, and one measurement:

1. A new job `changes` detects a docs-only pull request and outputs `docs_only`. The `screenshots` job and the e2e (end-to-end) steps of `sql-tests` skip when it is `true`.
2. A workflow-level concurrency group cancels the older run of the same pull request. Push and manual runs are never cancelled.
3. `deploy` waits for `build`, `changes`, `sql-tests`, and `screenshots`: every job.
4. The wall time of a normal run is measured. The screenshot jobs split into shards (parallel parts) only if a normal run is above about 11 minutes.

## User Stories

1. As the owner, I want a docs-only pull request to skip the screenshot jobs and the functional suite, so that a documentation fix does not use 25 minutes of runner time.
2. As the owner, I want `build` and the fixture shape check to run on a docs-only pull request, so that a broken build or a drifted fixture is still seen.
3. As the owner, I want a master push and a manual run never to skip for a docs-only reason, so that each master run produces a full baseline.
4. As a developer, I want a new push to a pull request to cancel the older run of that same pull request, so that I do not wait for a stale run.
5. As the owner, I want a master run never to be cancelled, so that every master commit keeps its baseline.
6. As the owner, I want `deploy` to wait for every job, so that a red job blocks the release.
7. As the owner, I want a normal run to finish in about 10 minutes, so that feedback stays fast. A measure above about 11 minutes triggers the shard decision.
8. As the owner, I want proof in the pull request that the skip and the cancel work, so that I do not trust the workflow text alone.

## Implementation Decisions

The decisions below come from the owner's comment on #235 (2026-10-06), except the ones that carry the mark "Author call". Further Notes lists the author calls.

- **The `changes` job**
  - It has no checkout. It lists the files of the pull request through the GitHub API (Application Programming Interface) and outputs `docs_only`.
  - Permissions: `pull-requests: read` only.
  - On a push or a manual run (no pull request number), `docs_only` is `false` and the job makes no API call.
  - On a pull request, `docs_only` is `true` only when the list is not empty and every path is under `docs/` (it starts with `docs/`) or ends with `.md`. An empty list gives `false`.
  - **Author call**: the step calls `gh api --paginate` (the `gh` tool is on the runner image) with `GH_TOKEN` set from `github.token`, `per_page=100`, and `--jq` so that each page prints names, one per line. The step captures the output in a variable before it tests it, so that a failed call stops the step. It does not pipe `gh` into another command.
  - **Author call**: a failed API call fails the job, and the jobs that need it do not run. The check fails closed.
  - **Author call**: for a renamed file, the old path (`previous_filename`) counts too. A move from `src/a.ts` to `docs/a.md` is not docs-only.
  - **Author call**: the API returns at most 3000 files. A list of 3000 names or more gives `false`, because the list may be cut. A rename gives two names, so this rule is stricter for renames. That is safe.
- **`screenshots`** adds `needs: changes`. Its `if` becomes `(github.event_name == 'pull_request' || github.ref == 'refs/heads/master') && needs.changes.outputs.docs_only != 'true'`. The parentheses are required. Without them, `&&` binds tighter than `||`, and the job never skips on a pull request. Matrix, steps, and comments do not change.
- **`sql-tests`**
  - **Author call**: it adds `needs: changes`. See Further Notes, call 1.
  - The steps `pnpm exec playwright install --with-deps chromium firefox webkit` and `pnpm test:e2e` get `if: needs.changes.outputs.docs_only != 'true'`.
  - The artifact upload step already runs only when the e2e step failed. A skipped e2e step uploads nothing.
  - `pnpm check:fixtures`, `pnpm dev:schedule`, and `scripts/run-sql-tests.sh` always run.
- **`build`** has no new `needs` and no `if`. It always runs.
- **Concurrency**, at workflow level:
  - `group: ${{ github.workflow }}-${{ github.event.pull_request.number || github.sha }}`. **Author call**: the prefix `github.workflow` keeps another workflow out of the group.
  - `cancel-in-progress: ${{ github.event_name == 'pull_request' }}`.
  - A pull request run is keyed by the pull request number. A new run cancels the older one. A push or manual run is keyed by the commit and is never cancelled.
  - The `labeled` and `unlabeled` events stay in the `pull_request` types and have no label filter. A label event cancels and reruns the whole run (accepted cost).
- **`deploy`**: `needs: [build, changes, sql-tests, screenshots]`. Its `if` does not change: master push, or manual run on master. On those runs `docs_only` is `false`, so no needed job skips.
- **Wall time**: no shard is added now. After the pull request's own CI run, the wall times go in the pull request body: one for a normal pull request run (with a master baseline), one for the latest master run. If a normal run is above about 11 minutes, the owner decides on shards in a follow-up. The run that captures the merge-base baseline is exempt.
- **Files**: `.github/workflows/ci.yml` and this spec file only. `schedule-action.yml`, the gate scripts, and app code do not change.

## Testing Decisions

- A good test shows what the workflow does on a real run. The proof uses the real GitHub runner, not a copy of the logic.
- **Detection script**: before the push, the `run:` body of the `changes` step runs locally with a stub `gh`. Nothing from this check is committed. The cases and the expected `docs_only` value:
  - Only `docs/x.md`: `true`.
  - Only `README.md`: `true`.
  - Only `docs/a.png`: `true`.
  - Only `src/a.ts`: `false`.
  - A mix of docs and source: `false`.
  - An empty list: `false`.
  - A rename from `src/a.ts` to `docs/a.md`: `false`.
  - A list of 3000 names: `false`.
  - A push event (no pull request number): `false`.
  - A failed `gh` call: the step exits with a non-zero code.
- **Workflow syntax**: `actionlint` runs on the file when it is available. If not, the pull request's own run proves the syntax.
- **Docs-only proof** (the owner's proof decision): a throwaway pull request changes one docs file. Its base is the ticket branch, so its diff is docs-only and the new `ci.yml` runs. The run shows `screenshots` skipped, the Playwright install and `pnpm test:e2e` skipped, and `build` and `pnpm check:fixtures` run. The user opens it with `gh pr create`, so the run starts (a `GITHUB_TOKEN` push does not start CI).
- **Cancel proof**: the second push goes out right after the first run starts, while `build` and `sql-tests` still run. It cancels the first run. Both run links go in the pull request body. The throwaway pull request then closes unmerged and its branch is deleted.
- **Normal run**: the pull request's own run gives the wall time. It counts only when its `screenshots` jobs downloaded a master baseline (the download step ran). If they captured the merge-base instead, the measure is not valid, and the run is repeated once on a commit with a baseline or the owner is told. The latest master run gives the other time.
- `pnpm lint`, `pnpm typecheck`, `pnpm test`, and `pnpm build` pass before the pull request opens.

## Out of Scope

- Sharding of the screenshot jobs (only if the measure says so).
- A label filter for the `labeled` and `unlabeled` events.
- Branch protection (none exists on master, so a skipped check does not block a merge).
- `schedule-action.yml`, the gate scripts, and app code.

## Further Notes

Author calls, for the owner to accept before implementation:

1. `sql-tests` gets `needs: changes`. The owner's comment says "`build` and `sql-tests` do not wait for anything new". A job reads the output of another job only through `needs`. The cost is a delay of about 10 seconds before `sql-tests` starts. A second cost: when the `changes` job fails, `sql-tests` does not run, so `pnpm check:fixtures` does not run either. Only `build` stays free of the new job. The other way (detect inside `sql-tests`) needs a second detection step, which duplicates the rule.
2. A renamed file counts by both of its paths.
3. A list of 3000 names or more gives `docs_only=false`.
4. The concurrency group starts with `github.workflow`. Two runs on the same commit (a master push and a manual run, or two manual runs) share a group. The second run waits. A third run replaces the waiting one. This cancels only a waiting run, never a running one. The owner's rule (keyed by commit) is followed as written.
5. `changes` also runs on push and manual runs. It outputs `false` without an API call, so the jobs that read it always have one value to read.
6. The `gh api` details in the `changes` job (token, page size, `--jq`, capture before test) are the author's choice. They make a failed call stop the job.

Facts checked (2026-10-06, against the GitHub documentation and the current `ci.yml`):

- The pull request files API returns at most 3000 files, and a renamed file has `previous_filename`.
- A job `if` without a status function has an implicit `success()`. A job whose needed job skipped or failed is skipped.
- `&&` binds tighter than `||` in a GitHub expression.
- A skipped step has `outcome` `skipped`, so `steps.e2e.outcome == 'failure'` is false for it.
- A job skipped by its `if` before the matrix expands shows in the checks as `screenshots-${{ matrix.engine }}`. This is cosmetic. No change is planned.
- A `pull_request` workflow with no `branches` filter runs for any base branch, and it uses the workflow file of the merge commit. This is why the stacked proof pull request runs the new `ci.yml`.
