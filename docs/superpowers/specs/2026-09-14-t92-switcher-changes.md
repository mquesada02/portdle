# Spec: Motion — switcher changes

Spec for #92. Tracker: https://github.com/mquesada02/portdle/issues/92. Parent: Spec 3, #87. Blocked by #89 (merged).

## Problem Statement

A Daily category tap or a History segment tap swaps everything below the switcher at once, with no transition, even though #89 already gave nav taps and wordmark taps a fade-and-rise motion and already made the router hold the whole screen still on a switcher tap so a later ticket could add its own motion there. That later ticket is this one: the router already asks for the `switcher` transition type on a Daily switcher tap, a History switcher tap, and a nav tap that lands back on the current screen (Daily from Protocols, History from the Blitz segment), but nothing in the stylesheet yet animates anything under that type — a switcher tap today looks identical to no transition at all.

## Solution

A Daily category tap, a History segment tap, and a nav tap that stays on the same screen move only the content below the switcher: it fades out over 100ms and rises in over 150ms with an 8px lift, the same feel as a screen change, while the switcher — and on History the heading above it — hold still. On the Daily screen this region is everything from the target caption down through the reveal, which today are separate siblings and gain one new wrapping element to carry the motion together. On History the region is the single list below the switcher, in both the Daily and the Blitz segment, which already exists as one element and needs no new wrapper. Browsers without the View Transitions API keep today's instant swap; reduced motion plays none of it. This ticket uses the router's existing `switcher` transition type end to end; it adds no new type and changes nothing about which taps request which type.

## User Stories

1. As a Daily player, I want everything below the Daily switcher, from the target's name down to the reveal, to change with motion when I pick Mixed, Protocols, or Applications, so that the switcher stays put and the category swap reads as a content change.
2. As a History reader, I want only the list below the History switcher to change with motion when I pick Daily or Blitz, so that the heading and the switcher I just tapped do not move under my finger.
3. As a Daily player, I want a nav tap that lands back on the Daily screen from a category other than Mixed to play the same switcher motion as tapping the Daily switcher directly, so that every way of reaching a category feels the same.
4. As a History reader, I want a nav tap to History from the Blitz segment to play the same switcher motion as tapping the History switcher directly, so that every way of reaching a segment feels the same.
5. As a Daily player, I want switching to a category whose Daily I already finished today to show the region rising in and then the reveal doing its own small rise, so that a finished category still greets me with the reveal's usual arrival.
6. As a player, I want a switcher change to finish within a fraction of a second, so that motion never slows me down.
7. As a player on a browser without the View Transitions API, I want switcher changes to work exactly as today, so that an older browser loses only the polish.
8. As a player who has asked my system to reduce motion, I want none of this motion to play, so that the app respects my setting as it already does for the board and for screen changes.
9. As a screen reader user, I want none of this motion to change what is announced or when, so that motion stays purely visual.
10. As a maintainer, I want the `switcher-content` view-transition rules to pass lint without weakening the linter for the rest of the stylesheet, so that the linter keeps its value.
11. As a maintainer, I want my stylesheet edit kept to one clearly delimited block so it merges cleanly alongside the parallel ticket that adds the `phase` type to the same file.

## Implementation Decisions

### The `switcher-content` region

- On the Daily screen, everything currently rendered after the Daily switcher — the target caption and heading, the Daily screen's own progress notice, the try counter, the board, the tracker strip, the message line, the Submit button, and the reveal, all siblings today — moves inside one new wrapping element that carries the `switcher-content` view-transition name via the same Tailwind arbitrary-property utility convention the shell's `screen` region already uses (`[view-transition-name:screen]` there, `[view-transition-name:switcher-content]` here). The wrapper carries no other styling and changes no existing element's classes, order, or nesting relative to each other; it only adds one ancestor. It has no role and no accessible name of its own, so it changes nothing about what a screen reader announces. The Daily switcher itself, which sits above this wrapper, is unaffected; the Daily screen has no heading above the switcher — its own `h1` (the target's name) is part of the region that moves.
- On the History screen, the single list below the switcher — the Daily segment's list of dated groups and the Blitz segment's list of dated run groups — carries the same `switcher-content` name directly, with no new wrapper. The two lists are not symmetric in one respect: the Blitz segment's list already renders an explicit "No runs yet." empty state inside the same `<ul>` when there are no runs, while the Daily segment's list has no such branch today and simply renders as an empty `<ul>` when there is nothing to show; this ticket does not add one, since a Daily empty state is not part of its scope. The `h1` above the History switcher, and the switcher itself, are unaffected.
- The region name is reused across both screens and both History segments the same way the `screen` region name is already reused across all four nav screens: only one is ever mounted at a time, so the browser never needs to disambiguate two live elements sharing a name.

### Stylesheet

- `src/styles.css` gains one clearly delimited, appended block, placed alongside the existing `screen`/`switcher` rules #89 added (so the two sibling tickets touching this file — this one and the one adding the `phase` type — each add an unambiguous block):
  - Under the `screen` type (`:active-view-transition-type(screen)`): `switcher-content` gets the same no-animation rule `screen` already gets under the `switcher` type — its group tween zeroed and its old and new snapshots both zeroed with `mix-blend-mode: normal`, so a screen change passing through a route that has a `switcher-content` region does not crossfade it separately.
  - Under the `switcher` type (`:active-view-transition-type(switcher)`): `switcher-content`'s group tween is zeroed (`animation: none`); its old snapshot gets `animation: fade-out 100ms ease-out both`; its new snapshot gets `animation: rise 150ms ease-out both` — the same keyframes, durations, and easing `screen` already uses under the `screen` type. Neither snapshot's blend mode is touched, since both are animating and the browser's default additive blend keeps the overlapping fade-out and rise-in from dipping in brightness. `screen` already carries its own no-animation rule under this type from #89, and the root already carries its untyped no-animation rule, so the switcher and (on History) the heading already hold still with no change needed here.
  - `switcher-content` is a hyphenated name, so per the linter facts verified for this ticket it never triggers Biome's `lint/correctness/noUnknownTypeSelector` (only a selector naming bare `screen` does); none of this block's new selector lines need a `biome-ignore` comment, unlike the six existing `screen`-naming lines #89 added.
- Nothing else in the stylesheet changes: the reduced-motion media block's existing universal rules (`::view-transition-group(*)`, `::view-transition-old(*)`, `::view-transition-new(*)`) already zero any named region's animation and reset its blend mode with no further edit, and the existing `screen`/`switcher` rules from #89 are untouched.

### The reveal's own rise

- Switching to a category whose Daily is already finished needs no code change to play the region's rise followed by the reveal's own delayed rise. Each Daily category is a separate route component (`MixedPage`, `ProtocolsPage`, `ApplicationsPage`), so a category switch fully unmounts and remounts `DailyPage`, and with it `DailyReveal`, exactly as it does today; `DailyReveal`'s existing `.animate-rise` (300ms, 250ms delay, `both` fill) already starts in its pre-animation state and only begins after its delay, which lands after the `switcher-content` transition's 150ms rise has already finished. Nothing in this ticket touches `daily-reveal.tsx`.

## Testing Decisions

A good test exercises a public seam with literal inputs and asserts what a player sees or what a pure function returns. Per Spec 3's Testing Decisions, how motion looks (timing, keyframes, the view-transition pseudo-elements) is checked by eye, not by tests; only whether, and with which type, a transition is requested is tested through a fake of the View Transitions API.

- This ticket's router-testing acceptance criteria are already met by tests `src/ui/app.test.tsx` carries today, added under #89 ahead of this ticket's need: "navigating by nav link and by switcher lands on the right screen with no API present" (covers a Daily switcher tap and a History switcher tap with no fake installed) and "a Daily switcher tap starts a view transition with the switcher type" / "a History switcher tap starts a view transition with the switcher type" (each with the fake `startViewTransition` and the fake selector-support check installed, asserting `calls` equals `[["switcher"]]`). No new router test is added; these three keep passing unchanged, proving the wrapper and the className addition don't touch the router's own type decision.
- No new App-seam test is added for the wrapper or the `switcher-content` region itself: this ticket's only testable claim beyond the router's existing coverage is that the Daily and History pages keep the same roles, accessible names, and text, which the existing app test file's suite already guards for the facts it checks — among others, "each route shows its heading, and the old Help address lands on the Daily" (asserts the Daily's `h1` by category name on all three routes), "Daily nav link is active on all three Daily routes and no other route", and the switcher-navigation assertions above (which read the Daily switcher's and History switcher's own `nav` landmarks and `Link`s by role and name). This catches a regression that changes a heading's name, a link's role or name, or navigation itself; it does not independently verify the wrapper's exact placement or either `<ul>`'s `aria-labelledby`, since no existing test asserts DOM nesting or `aria-labelledby` values directly and neither is checked by eye either — this ticket's edits leave both `<ul>`'s `aria-labelledby` untouched and add only the one wrapper described above, so the risk is confined to implementation care, not a gap this ticket adds a check for.
- Every existing test keeps passing with no edits: this ticket touches no test file.
- This ticket is proven done by `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm gen:schedule --check`, and `pnpm build` all passing, plus a by-eye check on the dev server, at phone and desktop widths, in a browser with the View Transitions API and in one without: a Daily category tap fades the region below the switcher out and rises the new category in while the switcher holds still; a History segment tap does the same for the list while the switcher and the `h1` hold still; a nav tap back to Daily from a category other than Mixed, and a nav tap to History from the Blitz segment, play the same motion as their own switcher taps; a switcher tap to a category whose Daily is already finished shows the region's rise followed by the reveal's own small delayed rise; nothing plays under reduced motion; and the built CSS carries the `switcher-content` rules described above with no unused lint ignore.

## Out of Scope

- The `phase` type, the `reorder` type, the Blitz arena/run/end-card transitions, and the Codex card glide — other tickets' work (ticket #93 and later).
- The shared view-transition helper for state changes outside the router — a later ticket's work.
- Any change to which transition type a route change requests, to the router's `screenFor`/`types` logic, or to `src/ui/nav.ts` — all settled by #89 and unchanged here.
- Any change to the Daily switcher's or History switcher's own markup, labels, active-state logic, or color transition.
- Any change to `daily-reveal.tsx`, or to the existing `pop`, `shake`, `draw`, or `rise` keyframes.
- A crossfade or a directional slide; the prototype settled on fade-and-rise, already implemented once by #89 and reused here.
- Animating the height of anything, a polyfill for browsers without the View Transitions API, and any motion library or spring physics.
