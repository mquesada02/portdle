# Ticket spec: Row sync (#136)

Ticket [#136](https://github.com/mquesada02/portdle/issues/136) of Spec 4 (accounts, sync, and leaderboards; issue #127, spec file `docs/superpowers/specs/2026-09-28-spec4-backend.md`). Map: #114. Blocked by the Persist seam (#131), the merge engines (#133), and the name confirm (#135), all merged. This ticket builds Sync for the Codex, the Bests, the runs, and the Dailies, with the stats rebuild. It builds no Preferences sync (#137), no Device progress choice (#138), no Leaderboards (#139), and no Account deletion (#140).

In this spec "row" means a database row or one synced record (a Codex entry, a Best, a run, a Daily), never the Daily board's Row from `CONTEXT.md`.

## Problem Statement

A signed-in player's Codex, Bests, runs, and Dailies stay on the device that made them. The merge engines exist but nothing calls them, the `Remote` seam cannot read or write these rows, the database has no tables for them, and nothing reacts when a player plays, opens the app, or comes back to the tab.

## Solution

A signed-in player whose name is confirmed gets Sync. Each thing they do reaches the account 1.5 seconds later. Every app open, and every return to the tab, pulls the account's rows, merges them into the device, and pushes back what the account lacks. Stats and last played are rebuilt from the merged Dailies. Sync is silent: a failure is dropped and the next trigger retries. When the account no longer exists, the device signs out and keeps its data. The backend gets four private tables with owner-only row-level security.

## User Stories

Spec 4 stories 20 to 22, 24 to 29, 31 to 35 (the Codex, Bests, runs, Dailies, and stats parts), 65 (the private tables), 64 (the detection half), and:

1. (R1) As a signed-in player, I want each Codex change, Best, finished Blitz run, and Daily try to reach my account about 1.5 seconds after I make it, so that my other devices see it.
2. (R2) As a signed-in player, I want only the rows I changed to be sent, so that Sync stays light.
3. (R3) As a signed-in player, I want a Codex fresh-flag clear to send nothing, so that opening the Codex sends nothing.
4. (R4) As a signed-in player, I want an app open or a return to the tab to pull my account's rows and merge them into this device, so that I see my other devices' progress.
5. (R5) As a signed-in player, I want rows where my merged value differs from the account's copy to be sent back, so that two devices that pushed at the same time converge.
6. (R6) As a signed-in player, I want nothing sent while my name confirm is pending, so that the name confirm is a real gate.
7. (R7) As a signed-in player, I want progress made while I was signed out to reach my account at my next sign-in, so that I lose nothing.
8. (R8) As a signed-in player, I want my stats and streaks rebuilt after a pull that changed a Daily, so that they never double-count a day.
9. (R9) As a signed-in player, I want a sync that fails to say nothing and to be retried by my next action, open, or return to the tab, so that Sync never gets in my way.
10. (R10) As a player whose account was deleted elsewhere, I want this device to sign itself out and keep my data, so that it becomes an ordinary signed-out device.
11. (R11) As a signed-in player, I want a Blitz run I finish while a pull is in flight to survive the pull, so that a pull never overwrites my newest play.
12. (R12) As the owner, I want the tables, policies, and grants as ordered SQL in the repo plus a hand-run smoke script, so that the backend can be rebuilt and checked from source.
13. (R13) As a signed-in player who goes offline, I want an offline tab return to keep me signed in, so that a network failure never signs me out.

## Implementation Decisions

- **`Remote` gains two calls.** `pull()` returns the account's rows and `push(accountId, rows)` upserts rows into that account (row-level security refuses them if the stored sign-in belongs to another account, so a sign-in switched in another tab never receives this device's rows). Both use one row-set shape: Codex entries as entry id to state, Bests as the existing Bests map, runs as a list, Dailies as a map keyed `category|date`. `push` takes a partial set (only the changed rows). `pull` returns the newest 50 runs and every other row. A new error type, `AccountGoneError`, is exported beside `Remote`; any call may reject with it. Every other rejection is an ordinary failure.
- **Supabase adapter.** Four tables, snake_case columns, mapped in pure exported functions. The mappers rebuild every run (with its rounds) and every Daily (with its guesses) field by field in the key order the app writes, because `jsonb` reorders object keys; `timeToScoreMs` stays absent when the column is null, and a round's `wrong` and a guess's `identified` map to and from `null` only (the stored-value guards accept nothing else). `pull` reads each table except runs ordered by its primary key, in pages of 1000 rows (the REST default cap), so a long history is never cut or duplicated; runs are read by `ended_at` descending with limit 50, no paging. `endedAt` is stored as `timestamptz` and returned as the exact ISO string the app writes (`new Date(value).toISOString()`, millisecond precision); a run whose `endedAt` is not a valid date and a Daily whose date is not a valid UTC date are left out of a push (one bad local value must not fail a whole chunk); other refused values are an accepted risk. `push` upserts in chunks of 500 rows per table, each row carrying the account id Sync passes in, with `onConflict` set to the primary-key columns of that table; a rejected `push` may have applied earlier chunks, which is harmless because a retry upserts again and Sync updates its snapshot only after a whole `push` succeeds.
  - **Account gone** is thrown as `AccountGoneError` when: the account row is missing on `getAccount` (Postgres code `PGRST116`; deletion cascades the row away, and `refresh()` reads the account first, so this is the normal path); an upsert fails with a foreign-key violation (`23503`; a race after `getAccount`); or a session read or refresh fails with auth code `user_not_found` (a defensive mapping; the expected route for a deleted user is a refused refresh, which gives signed out while active, below). A session read or refresh that fails with a non-retryable refusal (the stored sign-in is invalid, for example `refresh_token_not_found`, or another tab removed it) makes `getAccount` return signed out, as today. A retryable auth failure (the error's name is `AuthRetryableFetchError`, or its status is 0 or at least 500) makes `getAccount` reject with an ordinary error, so an offline tab return never signs the player out.
  - A missing or failed session on `pull` or `push` is an ordinary failure, not account gone; the next `refresh()`'s `getAccount` decides.
  - Such a run or Daily is left out of the snapshot too; Sync's diff skips them so they are not re-marked.
  - Hand-verified by the smoke script, not Vitest.
- **Sync module** (`src/sync`, depends on `Persist`, `Remote`, an injected clock, and an injected UTC-day function; never touches React). API: `attach()` registers the `Persist` write listener and the visibility and focus listeners and returns a detach function (calling it twice is safe under StrictMode; it also clears the timer and invalidates in-flight work); `refresh()` reads the account (with no stored sign-in the adapter answers signed out without loading the library, so a signed-out player pays no bundle cost) and, when it is signed in with a confirmed name, runs one full sync; `stop()` ends syncing (sign-out); `onAccountGone(listener)` returns an unsubscribe function; `accountGone()` runs the account gone steps below for a caller that detects it (the account menu). The clock is `{ setTimeout, clearTimeout }`; the default calls the global functions at call time.
  - **Activation and epoch.** Sync is active only after `refresh()` found a signed-in, confirmed account, and stays active until `stop()`, detach, or account gone. Activation is the change from inactive to active only; each activation gets a new epoch number. Every `refresh()` captures the epoch at its start and discards its result if the epoch changed; `stop()` and detach always change the epoch, even while inactive, so a sign-out during the account read cannot activate Sync. A `refresh()` while active keeps the epoch and the snapshot and replaces the snapshot with the new pull, unless `getAccount` returns a different account id than the active one, which counts as a new activation (another tab signed in as someone else). `stop()`, detach, account gone, and a new activation change the epoch (`stop()` also clears the rerun flag), clear the snapshot and the "pulled" flag, and clear the timer. Every queued step and every awaited result checks its epoch and is discarded when stale, so a pull that resolves after sign-out writes nothing, and a later account never diffs against an earlier account's snapshot. While inactive (signed out, or name confirm pending) the write listener and the triggers push and track nothing.
  - **`refresh()`.** All Sync work runs on one serial queue. A call while a `refresh()` runs sets a rerun flag and shares the running promise; when it ends, one more `refresh()` runs, so a trigger that arrived after the account read (for example the name confirm succeeding) is never lost, and any burst of triggers costs at most two syncs. It reads `getAccount`. Signed out while active means the auth service refused the stored sign-in: treat as account gone. Signed out while inactive: nothing. Name not confirmed: stay inactive (an active Sync is reset first, as when another tab signed in as someone else), nothing pulled or pushed. Confirmed: become active, pull, merge, mark differences, push pending. `refresh()` never rejects, and the account menu does not await it, so a sync failure never reaches the name confirm; its shared promise resolves after the rerun. A rejected `getAccount` or `pull` is silent (nothing is pushed after a failed pull), except `AccountGoneError`.
  - **Triggers of `refresh()`**: the app opening (the `App` component calls it once after `attach`), the tab becoming visible (`visibilitychange` with visible state), window focus, and the name confirm succeeding or sign-in completing (the account menu calls it after a successful `confirmDisplayName`). Sign-out (menu or name confirm link, after `signOut` succeeds) calls `stop()`.
  - **Change tracking.** The write listener ignores writes made while Sync itself writes (a flag around Sync's own persist writes; persist writes are synchronous) and every kind that is not a synced row (theme, How-to seen flag, and Codex sort belong to #137; stats, last played, and last seen day are never synced). For a Codex, Bests, runs, or Daily write it compares the row's synced value with Sync's in-memory snapshot of the account's copy, using a canonical text (object keys sorted, never raw `JSON.stringify` order; the Codex compares only its state, so a fresh-flag clear marks nothing). Rows that differ are added to the persisted changed-rows bookkeeping (`writeSyncChanges`; keys are the entry id, `category|orientation|mode`, `endedAt`, and `category|date`), and a push is scheduled. Sync reads the whole bookkeeping object, edits only the `codex`, `bests`, `runs`, and `dailies` lists, and writes it back with `preferences` intact.
  - **Snapshot** = the account's copy as last known, in canonical text: replaced by a pull's rows, updated for each row a whole successful push covers, empty after any epoch change.
  - **Push.** Debounced 1.5 seconds: each marking write restarts the timer. The timer callback runs a full `refresh()` when no pull has succeeded in this epoch (a push before a merge could overwrite a better account copy, since an upsert is last write wins), and otherwise pushes. A push reads the pending keys' current local values (a key with no local value is dropped), drops keys whose row equals the snapshot from the bookkeeping, and pushes the rest in one `push` call. On success it updates the snapshot and removes a key from the bookkeeping only if the local value still equals what was pushed (a row changed during the call stays pending). On an ordinary failure the bookkeeping stays and nothing else happens; `AccountGoneError` follows the account gone steps. Pending rows also go out at the end of every `refresh()`, so a failed push is retried by the next write, open, visibility, or focus.
  - **Merge on pull.** In one synchronous step with no await between the local read and the local write, so a concurrent player write is never overwritten: Codex with `mergeCodex`, Bests with `mergeBests`, runs with `mergeRuns`, each Daily with `mergeDaily` (an account-only Daily is written as is). Each merged value is written through `Persist` only when its canonical text differs from the local value's, inside the "Sync is writing" flag. After the merge, every local synced row whose canonical text differs from the snapshot is added to the bookkeeping, then pending rows are pushed. That one rule covers the first-sign-in import (every local row differs from an empty account), the later-sign-in push of progress made while signed out (R7), and the write-back of merged rows (R5).
  - **Stats rebuild.** For each Daily category with at least one Daily written by the merge, fold every stored Daily of that category (listed with `listDailyDates`) with `foldStats` and the injected UTC day, and write stats and last played through `Persist`, inside the flag. A fold with no finished Daily writes nothing.
  - **Last synced account.** After a successful merge Sync writes the account id with `writeSyncAccount`. Nothing reads it in this ticket (#138 does). A different account signing in on a device imports without asking until #138.
  - **Account gone.** On `AccountGoneError`, or signed out while active: Sync becomes inactive (epoch change as above), calls `signOut` on the `Remote` (its failure is ignored), and notifies the `onAccountGone` listeners. Local data is untouched.
- **Wiring.** `App` creates the Sync module when a `Remote` exists, attaches it in an effect, calls `refresh()` once, detaches on cleanup, and passes it down through the router context. The UTC-day function is `utcDateString(new Date())` at call time (the `utcToday` prop override of `App`, used by tests, is read through a ref). `createAppRouter` and the router context type gain `sync`, and the Shell passes it on. `AccountMenu` receives it, calls `refresh()` after a successful name confirm, calls `stop()` after a successful sign-out, and subscribes to `onAccountGone` to show the signed-out view; its own account read that rejects with `AccountGoneError` calls `accountGone()` and shows the signed-out view, not the load-failure line. A retryable auth failure now makes that read fail, so the menu shows its load-failure line offline where it showed signed out before. Without a `Remote` nothing is created and local play is untouched.
- **Migration `20260929000003_row_sync.sql`.** Four tables, each with `account_id uuid not null references public.accounts (id) on delete cascade`, all other text columns `text not null` with the checks named: `codex_entries` (`entry_id` non-empty, `state` in identified, missed, correct; key account and entry), `blitz_bests` (`category`, `orientation`, `mode` in their value sets, `score` integer at least 0, `time_to_score_ms` double precision null and at least 0, since the monotonic clock is fractional; key account, category, orientation, mode), `blitz_runs` (`ended_at` timestamptz, `category`, `orientation`, `mode`, `ended` in lives, timeout, `score` integer at least 0, `time_to_score_ms` double precision null, `rounds` jsonb array; key account and `ended_at`), and `dailies` (`category`, `day` as `date` (the app's UTC date; `date` is a type name), `status` in playing, won, lost, `guesses` jsonb array; key account, category, day). The two `jsonb` columns have a `jsonb_typeof(...) = 'array'` check. Row-level security enabled; one named policy per table (`codex_entries_own`, `blitz_bests_own`, `blitz_runs_own`, `dailies_own`) for the `authenticated` role, `for all`, `using` and `with check` on `account_id = (select auth.uid())`; one `for all` policy per table is deliberate (the four tables share one rule; `accounts` needs separate ones because its columns are granted separately). Grants: `select, insert, update, delete` on the four tables to `authenticated` only (delete lets the smoke script clean up, and lets a player delete their own rows through the API, which harms nobody else; the app never sends a delete). No grant to `anon`. Comments state that "Automatically expose new tables" is off.
- **Smoke script.** `scripts/smoke-backend.ts` gains checks for the four tables: anonymous read refused, own upsert reads back, upsert of an invalid state or status refused, insert with another account id refused, and cleanup of its own test rows. `supabase/tests/row-sync.sql` (owner-run, assertion style of `accounts.sql`) checks that deleting an auth user cascades away rows of all four tables.
- **No new domain term**, so `CONTEXT.md` does not change. ADR 0002 already records that Sync layers on `localStorage`.

## Testing Decisions

Good tests drive behavior through the highest seam and assert the local store, the fake account's rows, and the screen, never internal calls.

- **Sync module tests** (`memoryStore`, the fake `Remote`, a fake clock): push 1.5 seconds after a write (debounced, restarts on a second write), only changed rows, each kind (Codex, Best, run, Daily); Sync's own merge writes never mark or push; a Codex fresh-flag clear pushes nothing; pull merges each kind with the local store and keeps local `fresh` flags; local-only rows are pushed and equal rows are not; nothing pulled or pushed while the name is unconfirmed, and a full sync after it is confirmed and `refresh()` runs; progress made while signed out is pushed at the next sign-in; a pull that changed a Daily rebuilds stats and last played (equal to the incremental result), a pull that changed none does not; pull on visible and on focus, none on hidden; failures silent for `getAccount`, `pull`, and `push`, and the next write, visibility, or focus retries; a player write during an in-flight pull survives; a row changed during an in-flight push stays pending; two devices (two stores, one shared fake account) converge after concurrent writes and after concurrent Dailies of different rank; account gone (`AccountGoneError` from pull, from push, and a signed-out read while active) signs out, notifies the listener, and keeps local data; `stop()` ends pushes and clears the timer; `writeSyncAccount` holds the account id after a sync; two overlapping `refresh()` calls run at most two syncs and the second one sees a name confirmed after the first read the account; sign-out during an in-flight pull or account read writes nothing and clears the snapshot; an account id change while active starts a new activation; sign-out then sign-in as another account starts from an empty snapshot; a failed pull is followed by no push (the account holds a better Daily than the device); a push scheduled before any pull runs a full sync; a pulled row equal in value but with reordered object keys marks and pushes nothing; the bookkeeping keeps the `preferences` list; an offline `getAccount` failure is silent and keeps the device signed in; the account menu's own read rejecting with `AccountGoneError` signs Sync out and shows signed out; a signed-out player triggers no library load.
- **App-level tests** (fake `Remote`, vi fake timers): a signed-in confirmed account pulls on open and the merged Codex shows in the store; a Daily guess reaches the fake account after 1.5 seconds; an unconfirmed name sends nothing until Continue, then imports; a gone account shows the signed-out menu with the data kept; no `Remote` means no requests. Prior art: `name-confirm.test.tsx`, `account-menu.test.tsx`.
- **Adapter tests** (`supabase.test.ts`, injected fake library): row mapping in both directions including the ISO round trip and `time_to_score_ms` absent; paging past 1000 rows; chunking past 500; `pull` limit for runs; `AccountGoneError` for `PGRST116`, `23503`, and `user_not_found`; a non-retryable session refusal gives signed out and a retryable one rejects with an ordinary error; other errors rethrown as is; every paged read is ordered by primary key and pages concatenate; upserts carry `onConflict`; jsonb-reordered keys map back to the app's order; a run with an invalid `endedAt` is left out of a push.
- **Fake `Remote`** (`src/test/fake-remote.ts`): gains `pull` and `push` over an account row set that two fakes can share (the two-device tests), call logs, `failPull` and `failPush` switches, a switch that raises `AccountGoneError`, holds for `pull` and `push` (in-flight tests), and returns deep copies with the newest 50 runs, like the adapter. It can return rows with object keys reordered, as `jsonb` does.
- **Not in Vitest**: the SQL and the adapter against the real project (hand-run smoke script and `supabase/tests/row-sync.sql`).
- The existing suite passes; `pnpm lint`, `pnpm typecheck`, `pnpm test`, and `pnpm build` pass.

## Out of Scope

Preferences sync and any preference bookkeeping (#137); the Device progress choice (#138); Leaderboards and their views (#139); Account deletion (#140); reading the display name again on every pull (a Spec 4 statement no ticket lists); any sync UI; realtime, polling, or an online/offline listener; retry loops.

## Further Notes

Author calls not decided by #136 or Spec 4, listed so they can be overruled:

- `refresh()` reads the account itself (a second `getAccount` at app open, beside the account menu's read) so a failed account read is retried by the next trigger and Sync does not depend on the menu's lifecycle.
- The clock is `{ setTimeout, clearTimeout }`; the UTC day is a separate injected function.
- Deciding what to push is a diff against an in-memory snapshot of the account's copy plus the persisted changed-rows list; the snapshot is not persisted.
- A tab that regains visibility or focus runs the whole `refresh()` (account read, pull, merge, push pending), not a bare pull.
- Signed out while Sync is active (the stored sign-in vanished) is handled as account gone.
- `pull` reads all Dailies in pages, not a capped window; runs read only the newest 50.
- Tables use typed columns and `jsonb` only for the round log and the guesses; `time_to_score_ms` is `double precision` because the Blitz clock is fractional.
- `delete` is granted on the four tables only so the smoke script can clean up.
- Stats are not written when the fold finds no finished Daily.
- The account id written by `writeSyncAccount` is not read by anything until #138; a different account signing in imports without asking until then.
- Two devices that push at the same time can briefly leave the account with the lower value of a row; the higher device repairs it on its next pull, as Spec 4 decides ("neither device's local value ever goes down"). No server-side monotonic rule is added: Spec 4 limits the backend to ownership checks.
- `writeSyncAccount` marks a device as synced after #136, so #137 must not read "never synced" as "has no account id" alone (its preferences were never pushed by #136); flagged for that ticket.
- Stats are rebuilt only for categories whose Daily was written by the merge (Spec 4 says "each Daily category"); the result is equal when the incremental stats were right.
- A visibility or focus `refresh()` that lands between a successful sign-out and `stop()` may run the account gone path once more; it is redundant and harmless.
- The account keeps every run pushed to it (no server-side cap); a pull reads only the newest 50, and a cap is deferred.
- Not in the ticket, deferred: refreshing the account menu's display name on every pull.
