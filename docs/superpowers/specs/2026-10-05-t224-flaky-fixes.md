# Ticket spec: Flaky-test fixes

Spec for #224. Tracker: https://github.com/mquesada02/portdle/issues/224. Parent: Spec 6 (tests, CI, and motion), https://github.com/mquesada02/portdle/issues/222 (`docs/superpowers/specs/2026-10-04-spec6-tests-ci-motion.md`, "Unit suite stability"). Map: https://github.com/mquesada02/portdle/issues/212. Causes: https://github.com/mquesada02/portdle/issues/214. Fix decisions: https://github.com/mquesada02/portdle/issues/221. Base branch: `master`. Blocked by: none.

## Problem Statement

The unit suite fails on a loaded machine. The reproduction (#214) found 7 failing tests in 6 files, with 3 root causes. None is a race in app code:

1. Full-`App` tests need 3 to 5 seconds under load and hit the 5-second test timeout.
2. The Blitz tests render the whole app again until the real `Math.random` deals a fitting port. Their work, and so their run time, has no fixed bound.
3. `row-sync.test.tsx` waits 1 second (the default of `findByRole`) for a dialog that needs 1.3 to 1.9 seconds under load.

A flaky suite makes a red result mean nothing.

## Solution

Three changes:

1. Raise the time limits once for the whole suite: Vitest `testTimeout` and `hookTimeout` to 30 seconds, Testing Library `asyncUtilTimeout` to 10 seconds.
2. Give the Blitz page its random source (the engine calls it `rng`) through the App, as `persist` travels. Every Blitz test that rendered the app again until a deal fit now passes a scripted source. The scripted source deals the wanted port on the first render.
3. Add `pnpm test:stress [runs]`. It runs the full suite beside Central Processing Unit (CPU) burners and prints each failed test's name. A burner is a process that loops and uses one full core. A stress run is one full pass of the suite, not a Blitz Run. The merge gate is 5 of 5 green stress runs.

## User Stories

1. As a developer, I want the unit suite to pass on a loaded machine, so that a red run always means a real defect.
2. As a developer, I want one place for each time limit, so that I never tune a limit per test.
3. As a developer, I want a Blitz test to deal the port it needs on the first render, so that its work is fixed and its run time has a bound.
4. As a developer, I want the Blitz page to read its random source from the App, so that a test controls the deal without a stub of `Math.random` that depends on the page's call order.
5. As a developer, I want the production app to keep using `Math.random`, so that real Blitz runs stay random.
6. As a developer, I want `pnpm test:stress` to run the full suite under CPU load, so that I can prove a change keeps the suite stable.
7. As a developer, I want the stress command to print the name of each failed test, so that I do not read the whole log.
8. As a developer, I want the stress command to stop its CPU burners on every exit path, so that no burner stays on my machine.

## Implementation Decisions

- **Time limits**: `vite.config.ts` gets `testTimeout: 30_000` and `hookTimeout: 30_000` in its `test` block. `src/test/setup.ts` calls `configure({ asyncUtilTimeout: 10_000 })` from `@testing-library/react`. A comment in each place says the limits measure machine load, because the tests wait on nothing real. Accepted cost (owner, #221): a hung test takes 30 seconds to fail.
- **Random source in the app**: `App` gets an optional prop `random?: () => number`, with `Math.random` as the default. `createAppRouter` takes a required `random` in its options. `RouterContext` gains a required field `random: () => number`. `createAppRouter` puts it in the router context, as it does `persist`. `main.tsx` does not change: the default covers it.
- **Blitz page**: `BlitzPage` reads `random` from `useRouteContext`, with `persist` and `backend`. Its four `rng: Math.random` call sites (the timeout `reduceBlitz`, `startBlitz`, and the two guess `reduceBlitz` calls) become `rng: random`. The engine does not change: it already takes `rng`.
- **Scripted source (test helper)**: `src/ui/blitz.test.tsx` gets one helper, `dealPrompt(entry)`. It returns a random source for which the engine's shuffle puts `entry` first in the start pool.
  - The helper builds the pool as `startBlitz` does for the default Mixed category: `answerPool(catalog)` without the three Daily answers (`dailyOn("mixed")`, `dailyOn("protocols")`, and `dailyOn("applications")` from `src/test/dailies`), in catalog order.
  - The shuffle runs from the last index down to 1. Call `k` uses index `n - 1 - k`.
  - For the index where `entry` sits, the helper returns the value that picks swap target `0`. For every other index, and after the script ends, it returns `0.999999`, which picks the index itself (no swap).
  - A test creates the source once and passes the same function to every render, because the router is rebuilt when the `random` prop changes.
  - The tests assert the heading port, so a change of the engine's shuffle fails them at once.
- **Tests that change**: the four Blitz tests that used `startInvertedUntil` or `startInvertedWhere`:
  - "unique inverted heading shows the port number only": deals the first non-crowded Entry of the pool; still asserts the heading and that no crowded blurb shows.
  - "crowded inverted heading shows that port's blurb": deals the first Entry of the pool on a crowded port; still asserts one of that port's blurbs shows.
  - "an Inverted miss on a unique port records the prompt as Missed and the pick as Identified": deals a unique-port entry; the prompt Entry is known, so the test reads it from the `entry` it passed to `dealPrompt`, not from the catalog by port.
  - "a same-port Inverted pick records the prompt as Missed and the pick as Identified": deals a crowded-port Entry, then picks a sibling on the same port that is not the dealt Entry. The pick is always a same-port miss, so the 10-attempt loop and its "could not produce a same-port miss" error go away. The test still asserts the pick is Identified, and exactly one sibling is Missed and fresh.
  - `startInvertedUntil`, `startInvertedWhere`, and `startInvertedSamePortMiss` are removed. The tests pass the new `random` prop through `renderBlitz`, which gains an optional `random` option. `startInvertedFake` takes a `random` argument and forwards it; its order stays the same: render, click "Inverted", start fake timers, click "Start".
- **Stress command**: `pnpm test:stress [runs]` runs `tsx scripts/test-stress.ts`.
  - `runs` defaults to 5. A value that is not a positive integer exits non-zero with one message.
  - Before each run, the script starts `2 × os.availableParallelism()` burners (`process.execPath -e "for(;;){}"`, with ignored output).
  - It stops the burners after the run. This also holds after a thrown error, and after SIGINT or SIGTERM.
  - A run is `pnpm exec vitest run --reporter=json --outputFile=<file>`, with the file in `os.tmpdir()`.
  - A run passes only if Vitest exits with 0 and the report parses. Otherwise the run fails. The script then prints the exit code, and each failed test as `<file> › <full name>`.
  - The script runs every run, even after a failure. It prints `<passed> of <runs> runs passed`. It exits non-zero if any run failed.
  - The pure parts (argument parsing and failed-test extraction from a JavaScript Object Notation (JSON) report) live in `scripts/test-stress-core.ts`, with a Vitest test beside them, as `scripts/e2e-env.ts` does.
- **Type check**: `tsconfig.node.json` lists its files one by one, so `scripts/test-stress.ts` and `scripts/test-stress-core.ts` join its `include` list. The Vitest test file beside them stays out, as the other `scripts/*.test.ts` files do.
- **Proof**: the pull request (PR) body holds the output of `pnpm test:stress` with 5 of 5 stress runs green. `pnpm lint`, `pnpm typecheck`, `pnpm test`, and `pnpm build` also pass. No Continuous Integration (CI) job runs the stress loop (owner, #221).

## Testing Decisions

- A good test here asserts what the player sees. The Blitz tests keep their assertions and change only how the deal is set up.
- **Blitz tests**: the four tests above, with a scripted source. They prove the page takes its source from the App, because a real `Math.random` could not deal the needed port on the first render every time.
- **Default source**: no new test. `main.tsx` and every other test that omits `random` keep the default, and the existing Blitz tests cover real use.
- **Stress script**: a Vitest test for argument parsing (default 5, positive integer, rejects 0, a negative number, and text) and for failed-test extraction (a report with one failed test gives one line; a green report gives none).
- **The loop itself**: `pnpm test:stress` 5 of 5, run by the worker, is the acceptance check for the time limits and the Blitz change. Before the fix, the loop failed 3 of 3 runs (#214).
- **Burner cleanup (story 8)**: one manual check. Press Ctrl+C during a stress run, then confirm with `pgrep -f 'for(;;){}'` that no burner stays. No automated test covers it.
- Prior art: `scripts/e2e-env.test.ts` for a pure helper in `scripts/`.

## Out of Scope

- A separate fix for `name-confirm.test.tsx`: it never failed (#214).
- A CI stress job, a weekly job, or stress on every PR (rejected, #221).
- Rewriting slow tests to be cheaper, running fewer Vitest workers, and setting per-test timeouts (rejected, #221).
- Changes to `e2e/`, the Playwright configuration, the CI workflow, the server store, and the Supabase adapter: other tickets own them.
- Other uses of `Math.random` in `src/` outside the Blitz page.
