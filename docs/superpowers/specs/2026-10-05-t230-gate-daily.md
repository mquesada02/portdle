# Ticket spec: Gate for the Daily, Archive, and History

Spec for #230. Tracker: https://github.com/mquesada02/portdle/issues/230. Parent: Spec 6 (tests, CI, and motion), https://github.com/mquesada02/portdle/issues/222 (`docs/superpowers/specs/2026-10-04-spec6-tests-ci-motion.md`, "Screenshot gate: data", "Screenshot gate: freezing frames", "Screenshot gate: matrix and engines"). Map: https://github.com/mquesada02/portdle/issues/212. Gate tracer: `docs/superpowers/specs/2026-10-05-t227-gate-tracer.md` (#227, on master). Motion durations: Spec 3, "Durations and easing" (`docs/superpowers/specs/2026-09-13-spec3-motion-polish.md`). Base branch: `master`. Blocked by: #227 (done).

## Problem Statement

The gate from #227 guards one motion (the tile pop) and one screen (the fresh Daily). A change to any other Daily, Archive, or History motion or screen reaches review only when the owner opens the site.

## Solution

Add gate tests for the rest of the Daily, Archive, and History motions and screens, in Chromium, with the helpers and fixtures of #227. Each motion gets a frame sequence at fixed times. Each screen gets one frame at rest. The tests run on the full matrix (375 × 812 and 1024 × 768, light and dark, and reduced motion for every motion). A new `gate/state.ts` holds the small helpers that these tests share: stored game state, a held Global stats read, and a motion log. The shared gate files get small additive edits to two files (see "Shared files"). No app code changes.

## User Stories

1. As the owner, I want the row shake as a frame sequence, so that a change to its keyframes or its duration fails the gate.
2. As the owner, I want the divider draw and the delayed Reveal rise as one frame sequence, so that the start of the rise (at 250 ms) and the end of the draw (at 300 ms) are both in the frames.
3. As the owner, I want the Miss popover open and the Miss popover close as two frame sequences, so that the 120 ms enter and the 80 ms exit are guarded.
4. As the owner, I want the Daily switcher change and the History switcher change as frame sequences, so that the `switcher` view transition is guarded.
5. As the owner, I want a screen change by the Nav (Daily to History) as a frame sequence, so that the `screen` view transition and the Nav color change are guarded.
6. As the owner, I want the Archive list and an Archive board at rest as frames, so that the Archive screens are guarded. The route changes into the Archive have no frame sequence: no motion plays there (see Author calls, call 6).
7. As the owner, I want the How-to dialog open and close as frame sequences, so that the 150 ms enter, the 100 ms exit, and the backdrop are guarded.
8. As the owner, I want the Daily won, the Daily lost, the Archive list, an Archive board, History, and the error panel each as a frame at rest, so that these screens are guarded. The fresh Daily at rest already exists (#227).
9. As the owner, I want every frame time to be a fixed number of milliseconds from today's durations, so that a changed duration or easing changes the frames.
10. As the owner, I want every motion to run at 375 × 812 and 1024 × 768, in light and dark, so that the matrix of Spec 6 is proven.
11. As a player who asked for reduced motion, I want every motion to play no animation, so that the setting is guarded. Each motion test runs with reduced motion and takes one end frame.
12. As an agent, I want each test to fail on a request with no stub, so that a frame never depends on an unseen request (the #227 fixture already does this).

## Implementation Decisions

- **Seams**: the stub build in a real browser, as in #227. The tests assert frames. The helpers in `gate/state.ts` are test code, not pure code. The five-run check in Testing Decisions proves them.
- **Files**: `gate/daily-motion.spec.ts` (the motions), `gate/daily-screens.spec.ts` (the screens at rest), `gate/state.ts` (shared helpers). The tests reuse `gate/fixtures.ts`, `gate/freeze.ts`, `gate/stub.ts`, and the fixtures. `gate/daily.spec.ts` changes by one line: it imports `isReduced` from `gate/state.ts`, not a copy of its own.
- **Data**: the Daily fixtures of #227 (2026-10-10; Mixed is SSH, port 22; Protocols is FTP, port 21). The Schedule fixture has rows from 2026-10-04, so the Archive lists six past days. No new fixture file.
- **Stored game state** (`gate/state.ts`, `seedDailies`): an init script that writes `portdle:v1:daily:<category>:<date>` records (the `DailyPersist` shape: a `status` of `won`, `lost`, or `playing`, the `guesses`, and `late: false`) to `localStorage`. It writes only when the session has not written yet (a `sessionStorage` marker), so a reload keeps the progress that the test makes. The tests use these records:
  - Won: Mixed 2026-10-10, one correct guess (22).
  - Lost: Protocols 2026-10-10, six missed guesses of two digits that are not 21, with identified entries where the catalog has one.
  - One identified miss for the Miss popover: Mixed 2026-10-10, port 80 (HTTP), `identified: { id: "http", name: "HTTP", port: 80 }`.
  - For the Archive list and History: Mixed 2026-10-09 won, Protocols 2026-10-09 lost, Applications 2026-10-08 won, and the Mixed and Protocols records of 2026-10-10.
  - Every guess record has an `identified` field (a value or `null`), as `isDailyPersist` requires. The Won guess has `identified: null`.
- **Held Global stats read** (`holdGlobalStats`): a page-level route. It runs before the context route of the stub. It answers the `daily_global_stats` request only after the test calls the returned release function. Then it falls back to the stub. A finished Daily mounts the Global stats, which load after the finish and change the page height. The held read keeps the page the same during a frame sequence. Each test that holds the read releases it before it ends. The release lets the request reach the stub, so the check for requests with no stub still sees only requests that have a stub. The reduced-motion test of the Daily finish holds the read too, so its end frame shows the same state.
- **Clock**: the clock stays installed. Two motions need a paused clock, because a page timer would change the page while the animations are paused. The first is the Miss popover close: an 80 ms timer unmounts the panel. The second is the Daily finish: a 250 ms timer scrolls the page to the Reveal. A new `pauseClock` step in `freeze.ts` calls `page.clock.pauseAt` one second ahead. The test calls it after `waitForQuiet` and after all typing, and before the interaction, because the jump fires the timers that are due in that second. A paused clock stops the page's `requestAnimationFrame`, which the frame sync of `shootMotion` uses. With the option `pausedClock: true`, `shootMotion` syncs with the browser's own `requestAnimationFrame`. `gate/fixtures.ts` saves it as `window.nativeRaf` before it installs the clock. Without the option, the sync does not change, so the frames of #227 stay the same.
- **Targets**: the freeze helper waits for the named target. The targets are: `shake`; `draw` (the Reveal rise, a second animation with a 250 ms delay, is paused with it, because both run from the start); `popover-in`; `popover-out`; `::view-transition-new(switcher-content)` for both switchers (the Daily board and History's two segments carry the `switcher-content` name); `::view-transition-new(screen)` for the Nav screen change; `transition:opacity` for the dialog (a new form of target: a CSS (Cascading Style Sheets) transition by property name; it matches the dialog and its `::backdrop`, and `shootMotion` pauses both).
- **Frame times** (ms, from today's durations):
  - Row shake, 300 ms, ease-in-out: 0, 60, 120, 180, 240, 300 (the keyframe stops at 20, 40, 60, 80 percent are at 60, 120, 180, 240).
  - Divider draw (300 ms) and Reveal rise (300 ms after a 250 ms delay, so it ends at 550 ms): 0, 140, 250, 300, 425, 550.
  - Miss popover open, 120 ms: 0, 30, 60, 90, 120. Close, 80 ms: 0, 20, 40, 60, 80.
  - Every view transition (150 ms): 0, 40, 75, 110, 150. The Nav and switcher color transitions run for 150 ms, so they are in the same frames.
  - Dialog open, 150 ms: 0, 40, 75, 110, 150. Dialog close, 100 ms: 0, 25, 50, 75, 100.
- **Frames at rest of a finished Daily**: the won and lost frames mount the Global stats. The test waits until the Global distribution shows (the fixture has the rows of 2026-10-10), then takes the frame. The Archive board frame uses an unplayed Daily (Applications, 2026-10-09, which has no stored record), so it mounts no Global stats.
- **Frame names**: `<test name>-<time>ms` per frame, and `<test name>-end` for the one frame with reduced motion (the project name already says `reduced`). A frame at rest is a frame of a screen with no motion. An end frame is the one frame of a motion test with reduced motion. The test names are `daily-row-shake`, `daily-finish`, `daily-popover-open`, `daily-popover-close`, `daily-switcher`, `history-switcher`, `nav-screen-change`, `how-to-open`, and `how-to-close`. The divider draw is the line above the Reveal. Screens: `daily-won`, `daily-lost`, `archive-list`, `archive-board`, `history`, `error-panel`.
- **Frame shape**: frames of the Daily finish and every screen at rest use `fullPage: true`, because the Reveal and the long lists are below the first screen. A new option `fullPage` of `shootMotion` passes it on. The other frames show the viewport.
- **Reduced motion**: a motion test with reduced motion does the interaction, waits until the page is ready, asserts that the motion log is empty, and takes the end frame. The motion log (`installMotionLog` before the page loads, `motionLog` after) collects the `animationstart` and `transitionrun` events of the document. It proves that no animation started, also one that has ended before the check, which a check of `document.getAnimations()` cannot prove. A test that pauses the clock does not pause it with reduced motion, because nothing needs it. The screen tests at rest run only without reduced motion, as `daily-fresh` does.
- **One sequence per test**: `shootMotion` pauses the running animations and never resumes them, so a view transition stays unfinished and a closing dialog stays open after it. Each frame sequence is its own test with its own page. Before a sequence, the test reaches its start state without `shootMotion`: it opens the popover or the dialog, and so on.
- **Interactions**:
  - Row shake: click the first digit slot, then press the Enter key with no digit (the message "Not enough digits." shows, the row shakes).
  - Divider draw and Reveal rise: type 22, press Enter, with the clock paused and the Global stats held.
  - Miss popover: click the trigger (the entry name in the row caption) for the open test. For the close test, open the popover first, wait for no running animation, pause the clock, then press Escape inside the interaction.
  - Daily switcher: click Protocols in the Daily switcher. History switcher: click Blitz in the History switcher (the Blitz segment shows "No runs yet."; Blitz runs belong to #231).
  - Screen change: click History in the Nav.
  - Dialog: click "How to play" (open test). In the close test, open the dialog first, wait for no running animation, then click "Got it".
  - Error panel: a page-level route aborts the `catalog_entries` read, so the Daily shows the panel (the message "Portdle's server isn't answering. Try again in a moment."). The test waits for the message text, then for no running animation, takes the frame, and asserts that the message is still visible. A retry that starts on `focus` or `online` would show "Loading..." again, and this assert catches it.
- **Shared files** (small, additive edits to two files): `gate/freeze.ts` gets the `transition:` target form, the `pausedClock` and `fullPage` options, `pauseClock`, a color tolerance for in-flight frames, a 100 ms wait for late-starting animations, and a 10 second wait for a start (see "Owner decisions during implementation"); `gate/fixtures.ts` saves `window.nativeRaf` before the clock install. Rebase on `origin/master` right before the pull request, as the other Spec 6 gate tickets (#231, #232, #233) touch these files.

## Testing Decisions

- A good test drives the stub build as a player does and asserts frames and, with reduced motion, the motion log. The gate is its own test.
- Checks, run and recorded in the pull request:
  - `pnpm gate:capture`, then `pnpm gate` with the same baseline, passes with no difference, five times, inside the pinned Docker image. #227 ran twice. This ticket has more frames, so it runs five times.
  - A frame of each sequence differs from the frame at 0 ms and from the end frame (look at one mid frame of each sequence in its image file; the Nav link color at 75 ms differs from the colors at 0 ms and 150 ms).
  - The reduced-motion tests fail when the motion log is not empty (checked once in a scratch run that forces an animation with reduced motion on, not kept).
  - `pnpm lint`, `pnpm typecheck`, `pnpm test`, and `pnpm build` pass.
- No unit tests: the new code is test code and tiny helpers.
- Prior art: `gate/daily.spec.ts`, `gate/freeze.ts`, `e2e/signed-out.spec.ts`.

## Out of Scope

- Blitz, Codex, and signed-in screens (#231, #232), the Rounds disclosure (#233), the theme crossfade, and WebKit and Firefox.
- A separate frame sequence for the Nav and switcher colors (they are in the frames of the screen and switcher changes), and for the hover color.
- A change to app code.

### Owner decisions during implementation (2026-10-05)

1. **Color tolerance for in-flight frames** (a gate-wide rule in `shootMotion`, which replaces the first approval of a per-sequence option). Every frame between the first and the last time of a sequence is compared with a color threshold of 0.02. The first frame, the last frame, and the frames at rest stay exact. `maxDiffPixels` stays 0 everywhere. This also covers the tile-pop frames of #227. Reason: flakes reproduced in the pinned Docker image, with the five-run check and with `--repeat-each` on one test. Dialog close at 25 ms: two edge pixels one level off, 2 failures in 30 runs and 2 in 40, the same two pixels each time, and a wait of 150 ms before the shot did not help. Daily finish at 300 ms (375 px, light): 6 pixels, at most 2 levels off, the same pixels in 5 of 5 compare runs against a baseline that another run captured. The tile-pop frames of #227 at 0 and 40 ms (1024 px) differed by 3 pixels in the same pixel columns between two captures, so the master gate has this noise too. A threshold of 0.02 ignores a difference of one to three levels. A move of one pixel, or a color change of about ten levels or more, still fails. One exception, kept because the owner decision allows it for a frame that is not in flight: the two switcher view transitions (Daily and History) also take the tolerance on their first frame (the option `toleranceOnFirstFrame`). That frame, the tab label, drew one level off (27 and 199 pixels) in 2 of 2 five-run checks on the rebased code, and the cause is not found. The Nav screen change and the dialogs keep the exact first frame.
2. **Wait for a start**: the helper waits 10 seconds (not 2) for the target animation to start, because a loaded runner starts it late (one Daily switcher test timed out at 2 seconds under load). This follows the owner decision of #221 on wall-clock budgets under load.

### Fact found during implementation: late-starting animations

The color transitions of the Nav and the switchers can start a frame or two after the target animation. The helper paused only what ran at the moment it saw the target, so a late transition kept running and the frames at 0 to 110 ms changed from run to run (Nav screen change, 1024 px dark, a large difference). The helper now waits 100 ms after the target, then pauses every animation that runs. The cost is small: the paused target does not move, and every paused animation gets the frame time.
