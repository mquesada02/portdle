# Ticket spec: Local Supabase stack and SQL tests in CI

Spec for #183. Tracker: https://github.com/mquesada02/portdle/issues/183. Parent: Spec 5 (Dailies from the backend), https://github.com/mquesada02/portdle/issues/181 (`docs/superpowers/specs/2026-09-30-spec5-dailies-backend.md`, "Development and CI"). Map: https://github.com/mquesada02/portdle/issues/169, decision https://github.com/mquesada02/portdle/issues/180. Base branch: `spec5`.

## Problem Statement

Portdle will need the backend to show a Daily, but a developer has no backend to run against except the live project, and no SQL test runs unless the owner pastes it into the live SQL editor. A migration mistake reaches review only if the owner remembers to run the tests by hand.

## Solution

The repository holds the configuration of the Supabase CLI local stack (Docker) and a seed file. `pnpm dev` starts or reuses the stack, applies any new migration, and starts the dev server pointed at the stack. A new CI job starts the same stack (without Studio and the mail catcher) on every pull request and runs every SQL test file against it. A failing assertion in any test file fails the job.

The local stack enables email and password sign-in with one seeded test user whose display name is confirmed. The live project keeps email sign-in off.

## User Stories

1. As a developer, I want `pnpm dev` to start the local stack when it is not running, so that I need no separate setup command.
2. As a developer, I want `pnpm dev` to reuse a stack that already runs, so that a restart of the dev server is fast.
3. As a developer, I want `pnpm dev` to apply migrations that the stack has not seen, so that a stack started before a `git pull` is not out of date.
4. As a developer, I want `pnpm dev` to point the app at the stack's API URL and its publishable key, so that I never copy a key by hand.
5. As a developer, I want `pnpm dev` to stop with a clear message and no dev server when Docker or the stack cannot start, so that I do not debug a half-working app.
6. As a developer, I want the local stack to enable email and password sign-in with one seeded, name-confirmed test user, so that a signed-in flow can run with no OAuth provider.
7. As a developer, I want the seed file to hold only that user, so that the catalog and the Schedule come from migrations and not from a second source.
8. As a developer, I want the local stack to behave like the live project for table privileges ("Automatically expose new tables" off), so that a SQL test passes locally only when it passes live.
9. As a developer, I want one command, `pnpm test:sql`, to run every SQL test against the local stack, so that I run in one step what CI runs.
10. As a developer, I want the SQL test runner to stop at the first failed assertion and exit non-zero, so that a failure never hides behind later passes.
11. As a developer, I want the runner to skip `row-sync-cleanup.sql`, so that the owner's cleanup script never runs as a test.
12. As a reviewer, I want CI to run the SQL tests against a fresh local stack on every pull request, so that a migration mistake fails the pull request.
13. As a reviewer, I want the SQL job to be separate from the build job, so that each shows its own result.
14. As the owner, I want the live project to keep email sign-in off, so that the local stack's test user and password never exist there.
15. As the owner, I want the CLI version pinned in `package.json` and in the CI action at the same version, with a comment in each file that names the other, so that both run the same stack and a bump touches both.

## Implementation Decisions

- **Local stack configuration** (`supabase/config.toml`, created by `supabase init`, then edited): `project_id` is `portdle`. `api.auto_expose_new_tables` is `false`, matching the live project ("Automatically expose new tables" off; every migration already grants explicitly). With the CLI default (`true`) the Spec 4 tests `preferences`, `row-sync`, and `leaderboards` fail on their "no delete grant" and "anon cannot read" assertions. This was measured on a prototype stack. Services Portdle never uses are disabled: realtime, storage, edge runtime, analytics, and imgproxy and vector with them. Studio and the mail catcher stay at their defaults. Email sign-in stays enabled and `enable_confirmations` stays `false`. No other auth setting changes.
- **Seed file** (`supabase/seed.sql`): one `auth.users` row and its `auth.identities` row for `test@portdle.local` with a fixed local password stored as a bcrypt hash made by `crypt`, then one `update` setting `name_confirmed` to true on that user's `accounts` row (the accounts trigger creates the row). The display name is `Local Tester`. The header comment names the email and the password and says the file is for the local stack only. The file holds nothing else: the catalog and the Schedule come from migrations (spec).
- **CLI**: `supabase` 2.119.0 is a pnpm devDependency, pinned exactly, with `pnpm.onlyBuiltDependencies` in `package.json` listing `supabase`, so its install script downloads the binary (the repo has no `pnpm-workspace.yaml`). CI installs the same version with the pinned `supabase/setup-cli` action and runs no `pnpm install` in the SQL job.
- **`pnpm dev`**: the `dev` script runs a small TypeScript script (`scripts/dev.ts`, run with `tsx`) that (1) runs `supabase start`, which does nothing when the stack runs, (2) runs `supabase migration up --local`, which applies only new migrations and keeps data, (3) reads `API_URL` and `PUBLISHABLE_KEY` from `supabase status -o env`, (4) starts Vite with `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` set to those two values and passes the exit code through. If step 1, 2, or 3 fails, the script prints one message that says Docker must run and shows the CLI's error, exits non-zero, and does not start Vite. The stack keeps running when Vite exits; `supabase stop` stops it. The script has no generator step: ticket #185 adds it. The script uses the publishable key, as the live project does, not the legacy JWT key. A dev server that loses the stack after it started shows the app's behavior with a backend that does not answer (Spec 5, story 70).
- **SQL test runner** (`scripts/run-sql-tests.sh`, run as `pnpm test:sql`): for each `supabase/tests/*.sql` file in name order except `row-sync-cleanup.sql`, it runs `psql` with `ON_ERROR_STOP=1` and stops at the first non-zero exit with that exit code. The database URL comes from `DATABASE_URL`, defaulting to the local stack (`postgresql://postgres:postgres@127.0.0.1:54322/postgres`); the override is for a developer whose stack runs on another port. `pnpm test:sql` needs a local `psql` binary (the PostgreSQL client). It prints each file name before its run. With no matching file it exits non-zero, so a path error never passes silently.
- **CI** (`.github/workflows/ci.yml`): a new job `sql-tests` with the same triggers as `build`, `permissions: contents: read`. Steps: checkout, `supabase/setup-cli` at 2.119.0, `supabase start -x studio,mailpit` (the CLI's container names), `scripts/run-sql-tests.sh`. `psql` is on the runner image. The `build` and `deploy` jobs and `pnpm gen:schedule --check` stay as they are. Later tickets (#185, #193) add the generator run and the end-to-end suite to this job.
- **Test files stay unchanged.** Their header comment "Owner-run in the Supabase SQL editor" stays true for the owner's use; CI runs them the same way as a second place. (Spec 5's audit: every file already raises on failure.)
- **Failing assertion check** (owner decision): once locally and once in CI, then removed. Locally, a temporary failing file in `supabase/tests` must make the runner exit non-zero; the file is deleted. In CI, one throwaway commit adds a failing assertion to the pull request branch; the `sql-tests` job must go red; the commit is then removed by a `--force-with-lease` push of this branch only (owner approval; never `spec5` or `master`). Nothing failing is left in the branch.

## Testing Decisions

- A good test here runs the real thing: the real stack, the real migrations, the real test files, and checks the exit status and the visible effect. There is no mock of `psql` or of the CLI.
- Highest seam: the local stack itself. The checks, run once and recorded in the pull request:
  - a stack started from scratch applies all migrations and the seed with no error;
  - every SQL test file passes through `pnpm test:sql` and the script's exit code is 0;
  - the seeded user signs in through the local auth API with email and password and gets a token, and its `accounts` row has `name_confirmed` true;
  - `anon` reads nothing from the player tables; the seed holds exactly one `auth.users` row;
  - `pnpm dev` with a stopped stack starts it and serves the app with the stack's URL and key (the Vite server answers and the page's bundle holds the local URL);
  - `pnpm dev` with Docker unavailable exits non-zero with the message and starts no Vite;
  - the failing-assertion check described above, locally and in CI;
  - the CI `sql-tests` job is green on the pull request.
- Unit test: `scripts/dev.ts` keeps its one piece of logic, reading `API_URL` and `PUBLISHABLE_KEY` from the CLI's `status -o env` text, in a small pure function with a Vitest test beside it (prior art: `scripts/gen-schedule.test.ts`, `scripts/display-name-sql.test.ts`).
- `pnpm lint`, `pnpm typecheck`, `pnpm test`, and `pnpm build` still pass.

## Out of Scope

- The generator run in dev and CI, and the generator role (#184, #185, #194).
- The Playwright suite (#193) and any browser test.
- New SQL tests; they come with the tickets that add the schema (#184 and later).
- Any change to the existing migrations, SQL test files, or application code.
- Applying anything to the live project; the live project's email sign-in setting is not touched (it is a project setting, off by default). Nobody runs `supabase config push` or `supabase db push --include-seed` against the live project: they would apply the local email setting and the seed user.
- An owner runbook (#194) and a README section.
- Removing `pnpm gen:schedule --check` from `build`.

## Further Notes

- Author calls, all accepted by the owner during ticket work (2026-09-30 and 2026-10-01): CLI as a pinned devDependency with the pinned setup action in CI; `pnpm dev` starts the stack, applies new migrations, and fails hard with no Vite when the stack cannot start; the runner script and `pnpm test:sql`; the failing-assertion check done locally and in CI with one approved force push of this branch; `project_id` `portdle`; unused services disabled; studio and the mail catcher left at default; the seed's email, password, and display name; a separate `sql-tests` job; `origin/spec5` merged into the branch before the pull request; no new documentation beyond this spec and script comments (`AGENTS.md` lists no commands); the pull request title `feat(dev): local Supabase stack and SQL tests in CI`.
- Facts checked on a prototype on 2026-09-30 with CLI 2.119.0: the six migrations and a seed apply on `supabase start`; the seeded user signs in with email and password; all six SQL tests pass with `psql` and `ON_ERROR_STOP` once `auto_expose_new_tables` is `false`.
- The local stack's ports (54321 API, 54322 database) are the CLI defaults. A machine that already uses them must stop the other service.
- The local stack's keys and the seed password are public, well-known local values and not secrets.
