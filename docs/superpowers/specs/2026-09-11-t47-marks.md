# Spec: Marks, tiles, tracker strip

Spec for #47. Tracker: https://github.com/mquesada02/portdle/issues/47

## Problem Statement

A player who commits a Daily try today only learns whether the whole guess was right or wrong. A miss row shows the identified service name (or "Not in this catalog.") but says nothing about the digits themselves, so there is no way to close in on the port by deduction. The parent spec ("Daily digit feedback, fuzzy search, Help removal", issue #44) decided the Daily should become deducible the way Wordle is, through a per-digit mark on every committed row and a tracker strip summarizing what every digit has revealed so far. This ticket builds that mark and tracker strip.

## Solution

Every digit of a committed Daily row gets a mark: placed when it is the right digit in the right position, present when it exists in the port but at a different position, or absent when it does not exist in the port at all, using Wordle's rule for repeated digits. Each tile renders its mark (green for placed, yellow for present, gray for absent) and exposes the mark as accessible text in the form "digit, mark", with present tiles carrying an extra visible cue so the distinction never depends on color alone. A tracker strip of the digits 0 to 9 sits under the board, display-only, showing each digit's best mark across every committed row (placed beats present beats absent) or "unknown" for a digit never typed; it disappears once the Daily is won or lost. Marks are computed at render time from data already stored (the committed port and the answer), so nothing about what gets persisted changes, and a reload shows the identical marks. Row captions, the try counter, motion, the miss popover, and Blitz are all unaffected.

## User Stories

### Marks

1. As a player, I want each digit of a committed row marked placed, shown green, when it is the right digit in the right place, so that I can lock in what I know.
2. As a player, I want a digit marked present, shown yellow, when it exists in the port but not at that position, so that I can move it next try.
3. As a player, I want a digit marked absent, shown gray, when it is not in the port at all, so that I stop trying it.
4. As a player who types a digit twice, I want the marks to follow Wordle's repeated-digit rule, so that two present marks never promise two copies that are not there.
5. As a player, I want a winning row to be all placed, so that the finish reads the same as Wordle.
6. As a player, I want the row caption (identified service name or "Not in this catalog.") kept on the row as today, so that knowledge still helps alongside deduction.
7. As a player, I want a leading zero I typed to be marked like any other digit against the port padded to the slot count, so that the marks and my typed row agree.
8. As a colorblind player, I want each mark to be readable without color, through accessible text on each tile and a visible difference beyond hue for present, so that the deduction is not color-only.
9. As a player on a reload, I want every committed row to show the same marks as when I played it, so that refreshing costs nothing.
10. As a player, I want the marks to show only on the Daily, so that Blitz stays a one-shot knowledge test.

### Tracker strip

11. As a player, I want a row of the digits 0 to 9 under the board, so that I can see at a glance which digits are dead, present, or placed.
12. As a player, I want each tracker strip digit to show its best-known mark across all my rows, placed over present over absent, so that a digit never looks worse than the board proved.
13. As a player, I want untried digits in the tracker strip to look neutral, so that unknown is distinct from absent.
14. As a player, I want the tracker strip to be display-only, so that I do not tap it expecting input.
15. As a player, I want the tracker strip hidden once the Daily is finished, so that the reveal is the focus.

### Maintainer

16. As a maintainer, I want per-digit marks computed by a pure engine function from the typed digits and the answer's digits, so that persistence does not change.
17. As a maintainer, I want the mark function to live apart from the existing guess function's public result, so that the persisted guess shape and the Daily/Blitz guess contract are untouched.
18. As a maintainer, I want the present-tile visual cue to be a non-textual marker, so that it never changes what a tile's visible text reads and existing text-based assertions keep passing.

## Implementation Decisions

### Marks

- A mark is one of placed, present, or absent. A pure function in the engine layer takes a typed digit string and the answer's port padded to that same length and returns one mark per position, independent of any other guess logic. It is a new, small module of its own rather than an addition to the existing guess function's public result, so that function's return shape does not change and the persisted guess record does not change.
- The rule is Wordle's, in two passes. First pass: for every position where the typed digit equals the answer digit at that position, mark it placed and remove that answer digit from the pool available to the second pass. Second pass, left to right over the remaining positions: mark a digit present if the pool still holds an unconsumed copy of it, and consume that copy; otherwise mark it absent. A digit typed twice when the answer holds only one copy gets exactly one present or placed mark and one absent mark, never two. A padded leading zero is just another digit to this rule; it is never treated specially.
- Marks are derived every time a committed row renders, from that row's stored port (padded to the answer's digit length) and the answer's port (padded the same way). Nothing new is written to the persisted guess record, and a reload recomputes the same marks from the same stored data, so a refresh shows the identical board.
- Each committed-row tile renders its digit's mark: green for placed, yellow for present, the existing miss gray for absent. Every tile carries its mark as accessible text in the form "digit, mark" (for example "2, placed"), and a present tile additionally carries a visible cue that does not depend on hue — a non-textual marker (for example a small dot or a distinct border), never an extra character appended to the tile's own visible digit, so the tile's plain-text reading stays just the digit. A winning row's typed digits equal the answer's digits at every position, so it comes out of the same rule as all placed; there is no separate "correct" rendering path. Row captions, the try counter, the pop-on-commit and shake-on-reject motion, and the miss popover keep their current behavior untouched. Blitz's default orientation never calls the mark function and never renders marks; it keeps its one-shot, no-marks behavior exactly as today.

### Tracker strip

- The tracker strip is a row of the ten digits 0 through 9, rendered under the board, visible while the Daily is being played and removed entirely once the Daily is won or lost. It is display-only: not a button, link, or other focusable control, and not part of the tab order. Each digit's state is the best mark among every occurrence of that digit at every position of every committed row so far — including more than one occurrence of the same digit within a single row, each judged on its own mark — ranked placed above present above absent, so a digit already proven placed anywhere never regresses to a lower state because another occurrence, in the same row or a later one, was marked lower. A digit never typed in any committed row shows a neutral, unknown state and carries the accessible text "digit, unknown" (for example "7, unknown"); a digit that has been typed carries "digit, mark" using the same wording as the tiles. The strip's neutral and mark colors otherwise match the tiles' palette (green for placed, yellow for present, gray for absent).

## Testing Decisions

A good test exercises a public seam with literal inputs and asserts what a pure function returns or what a player can see through accessible roles, names, and text — never class names, inline styles, or other implementation detail. Expected values are literals worked out by hand, the way the existing guess, share, and search engine tests already do.

- **Engine seam**, new tests alongside the new mark module, in the style of the existing guess tests: `2233` typed against answer `3322` returns present for all four positions; `1230` typed against answer `1200` returns placed, placed, absent, placed; a digit typed twice where the answer holds only one copy returns one placed-or-present mark and one absent mark for that digit; typed digits identical to the answer return all placed; a case with a padded leading zero is marked the same way as any other digit, with the zero landing on whichever mark the rule produces for it.
- **App seam**, in a new test file for this ticket alongside the existing Mixed Daily test file, rendering the app with a memory store, a memory history, and an injected day, in the style of the existing Mixed Daily and daily reveal test files: a committed miss row's tiles expose the expected "digit, mark" accessible text for a known fixture guess and answer; after two committed rows the tracker strip exposes the expected "digit, mark" or "digit, unknown" accessible text for each of the ten digits; the tracker strip is absent from the page after a winning row; the tracker strip is absent from the page after six committed misses (a loss).
- The existing Mixed Daily test file is left alone except where one of its current assertions would fail purely because a tile now carries mark accessible text it did not carry before. The mark's accessible text is additive to a tile, and the present-tile visual cue is non-textual, so no currently-passing assertion in that file is expected to break; the exact accessibility mechanism is an implementer choice, made so the mark's accessible text is reliably exposed to assistive tech. If implementation nonetheless breaks an existing assertion, only that specific assertion is updated, and the reason is recorded in the commit that touches it.
- No new test duplicates coverage the existing guess tests already provide (invalid, duplicate, correct, miss identification): this ticket only adds coverage for the mark function and its rendering.
- No snapshot tests, no visual regression, no Playwright. This ticket is proven done by `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm gen:schedule --check`, and `pnpm build` all passing, in addition to the coverage above.

## Out of Scope

- The share line's per-digit grid (a separate ticket): the share formatter and its existing tests are untouched here.
- Fuzzy search, the Blitz end card's Best number, and Help removal: separate tickets, own files.
- Any change to Blitz's default-orientation behavior, its digit-slot input, or its one-shot scoring.
- Any change to what gets persisted for a Daily guess, to the schedule, or to routes.
- Higher/lower hints or any hint beyond marks and the existing miss identification.
