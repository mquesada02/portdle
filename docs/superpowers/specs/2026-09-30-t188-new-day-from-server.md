# Ticket spec: New day from the server

Spec for #188. Tracker: https://github.com/mquesada02/portdle/issues/188. Parent: Spec 5 (Dailies from the backend), https://github.com/mquesada02/portdle/issues/181 (`docs/superpowers/specs/2026-09-30-spec5-dailies-backend.md`, "New day detection", "No remount on a new day", "A Daily in progress at rollover"). Map: https://github.com/mquesada02/portdle/issues/169. Base branch: `spec5`. Blocked by #186 (merged).

## Problem Statement

An open tab does not move to the next Daily. The app shell holds a device-clock day, refreshed on focus, and a new device-clock day rebuilds the router and every screen. That uses the device clock, which can be wrong, and it throws away a Daily the player is playing. The server's today, loaded once at app start, never changes.

## Solution

The client asks the server for the current Dailies again when the tab regains focus and from one timer that fires at the next UTC midnight by the server's time. A new server today never rebuilds the router. A Daily with a committed try stays on screen until the player leaves. A finished Reveal stays until the player leaves. An untouched Daily moves to the new Daily at once. A Blitz run carries on.

## User Stories

1. As a player with Portdle open at UTC midnight, I want Portdle to ask the server for the new Daily, so that I do not need to reload.
2. As a player who returns to the tab on a new UTC day, I want the new Daily, so that I never play a stale one.
3. As a player mid-Daily at UTC midnight, I want my board to stay on the Daily I started until I finish it or leave it, so that the rollover never takes my game away.
4. As a player who finished a Daily and reads its Reveal at midnight, I want the Reveal to stay until I leave, so that the result does not vanish.
5. As a player on a Daily I have not started at midnight, I want the new Daily at once, so that I never play a stale Daily by mistake.
6. As a player who leaves a Daily after midnight and comes back, I want the new Daily, so that the old one is behind me.
7. As a player mid-Blitz-run at UTC midnight, I want the run to carry on, so that the day change never resets a run.
8. As a player with a wrong device clock, I want the midnight read to follow the server's time, so that my clock never moves the Daily.
9. As a player who switches tabs often, I want a focus read at most once per 30 seconds, so that Portdle does not flood the server.
10. As a player whose network drops after the Daily loaded, I want the loaded screens to keep working when a re-read fails, so that a short outage does not end my game.
11. As a player, I want the next focus to try again after a failed read, so that Portdle recovers by itself for the Dailies (there is no retry timer, so only a focus or the shared retry of #187 recovers; a failed catalog read of the first load is #187's).
12. As a developer, I want a new day never to rebuild the router, so that the account-flow remount stays the only remount.

## Implementation Decisions

- **Server time on the read**: `CurrentDailies` gains `serverNow`, the server's current time in epoch milliseconds. The Supabase adapter takes it from the `server_time` column that the current-Dailies function already returns (#184). The fake `Remote` serves it from a settable field, with a default that gives the fixture day. The adapter parses the timestamptz string with `Date.parse`; a missing, null, or unparseable value (NaN) makes the read fail, like an incomplete row set. The existing adapter test fixtures that use a placeholder `server_time` change to real timestamps. The fake default is noon UTC of its `today`; a test that moves the fake `today` or advances time sets `serverNow` too, because the fake does not follow any clock.
- **Server store**: the existing server store (outside the router) gains `refreshDailies()`, which reads the current Dailies, and `attach()`, which returns one disposer. With no remote (a build with no backend) both do nothing. The store keeps `lastSuccess`, which is null until a read is applied, and then holds the clock time at which the read finished and that read's `serverNow`. A read counts as applied only when its result is stored. There is no retry timer. The first `load()` Dailies read takes the same path as `refreshDailies()`, so the first applied read also arms the timer.
- **Reads and ordering**: each Dailies read gets a sequence number. Only the newest started read may apply its result or set `failed`; an older read that settles later is dropped completely (no value, no `lastSuccess`, no status change). "A read in flight" means the newest started read has not settled. So an older read settling never clears the guard of a newer one. If the newest read fails and no read has been applied yet, the status becomes `failed`; after an applied read, a failure changes nothing. An applied read always stores a new snapshot (`serverNow` changes), and it arms the timer only while the store is attached. The timer-fired read always starts (it ignores the throttle and any read in flight), so a read in flight from before midnight can never keep the old date. If a timer-fired read fails, no timer is left; recovery is the next focus (no throttle block once 30 seconds passed since `lastSuccess`). This follows Spec 5: no retry timer.
- **Catalog reload on a missing entry** (owner decision Q4, 2026-10-02; a deviation from Spec 5, "the focus and midnight reads ask only for the current Dailies"): when a Dailies read succeeds and the catalog is loaded, but an entry id of that read is not in the catalog (looked up by id in the whole catalog), the store reads the catalog once before it applies the Dailies. If that catalog read succeeds, the store applies the new catalog and then the Dailies together. If it fails, the store drops the Dailies of that read, so the shown Daily stays, as for a failed read (the next trigger tries again; `lastSuccess` and the timer are not touched). When the catalog is still loading or failed, there is no check and the Dailies apply as before (the shared retry is #187's). This is one conditional catalog read, never repeated within one refresh.
- **Timer**: one pending timer at a time. After every applied read the store clears the pending timer, then sets a new one for the time from `serverNow` to the next UTC midnight strictly after `serverNow` (at exactly 00:00:00.000 the delay is 24 hours). The timer calls `refreshDailies()`. The timer never decides the date; the server's answer does. A timer that fires early returns the same date, and the store re-arms with the remaining delay, with no minimum; `serverNow` advances with each read, so the delay shrinks to the midnight and cannot loop.
- **Lifecycle**: `attach()` adds the focus and visibility listeners. When a read was applied and no timer is pending (a StrictMode remount, or a read that finished before attach), it arms the timer from `lastSuccess`: its `serverNow` plus the clock time elapsed since it. When no read was applied yet, it arms nothing, and the first applied read does. The disposer removes the listeners and clears the timer. After dispose, an applied read still stores its value but arms no timer; the next `attach()` arms it. The App effect that calls `load()` also calls `attach()` and returns its disposer.
- **Focus read**: `window` `focus` and `document` `visibilitychange` (when visible) call `refreshDailies()` only when no read is in flight and either `lastSuccess` is null or 30 seconds have passed since it (the check is `lastSuccess === null`, never a falsy test, because the fake clock starts at 0). This throttle is separate from the sync pull's throttle: neither blocks the other. The sync module keeps its own listeners. A success after a failed first read makes the Dailies ready. The shared retry is #187's.
- **Injectable clock**: the store takes a clock of the existing sync clock type (set, clear, now) with the system clock as default, so tests use the fake clock. The throttle and the timer use it. The delay to midnight uses `serverNow` from the read, never the device date.
- **App shell**: the device-clock day state and its focus and visibility listeners leave `App`. `createAppRouter` and the router context drop `utcToday`, so a new day never recreates the router. The shell's streak-gap effect (`syncUtcDay`) is deleted from the shell (owner decision, Q1); the `categoryStreakGap` helper stays because the Daily screen still uses it until #189. The optional `utcToday` prop of `App` and the sync module's `utcToday` stay untouched, since they feed only the stats rebuild that #189 deletes. The account-flow remount (`generation`) stays unchanged.
- **Daily screen rollover**: the outer `DailyPage` (the gate that waits for the server data) keeps its own copy of the `{ today, entryIds }` of the day it shows, and a flag `started`, both in component state for the life of the mount. The copy starts from the first ready store value and feeds the board. `started` starts true when the stored record of the shown day for this category has at least one committed try, and the board sets it true through a callback when its first try is committed (so a try held only in memory, after a failed save, counts too). When the store's `today` differs from the copy's, and `started` is false, the screen replaces the copy with the store's value during render (derived state); a typed but uncommitted digit string is dropped by the move. With `started` true it stays on the shown day, with that day's entry id, until the screen unmounts. If only the entry ids change for the same `today` (an owner edit of a Daily), nothing moves; the next mount reads them. Each Daily category is its own route, so another category or another route unmounts the screen, and on return it shows the store's current value. The board keys on the shown date so a move resets the board state.
- **Blitz**: a run in progress is not affected. The run takes the excluded Daily ids when it starts. A test confirms a run keeps going when the server today changes.
- **History and the Codex** keep reading the live store (owner decision, Q2).
- **Owner-accepted deviation from Spec 5**: Spec 5 says "a screen already mounted keeps the data it mounted with and uses the new data on its next mount". Only the Daily screen pins its Daily. Blitz, History, and the Codex keep reading the live store. The owner accepted this on 2026-10-02 (Q2). A Blitz run is safe because it takes its excluded ids at start; History and the Codex only re-render with the new value.
- **Streak transient**: with the shell's streak-gap step gone, a tab open across a missed day shows no day-change reset; a finish still applies the gap on the Daily screen. #189 removes stored stats.
- **Dead code**: `syncUtcDay` in the streak-gap module and its tests become unused here; they are deleted in this ticket with the shell effect, and `categoryStreakGap` stays. Tests that assert the shell's day-change streak reset are removed.
- **Not in this ticket**: the `late` mark, the share line, stats removal, the error panel, the retry button, and the Archive.

## Testing Decisions

- A good test drives the App through the highest seam, with `memoryStore`, the fake `Remote`, and the fake clock, and asserts what the player sees and what the store holds. It never asserts internal calls.
- **Store unit tests** (the injected fake clock, the fake `Remote`): the timer fires at the next UTC midnight by `serverNow`, never by the device date; every successful read replaces the pending timer (the fake clock shows one pending timer, never two); a failed read arms none and leaves a loaded value as it was; the focus read is skipped within 30 seconds of the last success and runs after it; a sync pull inside its own 30 seconds does not block a Dailies focus read, and the reverse; a focus read after a failed first read runs and makes the Dailies ready; a focus read is skipped while a read is in flight; a timer firing during an in-flight read starts a new read and the older result is dropped; a failed timer read leaves no timer, and a later focus recovers; the disposer removes the listeners and clears the timer; a read finishing after dispose arms no timer and a new `attach()` arms it; after one applied read, mount, dispose, mount (StrictMode) leaves one pending timer; a dropped older success followed by a newer failure before any applied read sets `failed`; an older read settling does not clear the in-flight state of a newer read; with no remote, nothing runs.
- **Adapter tests**: `readCurrentDailies` returns `serverNow` as epoch milliseconds from a valid timestamptz, and fails on a missing, null, or unparseable `server_time`.
- **Catalog reload tests** (store and App): a Dailies read with an entry id missing from the loaded catalog reads the catalog once, then the Daily moves to the new answer; a failed catalog reload keeps the shown Daily and a later trigger tries again; with every id present, no catalog read happens.
- **App-level tests** (vitest fake timers and fake `Date`; the App takes no clock, and the store uses the system clock there): a new server today at the timer moves an untouched Daily at once; a Daily with one committed try stays on its Daily and its answer, also when the save failed (the try is held in memory only); a typed uncommitted digit string is dropped when an untouched Daily moves; the same `today` with a changed entry id moves nothing; an existing account-flow remount test (device choice or account deletion) stays green; a finished Reveal stays; leaving to another route and back shows the new Daily; a Blitz run in progress carries on and the router is not rebuilt (a screen's local state survives); a failed re-read leaves the loaded Daily working; a new day by focus works the same as by the timer; a device date that disagrees with the server's moves nothing, and the timer follows `serverNow`.
- Prior art: `server-data.test.tsx` (fake `Remote`, held reads), `sync.test.ts` (fake clock, throttle), `app.test.tsx`, and the Blitz suites.

## Out of Scope

- The `late` mark, the share line, global stats, and the stored-stats removal (#189).
- The shared error panel, the "Try again" button, and the `online` event (#187).
- The Archive and the History changes (later tickets).
- Any repeating poll; the midnight read is one timer per day.
- A read timeout (#187 adds the 10-second limit); until then a hung read keeps the focus guard closed, and the timer-fired read ignores that guard.
