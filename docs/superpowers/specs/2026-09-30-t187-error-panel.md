# Ticket spec: Error panel and retries

Spec for #187. Tracker: https://github.com/mquesada02/portdle/issues/187. Parent: Spec 5 (Dailies from the backend), https://github.com/mquesada02/portdle/issues/181 (`docs/superpowers/specs/2026-09-30-spec5-dailies-backend.md`, "Client: loading and today", "Error panel"). Map: https://github.com/mquesada02/portdle/issues/169. Builds on #186 (`docs/superpowers/specs/2026-09-30-t186-daily-from-server.md`). Base branch: `spec5`.

## Problem Statement

When the catalog or the current Dailies cannot load, the Daily, Blitz's Play tab, and the Codex show one plain line, "Could not load puzzles.", with no retry and no cause. A player must reload the page. A read can also hang with no end. History lists no Daily rows after a failed read, so the player's saved record looks empty.

## Solution

One shared error panel replaces the temporary line. It says why nothing loaded (offline, or the server does not answer) and has a "Try again" button. Portdle also retries by itself when the connection comes back and when the player returns to the tab. A read that fails or takes over 10 seconds counts as failed. A screen that has loaded never loses its content to a later failed read. On Blitz, the panel replaces only the Play tab's content. History lists the player's saved finished Dailies without names until its reads succeed.

## User Stories

1. As a player who is offline, I want the Daily, Blitz's Play tab, and the Codex to say "You're offline. Portdle needs a connection to load puzzles.", so that I know why nothing loads.
2. As a player who is online when the server does not answer, I want "Portdle's server isn't answering. Try again in a moment.", so that I know my connection is not the problem.
3. As a player on the panel, I want a "Try again" button, so that I can retry when I choose.
4. As a player on the panel, I want Portdle to retry when my connection comes back, so that it recovers without my help.
5. As a player on the panel, I want Portdle to retry each time I return to the tab, so that it recovers without my help.
6. As a player, I want a retry to show the loading line until it ends, so that I see that something is happening.
7. As a player, I want a read that takes over 10 seconds to count as failed, so that I never wait with no end.
8. As a player whose screen has loaded, I want a later failed read to change nothing, so that my game keeps working.
9. As a player on Blitz, I want the Play and Leaderboards tabs to stay, and the panel only in the Play tab, so that the Leaderboards tab keeps working.
10. As a player on the Codex, I want the panel only when the catalog fails, so that a failed current-Dailies read does not hide the Codex.
11. As a player on the panel, I want the nav to stay, so that I can still reach History.
12. As a player who reloads while offline in the middle of a game, I want the panel, and my saved tries kept, so that they come back when the network returns.
13. As a player offline, I want History to list my saved finished Dailies with category and date, so that my record is still there.
14. As a player, I want History to fill in the names and ports when its reads succeed, so that the list is complete again.
15. As a player on History, I want its reads to retry when I open it, when my connection comes back, and when I return to the tab, so that the names come back without my help.
16. As a player on a build with no backend, I want the panel, so that I never see a blank screen.
17. As a player, I want the offline or server message to follow my connection state while the panel shows, so that the message never goes stale.
18. As a developer, I want one panel component, so that the Archive (#191) can use it later.

## Implementation Decisions

Author calls Q1 (History offline rows) and Q2 (items 1 to 11 below) were accepted by the owner, 2026-10-02.

### Reads and timeout

- `settle` (the helper that turns a read into `loading`, `ready`, or `failed`) gains the timeout: it fails the read when it does not settle within 10 seconds (`Promise.race` with a timer that is cleared when the read settles). The timeout also marks the read cancelled, so a late result never sets state. History's Schedule read uses `settle`, so it inherits the timeout. The timeout lives in the client, not in the Supabase adapter, so it covers every `Remote`, the fake included. A result that arrives after the timeout is dropped. The 10-second value is one named constant.
- The server store gains `retry()`. It reloads only the reads whose state is `failed`, setting them to `loading` in one state change (the catalog and/or the current Dailies); a read that is `ready` or already `loading` is left alone, so a loaded screen never goes back to `loading` or `failed`, and a retry is ignored while its reads are in flight. A retried read goes to `loading` first, then to `ready` or `failed`. `retry()` does nothing with no `remote`.
- The store's first load uses the same timeout. A new read for the same state calls the previous cancel handle, then stores the new one, so only the newest request can set its state.

### Triggers

- `App` attaches, once per store, listeners on `window` `online`, `window` `focus`, and `document` `visibilitychange` (visible only), the same events Spec 4 sync uses. Each calls `store.retry()`. There is no throttle and no timer. While every read has succeeded, `retry()` has nothing to reload, so these listeners do nothing: the focus read for a new day is #188.
- The "Try again" button calls `store.retry()`.
- Every listener and read started by an effect (the `App` effect and History's Schedule hook) returns its detach and cancel function, so StrictMode and unmount leave no leak and no late state update.

### Panel

- One shared panel component replaces the failed branch of the shared status piece. The loading line stays as it is. The panel shows a message and a "Try again" button. The message is "You're offline. Portdle needs a connection to load puzzles." when `navigator.onLine` is false, and "Portdle's server isn't answering. Try again in a moment." otherwise. The panel re-renders on the window `online` and `offline` events, so the message follows the connection state.
- The temporary line "Could not load puzzles." and its TEMPORARY comment are deleted everywhere in the code and the tests.
- The Daily, Blitz's Play tab, and the Codex use the panel where they use the failed line today. The Daily's "entry id missing from the catalog" failed state shows the panel with the server message; both reads are loaded there, so its "Try again" does nothing (accepted, like the no-backend build). The shell, the nav, the Daily switcher, and Blitz's tab switcher stay. Blitz's panel replaces only the Play tab content. A no-backend build shows the panel and "Try again" does nothing. The Archive does not exist yet (#191): no wiring now.

### History

- While any of History's three reads (catalog, current Dailies, past Schedule rows) has not succeeded, the Daily segment lists the player's saved finished Dailies (status `won` or `lost`) read from the device store, newest date first, then category order, each as a category badge and the date, with no name and no port. When all three reads succeed, it lists the full rows with names as it does today. This includes the first load and every retry, so the saved rows never flash to a loading line. History never shows the panel and shows no loading line in the Daily segment.
- A pure engine function builds the saved rows from the stored Dailies, so it is unit tested.
- The past Schedule rows read gets the 10-second timeout and a retry: History reads it on mount, and retries it while it is `failed` on `online`, `focus`, and `visibilitychange`. On mount History also calls `store.retry()`, so failed catalog or current-Dailies reads reload when the player opens it.

### Test support

- The fake `Remote` already fails and holds each read. Tests use fake timers to cross 10 seconds, and set `navigator.onLine` and dispatch `online`, `offline`, `focus`, and `visibilitychange`.

## Testing Decisions

- A good test drives `<App>` with `memoryStore` and the fake `Remote` and asserts what the player sees and the store's contents, not internal calls. This is the one seam, as in #186. Prior art: `server-data.test.tsx`, `mixed-daily.test.tsx`, `history-page.test.tsx`.
- App-level tests, one per case: both messages by `navigator.onLine`, and the message changing on `offline`/`online` while the panel shows; "Try again" reloads and recovers; `online` retries; `focus` retries and `visibilitychange` retries, with every focus retrying while the panel shows (no throttle); a retry shows the loading line and a second trigger during it adds no second read; a read held over 10 seconds fails (fake timers) and its late result is dropped; a loaded screen survives a later failed read (a retry with a loaded read adds no request); Blitz keeps both tabs, the Leaderboards tab works, and the panel is only in Play; the Codex shows the panel only when the catalog fails and loads with the current-Dailies read failing; the nav stays and History is reachable from the panel; a reload offline with a saved mid-game record shows the panel, and after `online` the board shows the saved tries; a no-backend build shows the panel; History offline lists saved finished rows without names (an in-progress record is not listed), then fills names on success, and retries on mount, `online`, and `focus`.
- Unit tests: the read helper's timeout and drop-late behavior; the store's `retry` (reloads only failed reads, ignores in-flight reads); the saved-rows engine function.
- A test where a late result of an old read arrives after a retry has started and is dropped.
- The old "Could not load puzzles." assertions in existing tests move to the panel.
- `pnpm lint`, `pnpm typecheck`, `pnpm test`, and `pnpm build` pass; CI is green.

## Out of Scope

- New-day detection, the focus read for a new day, the midnight timer, and removing the router rebuild (#188).
- The `late` mark and stored stats (#189), puzzle numbers (#190), the Archive screen and History of only finished Dailies with results (#191). The Archive reuses the panel then.
- The puzzle number and the result in History's offline rows (the parent's story 20 lists them): #190 and #191 add them.
- A retry timer, a throttle, sync or Leaderboards error messages (they stay as Spec 4 decided).
- An abort of the underlying `fetch` on timeout.
