# Spec: Motion — Blitz state changes and the shared view-transition helper

Spec for #93. Tracker: https://github.com/mquesada02/portdle/issues/93. Parent: Spec 3, #87. Blocked by #89 (merged).

## Problem Statement

A Blitz run starts, ends, and restarts with hard cuts: pressing Start swaps the arena for the run in one frame, spending the last life or letting the clock run out swaps the run for the end card the same way, and Play again swaps the end card back to the arena the same way again. Ticket #89 built the router's screen-change motion and the stylesheet's view-transition conventions, but nothing outside the router can start a view transition yet — every state change that should animate this way needs a shared helper, per Spec 3's Technique decision, and the Blitz screen is the first (and, per this ticket, only) caller of it.

## Solution

The Blitz screen's three phase changes — arena to run (Start), run to ended (the guess that spends the last life, and the timeout), and ended to arena (Play again) — each run through one new shared helper, `runViewTransition`, in `src/ui/view-transition.ts`. The helper takes a list of transition types and an update function; it checks reduced motion first, then mirrors the two-step gate `router-core`'s own `startViewTransition` applies (the API's presence, then support for the `:active-view-transition-type()` selector) before calling `document.startViewTransition`, committing the update synchronously with React's `flushSync`. Every phase change calls it with `["phase"]`. The stylesheet's `screen`-type rules — the ones that fade the shell's `screen`-named content out and rise the new content in, added by ticket #89 — now also apply under `phase`, sharing their selectors through a type list on one parent rule. Round commits that leave lives, HUD ticks, round-log updates, and the setup dialog's own open and close start no transition, exactly as today.

## User Stories

Renumbered sequentially for this ticket; each traces back to Spec 3 (`docs/superpowers/specs/2026-09-13-spec3-motion-polish.md`, issue #87).

1. As a Blitz player, I want the arena to give way to the run with the same motion as a screen change when I press Start, so that a run beginning feels like arriving somewhere.
2. As a Blitz player, I want the run to give way to the end card with the same motion when the run ends, so that the end lands softly.
3. As a Blitz player, I want Play again to bring the arena back with the same motion, so that the loop feels consistent.
4. As a Blitz player, I want the HUD countdown and the round log to keep updating without motion during a run, so that fast play is never delayed by animation.
5. As a player who has asked my system to reduce motion, I want none of these transitions to play, so that the app respects my setting as it already does for the board.
6. As a screen reader user, I want none of these transitions to change what is announced or when, so that motion stays purely visual.
7. As a maintainer, I want one shared helper that starts a view transition when the browser supports it and just applies the change when it does not, so that the Blitz state changes and the Codex sort reorder do not each reimplement the fallback.
8. As a maintainer, I want the seam tests to keep passing with no new fake-timer use, so that motion stays outside the test contract as the redesign decided.

## Implementation Decisions

### Shared view-transition helper

- A new module, `src/ui/view-transition.ts`, exports one function: `runViewTransition(types: string[], update: () => void): void`. It checks `window.matchMedia("(prefers-reduced-motion: reduce)").matches` first, before either form below, and calls `update()` directly and returns when it matches. Otherwise, when `typeof document.startViewTransition !== "function"`, it calls `update()` directly and returns (no API). Otherwise it checks `window.CSS.supports("selector(:active-view-transition-type(a))")` — the same string `@tanstack/router-core`'s `router.js` checks in its own `startViewTransition` method (verified directly in `node_modules/.pnpm/@tanstack+router-core@.../router.js`) — and when it reports support, calls `document.startViewTransition({ update: () => flushSync(update), types })`; otherwise it calls `document.startViewTransition(() => flushSync(update))`, the callback form. `flushSync` is imported from `react-dom`. This is the same two-step gate the router relies on for route changes, reproduced here because the helper calls the API directly rather than going through the router; per Spec 3's Technique decision, the reduced-motion check running before either form is stricter than the router's own gate in the band where the API exists but the selector does not (there the router still starts an untyped transition even under reduced motion, relying on the CSS's universal reduced-motion rule to zero it), which is harmless since that CSS rule covers the band either way.
- No new type is exported or imported for `types` beyond `string[]`, matching ticket #89's own "no new type import" choice for the router's inline `types` callback: the DOM's `StartViewTransitionOptions`/`ViewTransitionUpdateCallback`/`ViewTransition` types are read from context by the compiler at each call site, the same way `app.test.tsx`'s existing `stubViewTransitions` fake already relies on them being ambient.
- This helper is the only caller of `document.startViewTransition` outside the router, per Spec 3's Technique decision and story 7 above. `src/ui/blitz-page.tsx` imports `{ runViewTransition }` from `./view-transition`.

### Blitz phase transitions

- `start()` in `blitz-page.tsx`: unchanged up through the `"error" in started` check (which still calls `setPoolError` directly and returns, starting no transition — the empty-pool notice is not a phase change). Every statement after that check — `setPoolError("")`, `setMessage("")`, `setDigits("")`, `setShakeKey(0)`, `setNewBest(false)`, `setRun(started)`, `setDialogOpen(false)`, and the `deadline`/`remaining` sets — moves inside one `runViewTransition(["phase"], () => { ... })` call, in the same order. This is the arena-to-run change (story 1); it also closes the setup dialog as part of the same update, which is expected — the dialog's own open/close decision (Spec 3's Blitz state changes decision: "Opening and closing the setup dialog is not a phase change") is about the dialog's own dismissal paths (Escape, backdrop click, Cancel), not about Start, which the same decision explicitly routes through the phase helper.
- `playAgain()`: its entire body (`setRun(null)`, `setDigits("")`, `setMessage("")`, `setPoolError("")`, `setDeadline(null)`, `setRemaining(null)`, `setNewBest(false)`) moves inside one `runViewTransition(["phase"], () => { ... })` call. This is the ended-to-arena change (story 3); `saveWarning` is untouched, per ticket #77's own decision that `playAgain` does not clear it.
- `applyResult()`: the tail of the function — currently `setDigits("")`, the `message` set, and `setRun(result.state)` — moves into a local `commit` closure. Because `submitGuess` and `submitInverted` both already guard `if (!run || run.ended) return;` before calling `reduceBlitz` and `applyResult`, `result.state.ended` is `null` on entry to `applyResult` and can only become non-`null` (specifically `"lives"`, since `applyResult` is never reached from the timeout path) as a result of this same call, per `reduceBlitz`'s `afterCommitted`, which ends the run in the same state update as the round's commit. So: when `result.state.ended !== null`, `applyResult` calls `runViewTransition(["phase"], commit)` (the guess that spends the last life, story 2); otherwise it calls `commit()` directly (every round commit that leaves lives, story 4). The early returns for an invalid guess, a duplicate default guess, and a duplicate inverted guess are unchanged and still return before reaching `commit` at all, so they start no transition, as today. `recordEncounters`/`setSaveWarning` stay exactly where they are, before the `commit`/`runViewTransition` call — `flushSync` flushes whatever React work is pending at the moment it runs, so a save-warning update queued immediately beforehand in the same handler still commits atomically with the phase change, preserving today's timing for the `ProgressNotice` live region.
- The countdown `useEffect` (keyed on `[deadline]`): gains one `let expired = false;` local to the effect body, alongside `endsAt`. `expire()` becomes: return early when `expired` is already `true`; otherwise set `expired = true` and call `runViewTransition(["phase"], () => setRun((current) => { if (!current || current.ended) { return current; } return reduceBlitz({ state: current, event: { type: "timeout" }, protocols, applications, rng: Math.random }).state; }))` — the updater body is unchanged from today. This guard is necessary because nothing else stops the effect's own `setInterval` from calling `tick()` (and so `expire()`) every 100ms for as long as the end card is showing after a timeout: today that repeat call is a harmless no-op (the updater returns the same `current` reference, and React bails out of re-rendering), but without the guard it would also call `runViewTransition` — and so `document.startViewTransition` — again on every subsequent tick. `expired` resets to `false` each time the effect re-runs, i.e., each time `deadline` changes (a fresh run starting, or `playAgain` returning it to `null`), so exactly one transition starts per run's timeout (story 2), and no transition starts on any other tick (story 4). The `window.setTimeout(expire, ...)` call site is unchanged; it now runs the same guarded `expire`.

### Stylesheet: sharing `screen`'s rules with `phase`

- In `src/styles.css`, the three rules ticket #89 added under `:root:active-view-transition-type(screen)` — zeroing `screen`'s group tween and animating its old and new snapshots with `fade-out`/`rise` — are rewritten as one parent rule, `:root:active-view-transition-type(screen, phase)`, holding the three as nested rules (`&::view-transition-group(screen)`, `&::view-transition-old(screen)`, `&::view-transition-new(screen)`), per Spec 3's Stylesheet and lint decision's "shared layout" (a type list on a parent rule) and per this ticket's own acceptance criteria. `:active-view-transition-type()` matches when the active transition's type list contains any of its comma-separated arguments, so this one rule now matches both a `screen`-type and a `phase`-type transition. Each of the three nested lines still names `screen` inside a view-transition pseudo-element and so still needs its own `biome-ignore lint/correctness/noUnknownTypeSelector` comment directly above it — per this ticket's own pre-verified linter facts (an ignore comment covers only the line that follows it, including a nested `&::view-transition-old(screen)` line; this codebase's stylesheet has no prior CSS-nesting block to check that against, so it is taken as given rather than re-derived here) — so the total stays at three ignores for this rule (down from three separate rules each needing one, to one parent rule whose three nested lines each still need one: the count of ignored lines is unchanged, only the selector repetition is removed). The parent selector itself, `:root:active-view-transition-type(screen, phase)`, never triggers the rule and carries no ignore, matching `:active-view-transition-type(switcher)` today.
- Nothing else in this block changes: the root's untyped no-animation rule, the `switcher`-type rule that holds `screen` still, the `fade-out`/`rise` keyframes, and the reduced-motion block's universal view-transition coverage are all untouched by this ticket — the `switcher`-type rule in particular is left exactly as ticket #89 wrote it, since ticket #92 (the `switcher-content` region) is editing it in parallel and this ticket's diff to `src/styles.css` stays confined to the `screen`/`phase` parent rule described above.
- No new keyframe, duration, or region name is added: `phase` reuses `screen`'s existing 100ms `fade-out` and 150ms `rise` exactly, per Spec 3's Blitz state changes decision ("animate the `screen` snapshots as on a screen change"), and the root's untyped no-animation rule already covers every type, `phase` included, so the shell holds still with no further edit.

### Test helper relocation

- `app.test.tsx`'s local `stubViewTransitions()` function moves, unchanged, into `src/test/helpers.ts` as a named export, and `app.test.tsx` imports it from there instead of defining it locally. This lets `blitz-arena.test.tsx` and `blitz.test.tsx` import the same fake rather than each defining their own copy, per this ticket's instruction to reuse the existing fake pattern. Its behavior, its existing descriptive comment, and the shape of its return value (`{ calls, restore }`) are unchanged by the move.
- `renderBlitz` in both `blitz-arena.test.tsx` and `blitz.test.tsx` gains a `reducedMotion` option threaded into `stubMatchMedia`, mirroring the `reducedMotion` option `app.test.tsx`'s `renderApp` already has (`src/test/helpers.ts`'s `stubMatchMedia` already accepts the parameter, from ticket #89; only the two Blitz test files' local render helpers need to start passing it through). Every existing call site keeps compiling and passing unchanged, since the new option defaults to `false`.

No new strings.

## Testing Decisions

A good test exercises a public seam with literal inputs and asserts what a player sees or what a pure function returns. How the motion looks is checked by eye, not by a test, per Spec 3's Testing Decisions; whether, and with which type, the helper asks for a view transition is tested through the same fake of the View Transitions API ticket #89 already established for the router. This ticket touches one seam.

1. **App seam** (`blitz-arena.test.tsx` and `blitz.test.tsx`; render the app with a memory store, memory history, and the injected `UTC_TODAY`, following each file's existing `renderBlitz` pattern; the current entry is still read from the `h1` heading, and the page still receives no rng).
   - Every existing test in both files keeps passing unchanged, aside from the mechanical `reducedMotion`-threading edit to `renderBlitz` described above, which changes no existing call site's behavior.
   - `blitz-arena.test.tsx`, new tests, each installing `stubViewTransitions()` after `renderBlitz` and calling `restore()` in a `finally`:
     - Starting a run from the arena (`New run` then `Start`) records one call with `["phase"]`.
     - Opening the dialog (`New run`) and closing it (`Cancel`) records no call.
     - Finishing a run and then clicking `Play again` (with the fake installed only after the run has already ended, so the run's own last-life transition is not conflated with Play again's) records one call with `["phase"]`.
     - With `reducedMotion: true` passed to `renderBlitz`, starting a run from the arena records no call and still lands on the run (`Round 1` visible).
     - With `reducedMotion: true` passed to `renderBlitz`, finishing a run and clicking `Play again` (fake installed only after the run has ended, as above) records no call and still lands back on the arena.
   - `blitz.test.tsx`, new tests, placed next to the existing `"three misses end with Out of lives and write a new best"` and `"sprint timer ends with Time's up"` tests, each installing `stubViewTransitions()` after `Start` (so the run's own start is not captured) and calling `restore()` in a `finally`:
     - Missing three times (`missThree`) records exactly one call, `[["phase"]]` — the first two misses, which leave lives, add nothing; only the third, which spends the last life and ends the run, does. This single assertion covers both "a round commit that leaves lives starts none" and "spending the last life... starts one transition with the phase type."
     - Letting the clock run out, on fake timers (`vi.advanceTimersByTimeAsync(60_000)`), records one call, `[["phase"]]`; advancing the fake clock further (well past the deadline, so the interval's own repeat ticks fire again) still leaves `calls` at exactly one entry, proving the countdown effect's new `expired` guard, not just the state updater's existing no-op reference-equality behavior, is what stops a second transition from starting on every subsequent 100ms tick.
     - With `reducedMotion: true` passed to `renderBlitz`, missing three times still ends the run (`Out of lives` visible) and records no call.
     - With `reducedMotion: true` passed to `renderBlitz` and fake timers, letting the clock run out still shows `Time's up` and records no call.
   - No new fake-timer use beyond what these two files' existing timeout/countdown tests already run on (story 8): the last-life test uses `userEvent` exactly as `missThree`'s existing callers do, and the timeout test reuses the existing `vi.useFakeTimers()`/`vi.advanceTimersByTimeAsync` pattern the file's own `"sprint timer ends with Time's up"` test already established.

No snapshot tests, no visual regression, no Playwright. This ticket is proven done by `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm gen:schedule --check`, and `pnpm build` all passing, plus confirming by eye in the built CSS that the `phase` type's rules are present (sharing the `screen` type's selectors) and that `pnpm lint` reports no unused suppression.

## Out of Scope

- The `switcher-content` region and any further edit to the `switcher`-type rules in `src/styles.css` — ticket #92's work, running in parallel on the same file.
- The `reorder` type, the Codex sort helper call, and its own stylesheet rules — a later ticket's work, which reuses `runViewTransition` from this ticket without changing it.
- The miss popover, dialogs, Rounds disclosures, and nav/switcher/sort-toggle color transitions — other tickets' work, already merged or separately tracked.
- Any change to `reduceBlitz`, `startBlitz`, `buildRun`, `prependRun`, or any other `src/engine/blitz.ts` export — this ticket only changes when `blitz-page.tsx` calls `setRun`/`setDialogOpen`/etc., never what state those calls compute.
- Any change to the setup dialog's own Escape/backdrop-click/Cancel dismissal, its preselection logic, or its markup — untouched; those three dismissal paths call `closeDialog`, which this ticket does not touch and which starts no transition, as today.
- A polyfill for browsers without the View Transitions API, and any motion library or spring physics.

- Glossary: `CONTEXT.md` gains no terms; this ticket introduces no player-facing copy or renamed concept. The type name `phase` and the reused region name `screen` are motion names local to Spec 3, not domain terms, as Spec 3's own Further Notes already state.
- ADR 0001 ("localStorage until a backend"), the only ADR in `docs/adr/`, is unaffected: it is about persistence, not motion or rendering.
- Author calls not covered by the ticket or Spec 3, listed so they can be overruled:
  - The countdown effect's `expired` local flag (see "Blitz phase transitions" above) is this ticket's own addition, not asked for by the ticket or Spec 3 in so many words — it exists because wrapping `expire()`'s existing update in `runViewTransition` turns a previously-harmless repeated no-op call (the interval's own `tick()` keeps calling `expire()` every 100ms for as long as the end card is showing, since nothing else stops it) into a repeated call to `document.startViewTransition`, which nothing in Spec 3 or this ticket wants. A `useRef` mirroring `run` on every render was considered and rejected in favor of the smaller, effect-local flag, since the effect does not otherwise need to read `run` at all (it already avoids that dependency by using `setRun`'s updater form) and the flag needs no cleanup.
  - `runViewTransition`'s `types` parameter is typed `string[]`, not a shared literal-union type, matching ticket #89's own choice not to introduce one for the router's `types` function; nothing in either ticket needs the compiler to reject an unrecognized type string, and a shared union would need updating by the later Codex-reorder ticket regardless.
