# Spec: Post-release polish

Spec for #67. Tracker: https://github.com/mquesada02/portdle/issues/67

## Problem Statement

Four small things a player or maintainer notices right after the digit-feedback release:

A player who opens How-to after playing a few tries sees no explanation of what the tile colors mean — the dialog tells them digit slots show how many digits, but nothing about green, yellow, or gray. A player running Blitz in the default orientation sees the digit slot row pinned to the left edge of its column at every width, unlike the Daily board, where the row is centered. A player using Blitz Inverted on the SvelteKit entry sees a blurb ("Svelte app framework") that gives away part of the name it's meant to obscure. A maintainer running the test suite sees "catalog miss names the service spends a life and advances" fail every so often for no code reason, because the Blitz run it drives picks its target from the real catalog with unseeded randomness.

## Solution

The How-to dialog gains one more rule, placed right after "Digit slots show how many digits.", spelling out what green, yellow, and gray mean on a committed row. Blitz's default-orientation digit slot row is wrapped so it centers horizontally like the Daily board's row does, at every width; the Submit button stays full width, and the Daily board itself is untouched. The SvelteKit catalog entry gets a new blurb that contains no part of its name, while still telling an Inverted player it's not Vite even though the port is the same. The flaky Blitz test's assertion is narrowed to the one element it actually means to check, so its result no longer depends on which entry the real, unseeded shuffle happens to deal next.

## User Stories

### How-to marks rule

1. As a player who opens How-to, I want a rule that explains green, yellow, and gray, so that I know how to read a committed row without guessing.
2. As a player, I want that rule placed right after the rule about digit slots, so that the rules read in the order I encounter them: how many digits, then what the colors mean, then how many tries I get.
3. As a player, I want the rule to use the words green, yellow, and gray, so that it matches what I actually see on the board rather than engine jargon.
4. As a maintainer, I want the rule's meaning to match the Mark vocabulary in `CONTEXT.md` (placed, present, absent) even though the player-facing copy says green, yellow, gray, so that the copy and the engine never disagree about what a color means.
5. As a maintainer, I want the rule to render from the same place every time the dialog opens, so that there is only one string to keep correct.

### Blitz Default slot centering

6. As a player running Blitz in the default orientation, I want the digit slot row centered under the prompt at every width, so that it doesn't look like a layout bug next to the centered prompt above it.
7. As a player, I want the Submit button to stay full width, so that the fix to the slot row doesn't shrink my tap target.
8. As a player using the Daily, I want no change to how my board looks, so that this fix is scoped to Blitz only.
9. As a maintainer, I want the Blitz slot row centered without importing the Daily's row-shell component, so that Blitz doesn't inherit caption-column layout it has no use for.

### SvelteKit blurb

10. As a player guessing in Blitz Inverted on the SvelteKit entry, I want a blurb that doesn't contain "SvelteKit" or any part of it, so that the blurb doesn't hand me the answer it exists to obscure.
11. As a player on the same entry, I want the blurb to still say something that separates it from Vite, so that seeing port 5173 with this blurb doesn't leave me guessing blind between the two.
12. As a maintainer, I want the entry's name, port, and aliases unchanged, so that this is a flavor-text fix, not an identity change.
13. As a maintainer, I want `pnpm gen:schedule --check` to keep passing, so that the catalog's existing validation still holds after the blurb changes.

### Flaky Blitz test

14. As a maintainer, I want "catalog miss names the service spends a life and advances" to pass every time I run the suite, so that a red run means something broke, not that the dice landed wrong.
15. As a maintainer, I want the fix to live in the test file only, so that the engine's real randomness in production is untouched.
16. As a maintainer, I want the fix to not depend on the shape of today's catalog beyond what's already true (an entry named HTTP at port 80, an entry named chargen at port 19), so that it keeps working as the catalog grows.

## Implementation Decisions

### How-to marks rule

- The How-to dialog's rules list gains one new entry, inserted immediately after "Digit slots show how many digits." and before "6 tries. A miss names the service if that port is in this catalog.": "After each try, green means right digit in the right place, yellow means the digit is in the port elsewhere, gray means it is not in the port."
- The rules list already renders from one shared list component used by the dialog's one render site, so this is a single string addition; no second copy exists anywhere else to update.

### Blitz Default slot centering

- Blitz's default-orientation run wraps its digit slot control in a new centering container, sibling to the Submit button, so only the slot row is centered and the button keeps its own full-width styling.
- The Daily board centers its own active row through a row-shell layout built for aligning a caption column beside the row; Blitz has no caption concept, so Blitz gets its own, simpler centering rather than reusing that component. The Daily's row-shell component and the Daily page are not touched.

### SvelteKit blurb

- The SvelteKit catalog entry's blurb changes from "Svelte app framework" to "Full-stack app framework built on Vite". It contains no substring of "svelte" or "kit" case-insensitively, satisfying the stricter-than-validator rule that no part of the entry's name may appear (the entry has no aliases). Mentioning Vite by name is fine — the rule is about this entry's own name and aliases, not another entry's — and doing so is what distinguishes the entry from Vite for an Inverted player on the shared port.
- Name, port, transport, and aliases on this entry are unchanged. This is a flavor-text edit under the identity-freeze rule (description/aliases/blurb/transport are editable anytime; name/port are not).
- A test file has a literal, hand-maintained list of expected blurb text per crowded port, used to assert Blitz Inverted's blurb rendering; that list's entry for port 5173 is updated to match the new SvelteKit blurb text so it keeps asserting real, current values rather than stale ones.

### Flaky Blitz test

- Root cause: the test starts a Blitz run, which deals its first entry from the full answer-eligible catalog via an unseeded shuffle. After committing a miss, the test asserts the identified service's name appears once on screen. When the run's *next* dealt entry (chosen by that same unseeded shuffle, immediately after the miss) happens to have the same name as the just-identified miss, that name now appears twice — once as the new heading, once in the miss message — and the test's single-match assertion throws, because it doesn't say which of those two elements it means.
- Fix: the assertion is narrowed to say what it always meant — the miss message, not the heading. The test already queries the heading separately (to confirm the run advanced past the missed entry); it reuses that same heading element to exclude it from the set of elements matching the identified name, and asserts at least one non-heading match remains. This holds regardless of which entry the real, unseeded shuffle deals next, including the exact case that produced the flake, so it needs no assumption about pool size or which entries exist beyond the two the test already relies on (an entry named HTTP at port 80, an entry named chargen at port 19).
- No changes to `engine/blitz.ts`, its shuffle, or any other production code, and no stubbing of `Math.random` — the fix is entirely a more precise query inside the one named test.

## Testing Decisions

A good test here exercises what a player can see or a maintainer can assert without new tooling, following the prior art already in the touched files (`src/ui/app.test.tsx`'s How-to tests, `src/ui/blitz.test.tsx`'s Blitz run tests, `src/engine/catalog.test.ts`'s blurb-validation tests).

1. **How-to rule (App seam)**: an assertion that opening How-to renders the new rule's exact text, alongside the existing How-to tests, which must keep passing unmodified in behavior.
2. **Blitz slot centering (App seam, presence only)**: no new automated test — the existing Blitz Default tests already assert the slot row and Submit button render; centering is a layout fact that jsdom cannot verify, so it is proven only by the two required screenshots (375px and 1024px width) attached as PR evidence, not by a unit or component test.
3. **SvelteKit blurb (catalog validation seam)**: no new test is added purely for this string; `pnpm gen:schedule --check` (which runs the existing catalog validator, including the blurb-leak check) is the existing coverage and must keep passing. The literal blurb-text list inside `src/ui/blitz.test.tsx`'s crowded-port Inverted tests is updated to the new value so those two existing tests keep passing and keep asserting real values.
4. **Flaky Blitz test (test-only fix)**: the fix lives entirely inside the one named test in `src/ui/blitz.test.tsx`, narrowing its query rather than controlling randomness; no engine or production code changes. Because the run's real, unseeded randomness stays in play, the ten-consecutive-run requirement below is still meaningful evidence that the flake is gone, not a formality.

No snapshot tests, no visual-regression tooling, no Playwright. This ticket is proven done by `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm gen:schedule --check`, and `pnpm build` all passing, plus the full suite run ten consecutive times after the flaky-test fix, all green, in addition to the seam coverage above.

## Out of Scope

- Any change to `src/engine/blitz.ts`, `src/engine/guess.ts`, or any other engine/production code.
- For the slot-centering fix specifically: no UI change beyond the one new centering wrapper around Blitz's default-orientation digit slot row (the How-to rule string and the SvelteKit blurb are, separately, the UI/content changes items 1 and 3 already call for).
- Any change to the Daily board, the Daily page, or the digit-slot control component itself.
- Automated visual-regression or screenshot tooling; the screenshots required by the issue are one-time manual verification evidence for this PR, not a new test suite.
- Any catalog entry's blurb other than SvelteKit's.
- Any change to How-to's dialog behavior, structure, or other rules beyond the one new rule string.

## Further Notes

- Glossary: no new terms. Uses `CONTEXT.md`'s existing Mark (placed, present, absent), Slot, How-to, Blitz, and Entry.
- The How-to rule's player-facing wording (green/yellow/gray) intentionally differs from the engine's mark vocabulary (placed/present/absent) per `CONTEXT.md`'s own guidance that colors are how marks render, not what they are called internally — the rule is written for the player, not the engine.
