# Spec: Motion — screen changes through the router

Spec for #89. Tracker: https://github.com/mquesada02/portdle/issues/89. Parent: Spec 3, #87.

## Problem Statement

Tapping a nav item or the wordmark swaps the whole screen at once: the old screen disappears and the new one appears with no transition, while the top bar and the tab bar redraw along with it since nothing holds them still. This is the first of Spec 3's abrupt moments and the foundation the rest of the motion work builds on: the router's transition-type plumbing, the `screen` named region, and the stylesheet's view-transition conventions and lint pattern do not exist yet.

## Solution

A nav tap or a wordmark tap plays a screen motion: the old screen fades out over 100ms and the new one rises in over 150ms with an 8px lift, while the top bar and the tab bar hold still. This runs through the router's built-in view-transition option, which decides per navigation whether the nav screen changed (Daily, Blitz, History, Codex, looked up in the nav's own table) or only the pathname changed within one screen (a Daily switcher tap, a History switcher tap, or a nav tap that lands back on the current screen's default address) — the first plays the screen motion, the second holds `screen` still so a future ticket can add its own motion there. Browsers without the View Transitions API swap instantly as today; under reduced motion nothing plays. This ticket lays only the foundation: the transition types, the router's types function, the `screen` region and its name, the stylesheet block, and the router tests. The `switcher-content` region, the `phase` and `reorder` types, the shared view-transition helper, the miss popover, dialogs, disclosures, and the color transitions are later tickets' work.

## User Stories

1. As a player, I want the content to fade out and the next screen to fade in and lift slightly when I tap a nav item, so that moving around feels smooth instead of jarring.
2. As a player, I want the top bar and the tab bar to hold still during a screen change, so that only the content moves and the nav stays where my thumb is.
3. As a player, I want a screen change to finish within a fraction of a second, so that motion never slows me down.
4. As a player, I want tapping the wordmark to move with the same motion as a nav tap to the same place, so that every route change feels the same.
5. As a player on a browser without the View Transitions API, I want screen changes to work exactly as today, so that an older browser loses only the polish.
6. As a Daily player, I want a switcher tap to hold the screen still rather than crossfade it, so that the switcher motion a later ticket adds is the only thing that plays there.
7. As a player who has asked my system to reduce motion, I want none of these transitions to play, so that the app respects my setting as it already does for the board.
8. As a screen reader user, I want none of these transitions to change what is announced or when, so that motion stays purely visual.
9. As a maintainer, I want the nav's table of screens and match paths defined once and imported by both the shell and the router, so that the router's screen lookup can never drift from what the nav renders.
10. As a maintainer, I want the view-transition stylesheet rules to pass lint without weakening the linter for the rest of the stylesheet, so that the linter keeps its value.

## Implementation Decisions

### Shared nav table

- `src/ui/shell.tsx`'s `NAV` array (`to`, `label`, `icon`, `matchPaths` per screen) and the four hand-authored icon path constants it references (`GRID`, `BOLT`, `CLOCK`, `BOOK`) move as-is into a new file, `src/ui/nav.ts`, which exports `NAV`. `shell.tsx` imports `{ NAV }` from `./nav` and keeps rendering it exactly as it does today; its own `HELP` icon constant, used only by the How-to button, stays in `shell.tsx`. `src/router.tsx` imports the same `{ NAV }` from `./ui/nav` for its screen lookup. Neither file's runtime behavior changes; this is a pure relocation so the table has one definition both files import, per the ticket.

### Router types function

- `src/router.tsx` gains a private `screenFor(pathname: string): string | undefined` helper that returns the matched `NAV` entry's `to` (each entry's `to` is already unique per screen — `/`, `/blitz`, `/history`, `/codex` — so it doubles as a stable screen identifier) by checking `matchPaths`, mirroring the lookup `shell.tsx`'s active-link highlighting already does.
- `createAppRouter` passes `defaultViewTransition: { types: ... }` to `createRouter`. The `types` function returns `false` (no transition) when `fromLocation` is absent, before anything else: verified directly in `router-core`'s `load-client.js`, `runClientTransaction` calls `router.startViewTransition` unconditionally on every client route load, including the initial one `Transitioner`'s mount effect triggers via `router.load({ sync: true })`, at which point `router.stores.resolvedLocation` (seeded `undefined` in `stores.js` and never pre-filled from the initial URL) makes `fromLocation` undefined — so without this guard, a fresh page load would itself play the fade-and-rise `screen` motion, which nothing in this ticket or Spec 3 asks for; today's instant first paint is preserved by treating "no prior location" as "nothing to compare, skip." It then reads `window.matchMedia("(prefers-reduced-motion: reduce)").matches`, the way `daily-reveal.tsx`'s reveal-scroll effect already reads it, and returns `false` when it matches — the literal value TanStack Router's `startViewTransition` treats as "skip the transition," verified in `router-core`'s `router.js`: `if (resolvedViewTransitionTypes === false) return fn();`. Otherwise it looks up the screen for `fromLocation` and for `toLocation` via `screenFor`, and returns `["screen"]` when they differ, `["switcher"]` when they are the same.
- No new type import is added: the callback is written inline as the `types` property of the `defaultViewTransition` object literal passed to `createRouter`, so its parameter type is inferred contextually from `ViewTransitionOptions["types"]` (`{ fromLocation?: ParsedLocation; toLocation: ParsedLocation; pathChanged: boolean; hrefChanged: boolean; hashChanged: boolean }` in `router-core`'s `router.d.ts`), of which only `fromLocation.pathname` and `toLocation.pathname` are read.
- This one function is the only thing that decides `screen` vs. `switcher` for a route change: the main nav, the Daily switcher, and the History switcher are all plain `Link`s the router already navigates through, so a Daily switcher tap (pathname changes among `/`, `/protocols`, `/applications`, all mapped to the Daily screen) and a History switcher tap (pathname changes between `/history` and `/history/blitz`, both mapped to the History screen) fall out of the same same-screen comparison a nav tap from Protocols to Daily does, with no special-casing.

### The `screen` region

- The shell's content wrapper in `src/ui/shell.tsx` — the `<div className="mx-auto max-w-3xl px-4 pt-6 pb-24 md:pb-6">` holding `ProgressNotice` and `Outlet` — gains the Tailwind arbitrary-property utility `[view-transition-name:screen]`, matching the codebase's existing utility-class-only styling convention (no inline `style` is used for a static value anywhere in this file). This is the only element named `screen`.

### Stylesheet

- `src/styles.css` gains, next to the existing `pop`/`shake`/`draw`/`rise` keyframes, a `fade-out` keyframe (`opacity` 1 to 0) for the screen's old snapshot; the new snapshot reuses the existing `rise` keyframe at a different duration and with no delay, so no second rise keyframe is added.
- A clearly delimited, appended block (so the two sibling tickets touching this same file, which add the `switcher`, `phase`, and `reorder` type rules and their own keyframes, have an unambiguous seam) adds:
  - The root's untyped no-animation rule: `::view-transition-group(root)` gets `animation: none`; `::view-transition-old(root)` and `::view-transition-new(root)` get `animation: none` and `mix-blend-mode: normal` (as one rule with a two-selector list, or as two separate rules — either is fine, since neither `root` nor `*` ever triggers the linter's unknown-type-selector rule regardless of how they're grouped). Untyped (not scoped by `:active-view-transition-type()`) so it applies to every transition regardless of type, holding the top bar and the tab bar still. `root` carries no ignore comment.
  - Under the `screen` type (`:root:active-view-transition-type(screen)` chained directly onto each `::view-transition-*(screen)` pseudo-element — the prototype chained onto `html` instead of `:root`; the two select the same element here, and `:root` is used to match this ticket's other selectors): `screen`'s group tween is zeroed (`animation: none`); its old snapshot gets `animation: fade-out 100ms ease-out both`; its new snapshot gets `animation: rise 150ms ease-out both`. Neither snapshot's blend mode is touched, since both are animating and the browser's default additive blend is what keeps the overlapping fade-out and rise-in from dipping in brightness. This is written as its own standalone `:active-view-transition-type(screen)` selector rather than a type list shared with `phase` — the ticket's shared-layout-is-the-default guidance describes the eventual state once the Blitz ticket adds `phase`; there is nothing to share with yet, since this ticket does not implement `phase`, so a single-type selector is the correct shape today and the later ticket extends it into a list rather than duplicating it.
  - Under the `switcher` type: `screen` carries the same no-animation rule as `root` (group zeroed; old and new zeroed with blend reset to normal), so a switcher tap holds the screen still today. This rule is what a later switcher ticket's own `switcher-content` motion will sit alongside, once that region exists.
  - Every one of the six selector lines above that names `screen` inside a `::view-transition-group/old/new()` pseudo-element sits on its own line with its own `biome-ignore lint/correctness/noUnknownTypeSelector` comment directly above it, per the linter facts verified for this ticket. `:active-view-transition-type(screen)` and `:active-view-transition-type(switcher)` never trigger the rule regardless of their argument, so neither needs one. No selector list is written for these six lines (each is its own single-selector rule, or grouped only with another `screen`-naming line that also needs its own ignore), so Biome's one-selector-per-line formatting requires no restructuring.
- The existing `@media (prefers-reduced-motion: reduce)` block gains two more rules, inside the same block: `::view-transition-group(*)`, `::view-transition-old(*)`, and `::view-transition-new(*)` get `animation: none`; `::view-transition-old(*)` and `::view-transition-new(*)` get `mix-blend-mode: normal`. The universal selector `*` never triggers the linter's rule. Because this is universal rather than named, it also covers whatever named regions later tickets add with no further edit to this block.
- Nothing else in the stylesheet's existing rules, keyframes, or formatting changes. In total this ticket edits `src/styles.css` at three sites, each minimal: the new `fade-out` keyframe alongside the existing keyframes, the appended root/`screen`/`switcher` block, and the two new rules inside the existing reduced-motion media block — not a single appended block, since the keyframe and the reduced-motion addition both belong next to what they extend. Per Spec 3, the sibling tickets (#90 miss popover, #91 dialogs/disclosures/colors) animate real DOM elements with plain CSS keyframes and Tailwind color transitions, not the View Transitions API, so neither touches any of these three sites: their own reduced-motion coverage comes from the pre-existing universal rule this ticket does not change (`*, *::before, *::after { animation: none; transition: none; }`), and neither needs the view-transition-specific pseudo-elements, `:active-view-transition-type()` rules, or `biome-ignore` comments this ticket adds.

## Testing Decisions

A good test exercises a public seam with literal inputs and asserts what a player sees or what a pure function returns. How the motion looks (timing, keyframes, the pseudo-elements themselves) is checked by eye, not by a test, per Spec 3's Testing Decisions; whether, and with which type, the router asks for a view transition is tested through a fake of the View Transitions API. This ticket touches one seam.

1. **App seam** (`src/ui/app.test.tsx`; render the app with a memory store, memory history, and an injected UTC day, following this file's existing pattern).
   - The test runner has no View Transitions API by default (`document.startViewTransition` is `undefined` in jsdom), so every existing test keeps exercising the router's fallback path unchanged; no existing test is edited.
   - New: navigating by nav link (Daily to Blitz) and by switcher (the Daily switcher's Protocols link, the History switcher's Blitz link) lands on the right screen, Daily category, or History segment, with no fake installed — confirming the router's plumbing changes do not alter normal navigation.
   - New: a local `stubViewTransitions()` helper in this file installs a fake `document.startViewTransition` that accepts both the object form (`{ update, types }`) and the plain-callback form, runs the update synchronously, records the resolved `types` (or `[]` for the callback form) into a `calls` array, and returns a stub `ViewTransition` whose promises are already resolved; it also stubs `window.CSS.supports` to report support for the active-view-transition-type selector, matching the two-step gate `router-core`'s `startViewTransition` checks (API present, then selector support) before it will pass `types` through at all. The helper returns `{ calls, restore }`; each test that installs it calls `restore()` itself once done, per the ticket.
   - New: with the fake installed before `renderApp` is called (so it is active for the router's initial-load `startViewTransition` call too), the initial render still lands on the right screen and `calls` stays empty — proving the types function's initial-load guard (see "Router types function" above) actually suppresses a transition on first paint rather than only being untested by jsdom's default lack of the API.
   - New, with the fake installed after the initial render: a nav tap from Daily to Blitz records `["screen"]`; a wordmark tap from Blitz records `["screen"]`; a nav tap to Daily from Protocols records `["switcher"]`; a Daily switcher tap (Mixed to Protocols) records `["switcher"]`; a History switcher tap (Daily to Blitz segment) records `["switcher"]`.
   - New, with the fake installed and reduced motion stubbed to match: a nav tap from Daily to Blitz still lands on Blitz, and `calls` stays empty (the router's own fallback path runs, calling the update directly rather than `document.startViewTransition`). This file's `renderApp` helper gains a `reducedMotion` option threaded into `stubMatchMedia` alongside its existing `prefersDark` one, the same way `prefersDark` already threads through, for this case to stub.
   - The case above needs `src/test/helpers.ts`'s shared `stubMatchMedia` to gain a second parameter, `reducedMotion = false`, alongside the existing `prefersDark` one: `matches` becomes `(prefersDark && query.includes("prefers-color-scheme: dark")) || (reducedMotion && query.includes("prefers-reduced-motion: reduce"))`, following the exact shape of the existing dark-scheme check. Every existing call site keeps compiling and passing unchanged, since the new parameter defaults to `false`. This is a one-function edit to a shared helper, not a second seam: `stubMatchMedia` is test setup for the App seam above, not something under test itself.

No snapshot tests, no visual regression, no Playwright. This ticket is proven done by `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm gen:schedule --check`, and `pnpm build` all passing, plus a by-eye check on the dev server confirming the built CSS carries the view-transition rules and ignores described above and that `pnpm lint` reports no unused suppression (a Chromium headless run cannot show the motion itself).

## Out of Scope

- The `switcher-content` region and any motion under the `switcher` type beyond holding `screen` still — a later ticket's work.
- The `phase` type, the Blitz arena/run/end-card transitions, and the `reorder` type and Codex card glide — later tickets' work.
- The shared view-transition helper for state changes outside the router (Blitz phases, Codex sort) — a later ticket's work.
- The miss popover's open/close motion, the dialogs' open/close motion, the Rounds disclosure rise, and the nav/switcher/sort-toggle color transitions — later tickets' work.
- A crossfade or a directional slide for screen changes; the prototype settled on fade-and-rise.
- Animating the height of anything, a polyfill for browsers without the View Transitions API, and any motion library or spring physics.
- Any change to the existing `pop`, `shake`, `draw`, or `rise` keyframes or the `.animate-*` classes that use them today.
- Any change to what a nav tap or a wordmark tap navigates to, or to the Daily switcher's or History switcher's own markup, labels, or active-state logic.
