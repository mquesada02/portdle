# Ticket spec: Preferences sync (#137)

Ticket [#137](https://github.com/mquesada02/portdle/issues/137) of Spec 4 (accounts, sync, and leaderboards; issue #127, spec file `docs/superpowers/specs/2026-09-28-spec4-backend.md`). Map: #114. Blocked by Row sync (#136), merged. This ticket adds Preferences to Sync. It builds no Device progress choice (#138), no Leaderboards (#139), and no Account deletion (#140).

**Preferences** are the theme, the How-to seen flag, and the Codex sort (`CONTEXT.md`). A **row** here means a database row or one synced record, never the Daily board's Row.

## Problem Statement

A signed-in player's theme, How-to seen flag, and Codex sort stay on the device where they were set. A player who picks the dark theme on a laptop gets the system theme on a phone, sees the How-to dialog again on every new device, and re-picks the Codex sort. `Persist` already has the bookkeeping list for changed preferences and the change events, but nothing marks or sends them, and the database has no table for them.

## Solution

A signed-in player's Preferences follow them, each on its own. A preference the player changes on a device reaches the account 1.5 seconds later, and only that preference is sent. Opening the app or returning to the tab pulls the account's Preferences: a preference the device has not changed takes the account's value, and a preference with a change not yet sent keeps its local value and is sent next. A preference changed while signed out, or before the account is known, counts as a local change too. On a device that never synced, every stored preference counts as a local change, so it can replace the account's value once, as the import does for other rows. A pulled theme shows the next time the shell mounts; a pulled Codex sort shows the next time the Codex screen mounts. Sync stays silent.

## User Stories

Spec 4 stories 36 and 65 (the Preferences table), 24 and 33 (Preferences part), and:

1. (P1) As a signed-in player, I want my theme, How-to seen flag, and Codex sort to reach my account, so that my other devices use them.
2. (P2) As a signed-in player, I want only the preference I changed to be sent, so that changing one never makes another look newer.
3. (P3) As a signed-in player, I want a preference I changed on this device to survive a pull until it is sent, so that a pull never undoes my newest choice.
4. (P4) As a signed-in player, I want a preference I did not change to take my account's value on a pull, so that another device's newer choice reaches this device.
5. (P5) As a player signing in on a device that never synced, I want the preferences stored on it to count as my changes, so that they are imported once.
6. (P6) As a signed-in player, I want an old unchanged theme on a device that already synced to never overwrite a newer theme on my account, so that signing in again is safe.
7. (P7) As a signed-in player, I want a pulled theme to show the next time the shell mounts and a pulled Codex sort the next time the Codex screen mounts, so that a pull never disturbs the screen.
8. (P8) As a player with a device that never chose a Codex sort or a theme, I want that device to send nothing for it, so that a default never replaces my account's real choice.
9. (P9) As the owner, I want the Preferences table, its trigger, policy, and grants as ordered SQL in the repo, with a hand-run smoke check, so that the backend can be rebuilt and checked from source.
10. (P10) As the owner, I want the server, not the client, to set each preference's timestamp, so that a client cannot forge recency.

## Implementation Decisions

- **`Preferences` type** (in the storage module, beside `Theme`; the remote module imports it as a type): an object with optional `theme`, `howToSeen` (only `true`), and `codexSort`. An absent key means "never set". `SyncedRows` gains a `preferences` field of this type; a pull returns the account's set values, a push carries only the changed ones.
- **`Persist` gains `readPreferences()`**, which returns only the preferences that are stored and valid (`howToSeen` only when `true`). The existing `readTheme`, `readHowToSeen`, and `readCodexSort` return defaults, which cannot tell "stored" from "default". Nothing else in `Persist` changes; `SyncChanges.preferences` and the theme, How-to seen, and Codex sort change events already exist.
- **Sync module.** Preferences become a fifth kind of row, with keys `theme`, `howToSeen`, and `codexSort`, and use the existing snapshot, changed-rows bookkeeping, push, and success-pruning code. A write of a preference marks only its own key (theme, How-to seen flag, and Codex sort each map to one key), never the other stored preferences. While Sync is active the key is marked only when its value differs from the snapshot of the account's value (an account with no value differs from any local value). While Sync is inactive (signed out, the name confirm pending, or the app just opened and the account not yet read) there is no snapshot, so the key is marked unconditionally; the push-time filter drops it later if it equals the account's value. A preference write while Sync is inactive only marks; it schedules no push (the next refresh sends it), so a signed-out player's theme toggle makes no network request. The preference branch of the write listener therefore runs before its inactive-Sync check. Sync's own writes never mark. A push carries only the pending keys whose value differs from the snapshot.
- **Merge on pull** (one synchronous step, inside the "Sync is writing" flag): for each preference the account has, if its key is pending, keep the local value; otherwise write the account's value through `Persist` when it differs. A preference the account has no value for is left alone. Pending is the bookkeeping list, plus, on a device that never synced, every stored preference.
- **Snapshot.** Preferences join the row kinds of the snapshot, the empty snapshot, the push-time sent set, and the bookkeeping pruning. A pull fills the preferences snapshot from the account's values (an absent value has no entry). The after-merge marking loop skips Preferences.
- **Marking stops after the pull.** Preferences are not part of the after-merge rule that marks every local row differing from the snapshot: only writes (above) and the never-synced import mark a preference, so a stored preference that was not changed locally is never sent (ticket criterion 2). The persisted bookkeeping is written before the account id, so a failed push is retried.
- **Never synced** means `readSyncAccount()` is null at the start of the merge, before the merge writes the account id. This step also writes those stored keys into the persisted bookkeeping, before `writeSyncAccount` runs, so a failed push is retried and a merge that fails midway still counts as never synced.
- **Screen mount.** The shell reads the theme and How-to seen flag, and the Codex screen reads the Codex sort, when they mount, and each preference write stores a new value the player picked, so no UI code changes. The Codex screen's sort read stays in the mount initializer.
- **`Remote` adapter.** `pull` also reads the account's single Preferences row (row-level security limits it to the caller's) and maps a missing row to no preferences and a null column to an absent key; it does not read the timestamp columns (the client merge is pending-based). `push` upserts one row keyed by account id containing only the changed columns, so unsent columns and their timestamps are untouched. A push with no changed preference makes no Preferences request, so an account never gets an empty row from an ordinary push. It goes through the existing push path, so a foreign-key violation still maps to `AccountGoneError`. The row mapping is a pure exported function pair beside the existing ones.
- **Migration `20260930000004_preferences.sql`.** One table `preferences`: `account_id uuid primary key references public.accounts (id) on delete cascade`; `theme text` checked to `system`, `light`, or `dark`; `how_to_seen boolean` checked to be true when set; `codex_sort text` checked to `name` or `port`; and `theme_updated_at`, `how_to_seen_updated_at`, `codex_sort_updated_at` as `timestamptz`. All value and timestamp columns are nullable; null means never set. A `before insert or update` row trigger sets each timestamp: on insert, the write time for a non-null value; on update, the write time when that column's value changed, else its old timestamp (the write time is `clock_timestamp()`, not the transaction time, so a sleep tells a kept stamp from a new one in the SQL test); a change is a null-safe comparison (`is distinct from`), so null to a value stamps `now()` and a value to null clears the timestamp; it always overwrites any timestamp on the row (defence in depth: the grants already refuse a client write to a timestamp column). It runs as the calling role with an empty `search_path`. The trigger function is not callable through the API (its execute right is revoked from `public`, `anon`, and `authenticated`, as migration 1 does). Row-level security is enabled with one owner-only policy `for all to authenticated`. Grants are column-level and explicit: `select` on the table, `insert` on `account_id`, `theme`, `how_to_seen`, and `codex_sort`, `update` on the same four columns (an upsert sets every column it carries, `account_id` included, and the policy's check keeps it the caller's own id); no `delete` (the row goes with the account by cascade) and no rights on the timestamp columns.
- **Smoke script and SQL test.** `scripts/smoke-backend.ts` gains Preferences checks: anonymous read refused; own upsert reads back with server-set timestamps; a client-sent timestamp is refused by the grants; an upsert of one column leaves the other columns' timestamps untouched; an invalid theme, Codex sort, or `false` How-to seen refused; a row for another account refused; delete refused; and the account's original values restored where the row existed (restoring re-stamps the restored columns, since the trigger stamps every change, and a row created by the script cannot be removed, since players have no delete; the leftover row holds only nulls, is inert, and needs no cleanup script; the smoke script's header says so). `supabase/tests/preferences.sql` (owner-run, assertion style of `row-sync.sql`, which bypasses the grants) checks the trigger stamps (insert, null to value, value to null, an unchanged column keeping its timestamp) and its overwrite of a supplied timestamp, the grants, and the cascade. The smoke script is the only check of the server-set timestamps, since Vitest cannot run SQL.
- **No new domain term**, so `CONTEXT.md` does not change.

## Testing Decisions

Good tests drive behavior through the highest seam and assert the local store, the fake account's rows, and the screen, never internal calls.

- **Sync module tests** (`memoryStore`, the fake `Remote`, a fake clock; prior art `sync.test.ts`): a preference write is pushed after 1.5 seconds and only that key; an unchanged old theme on a device that already synced does not overwrite a newer account theme and is not pushed; a pending change survives a pull and is pushed next; a preference without a pending change takes the account's value; a device that never synced pushes its stored preferences and sends nothing for an unstored one or an invalid stored one (a default Codex sort never replaces the account's); a preference changed while signed out, on a device that already synced, survives the next sign-in's pull and is pushed; writing one preference before the first pull leaves the other stored preferences unmarked; a pull with no Preferences row on the account leaves local values alone; a stored preference the account lacks, on a device that already synced, is not pushed; an `AccountGoneError` on a Preferences push signs the device out; Sync's own writes never mark; a pulled value is never pushed back; two devices (two stores, one fake account) converge with the later push winning, per preference; a failed push keeps the change pending and the next trigger retries.
- **App-level test** (prior art `app.test.tsx`, `codex-page.test.tsx`): a pulled theme applies when the shell next mounts and a pulled Codex sort when the Codex screen next mounts, and neither changes a screen already mounted.
- **`Persist` tests** (`storage.test.ts`): `readPreferences` returns only stored valid values.
- **Adapter tests** (`supabase.test.ts`, injected fake library): row mapping both ways with nulls, an upsert carrying only the changed columns, and `AccountGoneError` on `23503`.
- **Fake `Remote`** gains a `preferences` field in its shared row set (empty by default, so every row-set literal in existing tests gains it), returned by pull and merged key by key by push, so two devices pushing different preferences both land.
- **Not in Vitest**: the SQL and the adapter against the real project (smoke script and `supabase/tests/preferences.sql`, hand-run).
- The existing suite passes; `pnpm lint`, `pnpm typecheck`, `pnpm test`, and `pnpm build` pass.

## Out of Scope

The Device progress choice (#138); Leaderboards (#139); Account deletion (#140); any Preferences UI or new preference; comparing timestamps on the client; a server-side monotonic rule; Sync UI.

## Further Notes

Author calls not decided by #137 or Spec 4, listed so they can be overruled:

- Value and timestamp columns are nullable, and null means "never set", so a device that never chose a preference sends nothing for it.
- The client never reads the timestamps. Spec 4's rule (a pending change keeps its value, else the account's value) is pending-based, and the trigger's timestamp is the server-side record of push time that the ticket requires.
- The trigger stamps a preference only when its value changes. An upsert of a preference with the value the account already holds keeps the older timestamp, since a trigger cannot tell a resent value from an unsent column.
- Column-level grants keep the client away from the timestamp columns. This is narrower than the table-level grants of migration 3.
- `How-to seen` is stored as a boolean that is only ever true.
- Upgrade window: a device that signed in under Row sync (#136) already has a last synced account id, so it does not count as never synced, and its stored preferences were never marked. On its next pull the account's value wins for each preference the account has, and a preference the account lacks is not sent until the player changes it. This one-time loss of a local theme, flag, or sort is accepted over adding a second marker key; it departs from the row sync spec's note not to read "never synced" as "has no account id" alone, and the owner can overrule it.
- "Never synced" is not reset by a sign-out or by another account signing in: a device that synced as one account and later signs in as another counts as synced, so the other account's preferences replace its unchanged local ones, while its Dailies, runs, Bests, and Codex import. The Device progress choice (#138, merged after this spec was written) owns the account switch: its "Add this device's progress" writes the new account id before Sync runs, so that path does not import the device's preferences either, although Spec 4 says the choice "imports as above". This is left for the owner to decide.
- A theme of `system` is accepted by the table, although the toggle only writes `light` and `dark`.
