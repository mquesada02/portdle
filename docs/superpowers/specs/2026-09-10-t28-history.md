# Spec: History grouped by date

Spec for #28. Tracker: https://github.com/mquesada02/portdle/issues/28

## Problem Statement

A player who opens History today sees one line per row, with every date and category mixed together in a single flat list and no visual separation between one day and the next. A day with all three Dailies played reads as three indistinguishable lines, so the player cannot tell at a glance which answers belong together.

## Solution

History groups its rows by date, newest first, with the date rendered as a heading for each group. Under each date heading sits a list of that day's rows, each showing a category badge, the entry's name, and the port in monospace. The page stays read-only: no row or badge is a link. The underlying rules for which rows appear — each of today's Dailies appears only once it is individually finished, and no date beyond today ever appears — are unchanged; this ticket only changes how the existing rows are grouped and presented.

## User Stories

### History

1. As a player, I want History grouped by date, newest first, with the date as a heading, so that a day's three answers read together.
2. As a player, I want each History row to show a category badge, the name, and the port in monospace, so that rows scan quickly.
3. As a player, I want History to stay read-only with no links to past Dailies, so that it remains an archive, not a playable list.
4. As a player, I want the newest date group at the top and each older date group below it in order, so that I can scan recent history first without hunting for it.
5. As a player, I want a date's rows kept in a stable, predictable order within their group, so that the same day always reads the same way.
6. As a player who has finished a Daily today, I want that Daily's row to appear in today's date group, so that today reads the same as any other day once that Daily is done.
7. As a player who has not yet finished a Daily today, I want that Daily's row omitted from today's date group rather than shown incomplete, so that History never reveals an unfinished answer.
8. As a player, I want no date beyond today ever listed, so that History never shows a future answer.
9. As a screen reader user, I want the page's outer list still named "History" and each date's rows reachable as their own group under that date's heading, so that the grouped structure announces clearly.

### Maintainer

10. As a maintainer, I want the grouping done from the existing History rows without changing the rules for which rows are included or their order, so that the date and eligibility logic stays in one place.
11. As a maintainer, I want the redesign to keep the existing accessible names where behavior did not change, so that the current tests keep passing with minimal edits.

## Implementation Decisions

### Design language

- Follows the parent spec's design language: Tailwind zinc for surfaces and text, no yellow or partial-hint colors, and the system monospace stack for the port. The category badge is a new element and, like every new element in the redesign, defines both light and dark colors.
- The category badge uses the same category display names already shown elsewhere (Mixed, Protocols, Applications). It is a visual grouping aid only, not a new naming scheme.

### Grouping

- The page consumes the existing, already-sorted rows exactly as produced today: newest date first, and within a date in a fixed category order. Grouping is a presentation step over that order — a new date heading starts whenever the date changes while walking the rows — and never re-sorts, re-filters, or re-derives eligibility.
- Which rows exist at all remains entirely the responsibility of the existing pure row-selection logic: each of today's Dailies appears only once it is individually finished, with no date beyond today ever included. The page performs none of that eligibility logic itself; the only date comparison it makes is the adjacent-row check that starts a new date heading.

### Structure

- The page keeps its single `h1` reading "History". The outer list keeps its accessible name "History", associated with that heading exactly as it is today.
- Each date group renders the date exactly as already produced by the existing rows, as a heading below the page's `h1`, immediately followed by that date's list of rows.
- A row renders its category badge, then the name, then the port in monospace. No row, badge, or list item is a link or otherwise interactive; History remains read-only end to end.
- A date group holds at most one row per Daily category — up to three rows — since the underlying row-selection logic still produces at most one row per category per date.

## Testing Decisions

A good test renders the app through its public seam and asserts what a player can see or do: roles, accessible names, and visible text. It does not assert class names, CSS, or component internals, and it does not recompute expected values the way the code does. Expected strings are literals from this spec.

One seam, already existing:

- **App seam.** Render `App` with a memory store, a memory history at the History route, and an injected `utcToday`. Prior art: the existing History test file, plus the shared helpers for the memory store, the daily-lookup test helper, and the `matchMedia` stub. Cover: the outer list is still named "History"; date headings appear newest first with each date's rows underneath the right heading, in their existing fixed order; each row's visible text includes its category badge, name, and port; the list contains no links; each of today's Dailies appears in today's date group only once it is individually finished, and is omitted while it alone is unfinished, including when its stored progress cannot be read; no date beyond today ever appears.

Tests that must change by this ticket's decision: the existing History assertions that walk one flat list of `listitem`s move to first finding each date heading, then asserting that date's rows appear within it. Every other accessible name and existing behavior assertion (today's inclusion rules, no-links check) keeps its current expectation, only re-expressed against the grouped structure.

No snapshot tests, no visual regression, no Playwright. This ticket is proven done by `pnpm lint`, `pnpm typecheck`, `pnpm test`, and `pnpm build` all passing, in addition to the App-seam coverage above.

## Out of Scope

- Any change to which rows are included, their eligibility, or their sort order (owned by the existing pure row-selection logic, unchanged by this ticket)
- Any change to persistence, routing, or catalog data
- Links from a History row back to its Daily, or any other new interactivity
- Filtering, searching, or collapsing date groups
- Styling or behavior of the Daily or Blitz screens
- Shell, nav, How-to, and Help (ticket #23, already merged)
- Motion (tile pop, shake, divider draw, reveal rise) — none of these apply to History in the parent spec
