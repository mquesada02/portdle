# Ticket spec: Read abort on timeout

Spec for #225. Tracker: https://github.com/mquesada02/portdle/issues/225. Parent: Spec 6 (https://github.com/mquesada02/portdle/issues/222, `docs/superpowers/specs/2026-10-04-spec6-tests-ci-motion.md`, "Read timeout", story 32). Map: https://github.com/mquesada02/portdle/issues/212. Builds on the Spec 5 error panel ticket (`docs/superpowers/specs/2026-09-30-t187-error-panel.md`). Base branch: `master`.

## Problem Statement

A server read that passes the 10-second timeout counts as failed, but its request keeps running. A read that a newer read replaces, or whose screen is gone, also keeps its request. A request runs for nothing, and its late response is dropped only by a flag in the client.

## Solution

A server read that passes the 10-second timeout, that a newer read replaces, or whose screen is gone, stops its request. The late response changes nothing. An abort counts as a failed read, as a timeout does today.

## User Stories

1. As a player, I want a read that passes the 10-second timeout to stop its request, so that no request runs for nothing.
2. As a player, I want a read that a newer read replaces to stop its request, so that only the newest request uses my connection.
3. As a player who leaves a screen, I want that screen's read to stop its request, so that the read does not use my connection after I leave.
4. As a player, I want a late response after an abort to change nothing, so that an old answer never replaces a newer one.
5. As a player, I want an aborted read to count as a failed read, so that the error panel and its retries work as before.
6. As a developer, I want one read helper that owns the abort signal, so that every read gets the same behavior.
7. As a developer, I want the Supabase adapter to pass the signal to `fetch`, so that the browser stops the request.

## Implementation Decisions

### Read helper

- The `Remote` public reads each take an optional last parameter, an abort signal. These reads are the catalog, the current Dailies, the Schedule, and the read of one Daily's Global stats, which takes the signal after its category and date. A `Remote` that ignores the signal stays valid. The helper still drops its late result.
- `settle` turns a read into `loading`, `ready`, or `failed`. It now takes a function that receives the signal, not a started promise.
- `settle` creates one abort controller and the timeout before it calls the function. The read may settle during that call, so `settle` must be safe for that.
- A synchronous throw from the function counts as a failed read. `settle` attaches both handlers to the value that the function returns, without wrapping it, so no rejection goes unhandled and a test can control when the read settles.
- When the timeout fires, `settle` marks the read failed, then aborts. When the returned cancel function is called before the read settles, `settle` marks the read done, then aborts, and drops the result. The done flag flips before the abort in both paths, so the rejection that the abort causes is ignored. A cancel after the read settled does nothing.
- A timeout abort counts as a failed read. A cancel changes no state.

### Server store

- The server store reads the catalog and the current Dailies through `settle`, so both receive the signal. A new catalog read already cancels the previous one. This cancel now also aborts the request.
- The current-Dailies read is a sequence of up to two reads: the Dailies, then the catalog again. The store's helper `within` owns the cancel of the read in progress. Its promise rejects when it is cancelled, so it never hangs.
- The store keeps one cancel handle and sets it again before each `within` call. `within` installs its handle before it calls `settle`, and nothing assigns the handle after `settle` returns.
- The handle works before `settle` has returned its cancel function. It calls that cancel only if it exists, then rejects. A newer read that starts while the older read is still being attached keeps its own handle.
- A newer `refreshDailies` calls the handle first, whichever step the older sequence is in. Between the two steps, the older sequence checks that it is still the newest, and it ends if it is not. It does this before it starts the second catalog read. A superseded sequence therefore never starts a request and never replaces the handle of the newer read.
- The older `refreshDailies()` promise then resolves and changes no state. It leaves the loading state to the newer read.

### Screens

- History's Schedule read goes through `settle`, so it receives the signal. Its effect cleanup already calls the cancel function, so a screen that goes away aborts the read.
- Global stats: the effect creates an abort controller, passes its signal to the stats read, and aborts it in its cleanup. This covers a screen that goes away, a new category or date, and the first run of the effect under StrictMode.
- The Global stats effect keeps its `current` check, so a late result of a `Remote` that ignores the signal changes nothing.
- The read starts after the Sync refresh. A cleanup during that refresh aborts the signal before the read starts, and the read then receives an aborted signal. Its request rejects at once, and the effect ignores the result.
- Global stats gets no timeout (author call 1).

### Adapter

- The Supabase adapter passes the signal in the request options of `fetch` for every public read. The shared request helper and the helper that reads all rows of a path take the signal. The helper that reads pages stays unchanged, because the page closure carries the signal to every page.
- An aborted `fetch`, or an abort during the body read, rejects. This counts as a failed read. The adapter adds no new error type.

### Callers and tests

- All callers of `settle` change: the store's two uses (the catalog read and `within`) and History's Schedule read. The existing `settle` tests change to the function form.
- The fake `Remote` is not changed. Tests that need the signal wrap it.
- Comments on the helper and the store say what the abort does.

## Testing Decisions

- A good test drives the read helper and the adapter through their public interfaces with a fake clock (Vitest fake timers) and a fake `fetch`. It asserts the signal state and the resulting read state (`loading`, `ready`, or `failed`), not internal calls.
- A wrapper of the fake `Remote` spreads the fake and overrides only the read that the test captures. The fake's methods do not use `this`, so a spread is safe. A thenable result needs a type cast in the test, and `settle`'s type does not change for it.
- Read helper tests, in `server-store.test.ts`:
  - The timeout aborts the signal, and the read is `failed`.
  - The cancel function aborts the signal and drops the result.
  - A response that arrives after the abort changes nothing.
  - A cancel after the read settled does not abort.
  - The rejection that an abort causes does not set a second state.
  - A synchronous throw from the read function counts as `failed`.
- Server store tests, in `server-store-refresh.test.ts`, which has a scripted `Remote` that controls each read by call:
  - A newer Dailies read aborts the signal of the older one. The older `refreshDailies()` promise resolves, and only the newer read sets state.
  - A newer Dailies read aborts the older one during its second catalog read too.
  - A newer Dailies read that starts between the two steps of the older sequence stops the older sequence before its second catalog read. The older sequence starts no request, and a third read aborts the newer one.
  - For that test, the store first loads fully. Its catalog lacks an entry of the Dailies that the special read returns, so the second catalog read is due. Only the special result carries the missing entry. The default Dailies of the fake are in the catalog.
  - The wrapped `Remote` returns the special result for the next Dailies read only. The wrapper method is not `async` and returns the result directly.
  - The special result is a thenable. Its `then` method calls the success callback and then calls `refreshDailies()` in the same call. By then `settle` has finished the first read, so the cancel does nothing. Only the check between the steps stops the older sequence.
  - The test asserts that the catalog read count does not change and that the signal of the newer read is aborted after the third read.
  - A catalog read that a retry started is aborted when the second catalog read of an older Dailies sequence applies. The test needs per-call control of the catalog reads, so the retry's read stays pending when the held read finishes. The shared hold of the fake `Remote` is not enough.
  - For that test, the store loads with a catalog that lacks an entry, and the test holds that second read. Then it marks the catalog failed with `rejectCatalog()`, calls `retry()`, and lets the held read finish. The signal of the retry's request is then aborted.
- End-to-end read tests, in `server-store.test.ts`. Each builds a store on the Supabase adapter with injected dependencies and uses fake timers. The fake `fetch` never answers, records its signal, and later answers without checking the signal:
  - After 10 seconds the recorded signal is aborted, the read is `failed`, and a late answer from the fake `fetch` changes nothing.
  - A newer Dailies read aborts the signal of the older read, and a late answer from the older request changes nothing.
- Adapter tests, in `supabase.test.ts` with its injected `fetch`:
  - Each of the four public reads passes the given signal to `fetch`.
  - An aborted `fetch` makes the read reject.
  - A paged read passes the signal to every page.
- Schedule screen test, in the existing History test file: leaving the screen aborts the signal of the Schedule read.
- Global stats test, in `global-stats.test.tsx`: leaving the screen aborts the signal of its read. The test flushes the Sync refresh before it captures the signal. A late result after the cleanup does not throw and shows nothing.
- Prior art: `server-store.test.ts`, `server-store-refresh.test.ts`, `supabase.test.ts`, `global-stats.test.tsx`.
- `pnpm lint`, `pnpm typecheck`, `pnpm test`, and `pnpm build` pass.

## Out of Scope

- Aborts for Leaderboard reads, the Sync pull and push, and the Account calls. They keep Spec 4's behavior.
- A timeout for the Global stats read.
- A retry timer or a change to the 10-second value.
- Changes to the Blitz screen, the Vitest configuration, `e2e/`, and CI (other Spec 6 tickets own them).

## Further Notes

No ADR is needed, and `CONTEXT.md` does not change. The Spec 6 file already supersedes the t187 out-of-scope item "An abort of the underlying `fetch` on timeout". The pull request targets `master`, with title `fix(client): abort reads on timeout or cancel` and body "Closes #225".

The owner accepted author calls 1 to 4 on 2026-10-05:

1. Global stats gets the signal and aborts when its screen goes away, but gets no 10-second timeout. The ticket says the read "receives an abort signal". A timeout there adds a new error timing that no ticket asks for. The alternative is to wrap it in `settle` too, which also puts a timeout on the Sync refresh before it. That alternative costs new visible behavior.
2. `settle` changes from taking a promise to taking a function with the signal. This is the only way the helper can own the controller before the request starts. No caller changes behavior, except for the abort.
3. The optional signal is the last parameter of each public read on `Remote`, not an options object. It follows the `fetch` convention and adds one argument.
4. A cancelled older Dailies sequence ends by rejection inside the store and changes no state. The store's `sequence` counter already guarantees this, so no new state is needed.
