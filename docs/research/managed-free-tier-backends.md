# Research: managed free-tier backends

Resolves [issue #115](https://github.com/mquesada02/portdle/issues/115), child of the [Backend: accounts, sync, leaderboards map (#114)](https://github.com/mquesada02/portdle/issues/114).

## Question

Which managed, free-tier backend fits Portdle — a static React SPA on GitHub Pages at a project subpath (`https://mquesada02.github.io/portdle/`) — for optional sign-in, cross-device sync (~1 MB of player data at the caps), and leaderboards (e.g. Blitz best score per category x orientation x mode, top N)? Candidates: Firebase, Supabase, Cloudflare (Workers + D1), Appwrite (Cloud).

This is **facts only**. No candidate is recommended here — that decision belongs to a later grilling ticket on map #114.

All research below is against primary sources (official docs/pricing pages) only, accessed **2026-09-28**, and covers the managed/cloud offering of each service (self-hosting is out of scope — the owner's constraint is "no servers to run").

## Detailed findings

### Firebase (Spark plan, i.e. no billing account attached)

**Top-line flags**

- Cloud Functions for Firebase are **not usable on Spark at all** — they require upgrading to Blaze (pay-as-you-go with a linked Cloud Billing account), even though Blaze's own quota includes a no-cost monthly allowance (2M invocations, 400K GB-seconds, 200K CPU-seconds, 5 GB outbound/mo). "Free" here means free in dollars, not free of attaching a billing instrument. [Source: https://firebase.google.com/pricing, accessed 2026-09-28] [Source: https://firebase.google.com/docs/functions, accessed 2026-09-28] [Source: https://firebase.google.com/docs/projects/billing/firebase-pricing-plans, accessed 2026-09-28]
- Phone Authentication has required a linked Cloud Billing account (Blaze) to send SMS since September 2024 — not usable on pure Spark. [Source: https://firebase.google.com/docs/auth/faq-and-troubleshooting, accessed 2026-09-28] [Source: https://firebase.google.com/docs/auth/limits, accessed 2026-09-28]
- Cloud Storage for Firebase (binary file storage) also requires Blaze for all projects since September 2024; every Spark row on the pricing table shows "Not applicable." [Source: https://firebase.google.com/docs/storage/faqs-storage-changes-announced-sept-2024, accessed 2026-09-28] [Source: https://firebase.google.com/pricing, accessed 2026-09-28]
- Email-link sign-in is capped at 5 emails/day on Spark (25,000/day on Blaze). [Source: https://firebase.google.com/docs/auth/limits, accessed 2026-09-28]
- Firestore and standard Auth (email/password, Google, GitHub, anonymous) remain fully usable on pure Spark with zero billing account attached.

**1. Auth providers.** Firebase Auth supports email/password, email link, phone, anonymous, Google, Facebook, Apple, Twitter, GitHub, Microsoft, Yahoo, Play Games, Game Center, custom tokens, SAML, and OIDC. [Source: https://firebase.google.com/docs/auth, accessed 2026-09-28] On the pricing table, "Other Authentication services" (the non-phone, non-SAML/OIDC providers) show as free/included on both Spark and Blaze with no MAU cap; the 50K-MAU and 50-MAU (SAML/OIDC) caps apply only under the optional "Identity Platform" upgrade layer, not to standard sign-in. Registered users are "Unlimited" on Spark; anonymous accounts cap at 100 million. [Source: https://firebase.google.com/pricing, accessed 2026-09-28] [Source: https://firebase.google.com/docs/auth/limits, accessed 2026-09-28]

**2. Free-tier limits.** Firestore (Standard edition) on Spark: 1 GiB stored data, 10 GiB/month network egress, 20K writes/day, 50K reads/day, 20K deletes/day, one free database per project. [Source: https://firebase.google.com/pricing, accessed 2026-09-28] [Source: https://firebase.google.com/docs/firestore/quotas, accessed 2026-09-28] Auth rate limits: 100 new accounts/hour/IP, Identity Toolkit API 1,000 req/sec & 10M req/day per project. [Source: https://firebase.google.com/docs/auth/limits, accessed 2026-09-28] Overage behavior: "If you exceed the no-cost quota limit in a calendar month for any product, your project's usage of that specific product will be shut off for the remainder of that month" (Spark). [Source: https://firebase.google.com/docs/projects/billing/firebase-pricing-plans, accessed 2026-09-28] No official documentation was found describing automatic pausing or deletion of inactive Spark projects (checked https://firebase.google.com/docs/projects/learn-more and https://firebase.google.com/support/faq); only explicit/manual project deletion has a documented (30-day recovery) policy. [Source: https://support.google.com/firebase/answer/9137886?hl=en, accessed 2026-09-28] Treat "no inactivity pausing" as unconfirmed-either-way rather than a documented guarantee.

1 GiB storage ÷ ~1 MB/player ≈ ~1,000 players' worth of data.

**3. Client SDK bundle size.** Firebase's own migration codelab publishes a measured table (gzipped): v8 namespaced full SDK 138 KB; v9 modular Auth-only 102 KB; v9 fully modular Auth + Firestore (realtime) 74.6 KB; v9 modular Auth + Firestore Lite (no realtime listeners) 34.9 KB. [Source: https://firebase.google.com/codelabs/upgrade-to-modular, accessed 2026-09-28] [Source: https://firebase.google.com/docs/web/setup, accessed 2026-09-28]

**4. Static-SPA-on-GitHub-Pages fit.** Firebase Auth's redirect flow uses an `authDomain` (default `PROJECT_ID.firebaseapp.com`) hosting `/__/auth/handler`. [Source: https://firebase.google.com/docs/auth/web/redirect-best-practices, accessed 2026-09-28] Adding a custom app domain to "Authorized domains" authorizes it at the **domain level, not the path level** — "whitelisting a domain allows for requests from any URL and port of that domain" — so `mquesada02.github.io/portdle/` inherits authorization from `mquesada02.github.io` being listed; no primary source discusses GitHub Pages subpaths by name, but the domain-scoped (not path-scoped) mechanism is explicit. [Source: https://support.google.com/firebase/answer/6400741?hl=en, accessed 2026-09-28] CORS is not enabled by default on Cloud Functions HTTP endpoints or Storage buckets and must be explicitly configured if used; no CORS gating is documented for the Firestore/Auth client SDK traffic itself. [Source: https://firebase.google.com/docs/functions/http-events, accessed 2026-09-28] [Source: https://firebase.google.com/docs/storage/web/download-files, accessed 2026-09-28]

**5. Per-user access rules / RLS.** Firestore Security Rules match `request.auth.uid` against a document path or field, e.g. `match /users/{userId} { allow read, write: if request.auth.uid == userId; }`. [Source: https://firebase.google.com/docs/firestore/security/rules-structure, accessed 2026-09-28] [Source: https://firebase.google.com/docs/firestore/security/rules-conditions, accessed 2026-09-28]

**6. Offline/client cache.** Firestore caches documents for offline access, but on web this is **disabled by default** — requires calling `enablePersistence()`. Default cache size 100 MB (configurable, 1 MB minimum, or unlimited), periodically evicts older/unused documents, persists across sessions, resolves conflicting offline writes last-write-wins. [Source: https://firebase.google.com/docs/firestore/manage-data/enable-offline, accessed 2026-09-28]

**7. Leaderboard top-N queries.** `orderBy()` + `limit()`, combinable with `where()` equality/range filters. [Source: https://firebase.google.com/docs/firestore/query-data/order-limit-data, accessed 2026-09-28] A composite index is required for filter+sort combinations across multiple fields (e.g. category + orientation + mode + score); missing indexes throw an error with a direct console link to auto-create it, or indexes can be predeployed via `firestore.indexes.json`. [Source: https://firebase.google.com/docs/firestore/query-data/indexing, accessed 2026-09-28]

**8. Server-side functions for score validation.** Every Cloud Functions line item (invocations, GB-seconds, CPU-seconds, outbound networking, build minutes) shows "Not applicable" on Spark on the live pricing table — the feature is entirely absent without Blaze. [Source: https://firebase.google.com/pricing, accessed 2026-09-28] "Upgrade your project to the pay-as-you-go Blaze pricing plan and deploy your functions using the Firebase CLI." [Source: https://firebase.google.com/docs/functions, accessed 2026-09-28] "Paid Google Cloud products and features ... are not available for projects on the Spark pricing plan." [Source: https://firebase.google.com/docs/projects/billing/firebase-pricing-plans, accessed 2026-09-28]

### Supabase (Free plan)

**1. Auth providers.** Email & password, magic link, email OTP, phone/SMS OTP (via a third-party SMS provider), anonymous sign-ins, ~19 social OAuth providers (Google, GitHub, Apple, Discord, Facebook, LinkedIn, Twitter/X, Twitch, Spotify, etc.), custom OAuth2/OIDC, and SAML 2.0 SSO for enterprise. [Source: https://supabase.com/docs/guides/auth, accessed 2026-09-28] No sign-in method is documented as blocked on Free; regular/OAuth users count toward the 50,000 MAU free quota, while SSO users are metered separately. [Source: https://supabase.com/docs/guides/auth, accessed 2026-09-28] Anonymous sign-ins have no plan-gating language found and count as MAU. [Source: https://supabase.com/docs/guides/auth/auth-anonymous, accessed 2026-09-28]

**2. Free-tier limits.** Database: 500 MB size, shared CPU, 500 MB RAM. File storage: 1 GB. Egress: 5 GB uncached + 5 GB cached/month. Auth: 50,000 MAU included, unlimited registered users, unlimited API requests. Edge Functions: 500,000 invocations/month. Max 2 active Free projects per organization. 1-day log retention, no backups/PITR/branching/custom domains on Free. [Source: https://supabase.com/pricing, accessed 2026-09-28] [Source: https://supabase.com/docs/guides/platform/manage-your-usage/monthly-active-users, accessed 2026-09-28] Overage on Free triggers a notification + grace period under the Fair Use Policy rather than auto-billing (no payment method attached). [Source: https://supabase.com/docs/guides/platform/manage-your-usage/egress, accessed 2026-09-28]

500 MB ÷ ~1 MB/player ≈ ~500 players' worth of data (before Postgres/index overhead).

**Project pausing (flagged as a real risk).** Free-tier projects are paused "after low activity over a 7-day period"; a few API/DB requests per day is enough to prevent pausing. [Source: https://supabase.com/docs/guides/platform/free-project-pausing, accessed 2026-09-28] A paused project is restored via a one-click resume in Supabase Studio — this requires the **project owner** to log in; the documentation gives no indication that an end player's own app traffic against a paused project auto-resumes it. Restorable via Studio for up to 1 year after pausing; after that, only a manual backup-based migration remains possible before deletion. [Source: https://supabase.com/docs/guides/platform/free-project-pausing, accessed 2026-09-28] [Source: https://supabase.com/docs/guides/troubleshooting/restore-project-after-90-days-pause, accessed 2026-09-28] Paid (Pro+) projects are exempt from inactivity pausing. [Source: https://supabase.com/docs/guides/platform/free-project-pausing, accessed 2026-09-28]

**3. Client SDK bundle size.** No gzipped/minified size figure is published on supabase.com/docs or supabase.com/pricing for `supabase-js`; checked the JS reference install page and the client-library marketing page, neither states a size. Flagged as not sourceable from Supabase's own primary documentation. [Source: https://supabase.com/features/client-library-javascript, accessed 2026-09-28] [Source: https://supabase.com/docs/reference/javascript/v1/installing, accessed 2026-09-28]

**4. Static-SPA-on-GitHub-Pages fit.** Supabase's API gateway applies a permissive CORS policy by default (all origins, all standard methods/headers) at the virtual-host level for the main API surface — calling the REST/PostgREST API from a GitHub Pages origin needs no special CORS configuration. [Source: https://supabase.com/docs/guides/self-hosting/self-hosted-envoy, accessed 2026-09-28] Edge Functions also support CORS via an importable `corsHeaders` helper. [Source: https://supabase.com/docs/guides/functions/cors, accessed 2026-09-28] Auth redirects use a "Site URL" default plus a "Redirect URLs" allow-list that supports glob wildcards (`*`, `**`, `?`, character ranges; separators `.`/`/`) — a pattern like `https://mquesada02.github.io/portdle/**` can be registered, though Supabase recommends exact paths in production over wildcards. No indication that project-subpath hosting is unsupported. [Source: https://supabase.com/docs/guides/auth/redirect-urls, accessed 2026-09-28]

**5. Per-user access rules / RLS.** Full Postgres Row Level Security: `ALTER TABLE ... ENABLE ROW LEVEL SECURITY`, then per-operation policies keyed to roles (`anon`, `authenticated`, `service_role`), enforced at the database layer regardless of access path. [Source: https://supabase.com/docs/guides/database/postgres/row-level-security, accessed 2026-09-28] No plan-gating language was found for RLS itself.

**6. Offline/client cache.** No offline-sync or client-cache capability for a deployed app is documented; the only "offline" capability is the CLI's local-development stack (a dev-environment tool, not a runtime offline layer). [Source: https://supabase.com/docs/guides/local-development, accessed 2026-09-28] Left entirely to the app.

**7. Leaderboard top-N queries.** `.order(column, { ascending })` + `.limit(rows)` via the query builder, e.g. filtering by category/orientation/mode then ordering by score descending with a limit. [Source: https://supabase.com/docs/reference/javascript/using-modifiers-order, accessed 2026-09-28] [Source: https://supabase.com/docs/reference/javascript/using-modifiers-limit, accessed 2026-09-28] Query-optimization docs recommend a composite index ordered as (filter columns, sort column) for exactly this access pattern. [Source: https://supabase.com/docs/guides/database/query-optimization, accessed 2026-09-28]

**8. Server-side functions for score validation.** Edge Functions are available on Free (no paid plan required): 500,000 invocations/month, 150s wall-clock limit on Free (400s on paid — the only plan-dependent limit), 2s max CPU time per request (excludes async I/O wait, same across all plans), 256 MB memory (same across all plans). [Source: https://supabase.com/docs/guides/functions, accessed 2026-09-28] [Source: https://supabase.com/docs/guides/functions/limits, accessed 2026-09-28] [Source: https://supabase.com/pricing, accessed 2026-09-28]

### Cloudflare (Workers Free + D1)

**1. Auth providers.** **No first-party end-user authentication product exists.** Cloudflare Access ("Cloudflare One") authenticates users to reach an application by validating them against an external IdP plus policy rules (email domain, country, device posture, etc.) — it is Zero-Trust access control for internal apps and team members, not a consumer sign-up/sign-in system; there is no email+password signup flow anywhere in the product. [Source: https://developers.cloudflare.com/cloudflare-one/, accessed 2026-09-28] [Source: https://developers.cloudflare.com/cloudflare-one/access-controls/policies/, accessed 2026-09-28] D1 is reachable only via the Workers Binding API (from inside a Worker) or an account-token-gated management REST API described as "best suited for administrative use." [Source: https://developers.cloudflare.com/d1/worker-api/, accessed 2026-09-28] Cloudflare's own tutorial for exposing D1 to an app says to "create an API using a Worker" and that customizing access control is the developer's job. [Source: https://developers.cloudflare.com/d1/tutorials/build-an-api-to-access-d1/, accessed 2026-09-28] A developer must hand-roll auth entirely in Worker code (OAuth code exchange, session-cookie issuance, credential storage in D1) or integrate a third-party auth provider — the single largest extra-build-effort item among the four candidates.

**2. Free-tier limits.** Workers Free: 100,000 requests/day (resets 00:00 UTC), 10 ms CPU time per HTTP request/Cron Trigger (waiting on I/O doesn't count), 50 subrequests/invocation, 128 MB memory/isolate, 100 Workers/account, 5 Cron Triggers/account. [Source: https://developers.cloudflare.com/workers/platform/limits/, accessed 2026-09-28] D1 Free: 500 MB/database (5 GB/account total, 10 databases/account), 5,000,000 rows read/day, 100,000 rows written/day, max SQL statement 100,000 bytes, max row size 2,000,000 bytes, max query duration 30s, 7-day point-in-time recovery. No egress/bandwidth charges. **No documented pausing/inactivity-suspension rule** — only hard daily quota errors on breach, with upgrade removing limits "typically within minutes." [Source: https://developers.cloudflare.com/d1/platform/limits/, accessed 2026-09-28] [Source: https://developers.cloudflare.com/d1/platform/pricing/, accessed 2026-09-28]

500 MB/database ÷ ~1 MB/player ≈ ~500 players' worth of data per database (~5,000/account across 10 databases); in practice the 100K-writes/day cap is likelier to bind first for an active small app.

**3. Client SDK bundle size.** No browser SDK is needed or provided — a Worker is just an HTTP endpoint, called with plain `fetch()`. [Source: https://developers.cloudflare.com/workers/examples/cors-header-proxy/, accessed 2026-09-28] D1 has no client-side/browser SDK at all. [Source: https://developers.cloudflare.com/d1/worker-api/, accessed 2026-09-28] Net effect: zero added client bundle size.

**4. Static-SPA-on-GitHub-Pages fit.** Cloudflare's official "CORS header proxy" Workers example sets `Access-Control-Allow-Origin`/`-Methods`/`-Max-Age` and handles `OPTIONS` preflight explicitly — CORS must be hand-implemented per this pattern, setting the origin to `https://mquesada02.github.io` (Origin headers never include the path, so the `/portdle/` subpath is irrelevant to CORS itself). [Source: https://developers.cloudflare.com/workers/examples/cors-header-proxy/, accessed 2026-09-28] With no built-in OAuth product, any "sign in with X" flow requires a Worker to perform the server-side authorization-code exchange, with the SPA itself parsing the callback URL/query params under its subpath (GitHub Pages does no server-side routing/rewrites) — standard SPA-on-subpath handling, not a Cloudflare feature.

**5. Per-user access rules / RLS.** **Confirmed absent.** D1's "Data security" reference page documents only encryption-at-rest/in-transit and compliance certifications — no row-level security or per-user policy engine. [Source: https://developers.cloudflare.com/d1/reference/data-security/, accessed 2026-09-28] D1 executes whatever SQL it's given with no server-enforced tenant isolation; the build-an-API tutorial confirms both authorization (e.g. `WHERE user_id = ?`) and input validation are the developer's responsibility inside Worker code. [Source: https://developers.cloudflare.com/d1/tutorials/build-an-api-to-access-d1/, accessed 2026-09-28]

**6. Offline/client cache.** The Workers "Cache" runtime API is an explicitly **server-side, edge** cache living in Cloudflare's data centers, not the end user's browser. [Source: https://developers.cloudflare.com/workers/runtime-apis/cache/, accessed 2026-09-28] No client-side/offline SDK is provided; any offline behavior for the SPA relies entirely on standard web-platform features.

**7. Leaderboard top-N queries.** Plain SQL: `SELECT ... WHERE category=? AND orientation=? AND mode=? ORDER BY score DESC LIMIT N`, since D1 uses SQLite's query engine (`EXPLAIN QUERY PLAN` available). [Source: https://developers.cloudflare.com/d1/best-practices/query-d1/, accessed 2026-09-28] A multi-column index (e.g. `(category, orientation, mode, score)`) is recommended to avoid a full table scan; D1 bills by **rows read (scanned), not returned**, so an unindexed leaderboard query costs more against the daily reads cap. [Source: https://developers.cloudflare.com/d1/best-practices/use-indexes/, accessed 2026-09-28] Each D1 database is single-threaded (one query at a time); Free plan caps queries per Worker invocation at 50 — ample for a single top-N read. [Source: https://developers.cloudflare.com/d1/platform/limits/, accessed 2026-09-28]

**8. Server-side functions for score validation.** Workers are Cloudflare's serverless compute layer by design — "Build APIs and connect to data stores," "no infrastructure to manage." [Source: https://developers.cloudflare.com/workers/, accessed 2026-09-28] Free plan gives 10 ms CPU time per HTTP request for custom logic (e.g. validating a submitted score before writing to D1) before an error is thrown; CPU time excludes I/O wait. Average Worker use is ~2.2 ms/request; "heavier workloads that handle authentication ... typically use 10-20 ms," which could approach the Free cap if auth-related compute (e.g. password hashing) is combined with validation logic in the same request. [Source: https://developers.cloudflare.com/workers/platform/limits/, accessed 2026-09-28]

### Appwrite Cloud (Free plan)

Appwrite Cloud (the managed SaaS) has three plans — Free ($0), Pro (from $25/mo), Enterprise. [Source: https://appwrite.io/pricing, accessed 2026-09-28] Appwrite's docs recently renamed "Documents/Collections" to "Rows/Tables" under a "TablesDB" product; some older doc URLs 404 as a result.

**1. Auth providers.** Email/password (Argon2 hashing), phone (SMS) passwordless, magic URL, email OTP, OAuth2 (40+ providers including Google, GitHub, Facebook, Apple, Discord, GitLab, Microsoft, Slack, Spotify, Twitch, Yahoo, Okta, Auth0, OIDC), anonymous sessions (convertible to full accounts), JWT, custom token (biometrics/passkeys), MFA. ## Notable / surprising findings

- **Firebase's Spark plan cannot run Cloud Functions at all.** Server-side score validation on Firebase requires attaching a billing account (Blaze), even if usage never exceeds Blaze's no-cost quota and $0 is ever charged. This is the clearest hard gate among the four services relative to "free tier ... no servers to run."
- **Cloudflare ships no end-user authentication product.** Workers + D1 would require hand-building the entire auth layer (OAuth exchange, sessions, credential storage) or paying for a third-party auth provider — a materially larger build than the other three candidates, which each include a full auth product.
- **Supabase and Appwrite both pause free projects after about a week of inactivity**, and in Supabase's case the documented resume path requires a human logging into the dashboard — it is not documented as auto-resuming from an end player's own app traffic. For a hobby game with sporadic players, this risks cross-device sync silently failing until someone manually resumes the project (or a scheduled keep-alive ping is added). Firebase and Cloudflare have no documented inactivity-pausing policy for their free tiers.
- **Appwrite's free database tier has no gigabyte cap** — unlike Firebase (1 GiB) and Supabase (500 MB), Appwrite bounds free database usage only by monthly read/write operation counts (500K reads / 250K writes), not by stored data volume.
- **Client bundle size varies widely by what's actually needed**: Cloudflare adds zero client SDK weight (plain `fetch()`), Appwrite's tree-shakeable ESM build is the lightest published/measured SDK (~42 KB gzip), and Firebase's fully modular Auth + Firestore is ~74.6 KB gzip (or ~35 KB using Firestore Lite, which drops realtime listeners).
- Two data points could not be confirmed from primary sources in this pass and are flagged rather than asserted: Supabase's `supabase-js` gzipped bundle size (not published), and Appwrite's hard `Query.limit()` ceiling on Cloud and its OAuth2 redirect URL-validation behavior for a subpath.
